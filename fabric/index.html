What Microsoft Fabric Is

In brief

§1.1.1One platform, sold as a service

Microsoft Fabric is an end-to-end analytics platform delivered as software as a service (SaaS). Instead of provisioning a storage account, a Spark cluster, a data warehouse and a Power BI capacity separately, you buy capacity and create items in workspaces. Microsoft runs the infrastructure.

Three ideas hold it together:

Idea What it means
OneLake One logical data lake for the whole tenant. Every Fabric item stores its data there
Open format Tables are stored as Delta Lake (Parquet files plus a transaction log), readable by any engine
Shared capacity Every workload draws from the same pool of capacity units (CUs)

§1.1.2The workloads

Workload Main items Typical users
Data Factory Pipelines, copy jobs, Dataflows Gen2, mirrored databases Data engineers, integration developers
Data Engineering Lakehouses, notebooks, Spark job definitions, environments Data engineers
Data Warehouse Warehouses, SQL analytics endpoints SQL developers, analytics engineers
Databases SQL database in Fabric, plus mirroring from external databases App developers, data engineers
Data Science Notebooks, ML models, experiments Data scientists
Real-Time Intelligence Eventstreams, Eventhouses, KQL querysets, real-time dashboards, Activator Streaming, IoT and operations teams
Power BI Semantic models, reports, dashboards, apps Analysts and business users
Fabric IQ Ontology and data agents that give AI a shared business model Analytics and AI teams

Everything appears in one web portal at app.fabric.microsoft.com, which is also the Power BI service.

§1.1.3How it relates to what came before

Previous product In Fabric
Power BI Premium capacities (P SKUs) Replaced by Fabric capacities (F SKUs); P SKUs are being phased out
Azure Synapse Analytics dedicated SQL pools Fabric Warehouse, with a migration assistant
Synapse Spark pools Fabric Spark in lakehouses and notebooks
Azure Data Factory Fabric Data Factory pipelines; existing ADF factories can be mounted in a workspace
Azure Data Explorer Eventhouses and KQL databases
Azure Data Lake Storage Gen2 OneLake, which exposes ADLS Gen2-compatible APIs

Azure Synapse and Azure Data Factory remain available as Azure services, but Microsoft's investment is going into Fabric. New analytics platforms on Microsoft technology usually start there.

§1.1.4What changes for a data team

Less infrastructure work. There are no clusters to size, no storage accounts to network, no separate Power BI capacity to manage.

New operational concerns. You manage capacity consumption instead of servers. One runaway notebook can slow Power BI reports for the whole company if they share a capacity. The fundamentals module covers throttling in detail.

Governance is closer to Power BI's model. Workspaces, roles, sharing and tenant settings will feel familiar to Power BI administrators and unfamiliar to Azure engineers used to resource groups and RBAC.

Engines share data. A table written by Spark can be queried by T-SQL and read by Power BI without copying, because everything is Delta in OneLake.

§1.1.5When Fabric fits, and when it doesn't

Fabric fits well when:

  • The organisation already uses Power BI and Microsoft 365.
  • Teams want one platform for ingestion, engineering, warehousing and reporting.
  • A small platform team needs to support many analysts without running infrastructure.

Think harder when:

  • You need fine-grained control over compute, networking or engine versions.
  • Your estate is heavily multi-cloud and already standardised on Databricks or Snowflake. Fabric can still sit alongside them through shortcuts and mirroring.
  • Workloads are extremely spiky and would need very large capacities for short peaks.

§1.1.6What good looks like

  • A clear reason for choosing Fabric, documented against alternatives.
  • Workloads mapped to items and capacities before migration starts.
  • A platform owner responsible for capacities, tenant settings and governance.

§1.1.7Red flags

  • Treating Fabric as "Power BI with extra buttons" and letting everyone create anything anywhere.
  • Moving every Synapse and ADF asset in a big bang without testing costs on capacity.
  • No plan for how shared capacity will be protected for business-critical reports.

§1.2.1Capacities and capacity units

A Fabric capacity is a pool of compute purchased in Azure as an F SKU. The number in the SKU is the number of capacity units (CUs):

SKU Capacity units Notes
F2, F4, F8, F16, F32 2 to 32 Development, small teams, departmental use
F64 64 Equivalent to the old Power BI Premium P1; free-licence users can view Power BI content
F128 to F2048 128 to 2,048 Large enterprise workloads

Every operation, from a Spark job to a report query, consumes CU-seconds from the capacity its workspace is assigned to.

Buying options:

  • Pay-as-you-go, billed per second while running, and pausable when not needed.
  • Reservations for one year at a significant discount, usually around 40%. Reservations cannot be paused to save money, because you have committed.
  • A trial capacity equivalent to F64 for 60 days.

Common pattern: reserve a baseline production capacity, use pay-as-you-go development capacities that pause out of hours.

§1.2.2Who needs which licence

Activity Licence needed
Creating and using Fabric items (lakehouses, notebooks, pipelines) in a workspace on an F capacity Free Fabric licence is enough
Creating, publishing and sharing Power BI content Power BI Pro or Premium Per User
Viewing Power BI content on F64 or larger Free licence
Viewing Power BI content on F32 or smaller Pro or PPU

That licence threshold at F64 is often what drives capacity sizing for organisations with many report viewers.

§1.2.3Bursting and smoothing

Fabric lets operations use more compute than the capacity's size for short periods, called bursting, so jobs finish faster. The borrowed usage is then smoothed, meaning spread over future time:

Operation type Examples Smoothed over
Interactive Report queries, ad hoc SQL, on-demand notebook runs At least 5 minutes
Background Scheduled refreshes, pipelines, scheduled Spark jobs 24 hours

This is why an F64 can run a job that briefly needs far more than 64 CUs. It is also why a large overnight job can leave the capacity "in debt" well into the next day.

§1.2.4Throttling

When smoothed usage exceeds what the capacity can pay back, Fabric throttles in stages, based on how many minutes of future capacity have already been consumed:

Future usage consumed What happens
Up to 10 minutes Overage protection: no throttling
10 to 60 minutes Interactive delay: new interactive operations are delayed by about 20 seconds
60 minutes to 24 hours Interactive rejection: new interactive operations are rejected; background jobs still run
Over 24 hours Background rejection: all new operations are rejected

The practical effect: a heavy set of background jobs can make Power BI reports slow or unavailable for everyone on that capacity. Surge protection lets administrators set a lower threshold at which new background jobs are rejected, protecting headroom for interactive users.

§1.2.5Sizing a capacity

There is no reliable formula. A sensible approach:

  1. Start a trial or pay-as-you-go capacity for a representative workload.
  2. Run real pipelines, refreshes and report tests for at least a week.
  3. Install the Fabric Capacity Metrics app and look at peak smoothed utilisation, throttling events and the top consuming items.
  4. Choose a SKU where normal peaks sit well below 100%, leaving room for growth and surprises.
  5. Reassess monthly for the first quarter.

§1.2.6Designing around shared capacity

Pattern Why
Separate production and development capacities Experiments cannot throttle business reports
Separate capacity for heavy data engineering from Power BI consumption in larger estates Background debt doesn't block interactive queries
Schedule heavy jobs in quiet periods Smoothing pays back before business hours
Use surge protection on capacities serving reports Protects interactive users
Consider autoscale billing for Spark where available Spark jobs billed separately on demand instead of consuming the shared capacity

§1.2.7What good looks like

  • Capacities split by environment and, at scale, by workload type.
  • The Capacity Metrics app reviewed weekly by a named owner.
  • Pay-as-you-go development capacities paused outside working hours.
  • A licence plan that matches the number of report viewers to the F64 threshold.

§1.2.8Red flags

  • Everything in one capacity, including data scientists' experiments and the CEO's dashboard.
  • Upgrading the SKU every time reports slow down, without finding the item causing it.
  • Nobody knows what throttling looks like until a board meeting report fails.
  • A reservation bought before measuring real consumption.

§1.3.1The administrative layers

Layer What lives there Who manages it
Tenant Tenant settings, capacities, domains, audit and usage data Fabric administrators
Capacity Compute pool, workload settings, capacity admins and contributors Capacity administrators
Domain A logical grouping of workspaces by business area Domain administrators and contributors
Workspace Items, roles, Git connection, workspace identity Workspace admins
Item Lakehouse, warehouse, notebook, report and so on Item owners and permitted users

The Fabric administrator role in Entra ID, together with Global Administrators and Power Platform administrators, controls the admin portal.

§1.3.2Tenant settings that matter on day one

The admin portal has hundreds of settings. Review these early:

Setting Why it matters
Users can create Fabric items Enable for specific security groups rather than everyone at first
Workspace creation Decide who can create workspaces; uncontrolled creation leads to sprawl
External sharing and guest access Controls sharing outside the organisation
Export and download Controls exporting data from reports and items
Service principals can use Fabric APIs Needed for automation and CI/CD; restrict to a group
Copilot and Azure OpenAI features Whether AI features are available and whether data may be processed outside your geography
Delegation to domain and capacity admins Lets business areas manage some settings locally

Most settings can apply to the whole organisation, to specific security groups, or to everyone except specific groups. Always prefer groups.

§1.3.3Domains

A domain groups workspaces that belong to a business area, such as Finance, Sales or Supply Chain, with optional subdomains. Domains support a data mesh style of ownership:

  • Domain admins can manage some tenant settings for their domain.
  • Items can be filtered and discovered by domain in the OneLake catalog.
  • Endorsement and governance reporting can be viewed per domain.

Assign workspaces to domains from the start. Retrofitting ownership onto hundreds of workspaces is painful.

§1.3.4Designing workspaces

A workspace is the unit of access, Git integration, deployment and capacity assignment. Design it around those.

A common pattern for a data product:

Workspace Contents
Sales - Ingest [Dev] / [Test] / [Prod] Pipelines, mirrored databases, bronze and silver lakehouses
Sales - Model [Dev] / [Test] / [Prod] Gold lakehouse or warehouse, semantic models
Sales - Reports [Prod] Reports and apps for business users

Why split:

  • Different people. Engineers need write access to ingestion; analysts need read access to gold data; business users need only reports.
  • Different lifecycles. Reports change weekly; ingestion pipelines less often.
  • Different capacities. Heavy engineering can sit on a different capacity from reports.

Keep the split modest. Dozens of tiny workspaces per product become unmanageable.

§1.3.5Workspace roles

Role Can do
Admin Everything, including managing access and deleting the workspace
Member Everything except removing admins or deleting the workspace; can share items
Contributor Create, edit and delete items; cannot share or manage access
Viewer View and read items; with SQL endpoints and Direct Lake, often read data too

Workspace roles apply to every item in the workspace. For finer control, grant item permissions instead of workspace roles, covered in the security module.

§1.3.6Workspace identity

A workspace identity is a managed identity for the workspace, created in Entra ID. Items such as pipelines, shortcuts and semantic models can use it to connect to data sources, for example to reach a firewall-protected storage account through trusted workspace access. It removes the need for personal credentials on connections.

§1.3.7What good looks like

  • Item creation and workspace creation enabled for defined groups, not the whole organisation.
  • Domains assigned to every workspace, with named domain owners.
  • Workspaces designed around access, lifecycle and capacity, with a naming convention.
  • Workspace identities used for connections instead of individuals' accounts.

§1.3.8Red flags

  • Thousands of personal "My workspace" artefacts feeding production reports.
  • A workspace where 60 people are Admin.
  • Tenant settings still at defaults a year after rollout.
  • Connections that stop working when the engineer who created them leaves.

§2.1.1One lake per tenant

OneLake is a single, logical data lake that comes with every Fabric tenant. You don't create it, size it or network it. Every workspace is a folder in OneLake, and every data item stores its contents there:

OneLake (tenant)
└── Sales - Model [Prod]            (workspace)
    ├── SalesGold.Lakehouse         (item)
    │   ├── Tables/                 (managed Delta tables)
    │   │   └── fact_orders/
    │   └── Files/                  (any files: CSV, JSON, images)
    └── SalesDW.Warehouse
        └── Tables/dbo/dim_customer/

The benefit is simple: one copy of data, visible to every engine that has permission, instead of exports between a lake, a warehouse and Power BI.

§2.1.2Delta Lake as the common format

Tables in OneLake are stored as Delta Lake: Parquet data files plus a _delta_log folder of JSON commit records. Delta gives:

Feature Meaning
ACID transactions Readers never see half-written data
Time travel Query or restore earlier table versions
Schema enforcement and evolution Bad writes rejected; controlled column additions
Efficient updates and deletes MERGE, UPDATE, DELETE on lake data

Because Spark, the SQL engines, Power BI Direct Lake and KQL all read the same Delta tables, a table written by a notebook is immediately available to T-SQL and reports.

Fabric also applies V-Order, a write-time optimisation of Parquet layout that speeds up reads, especially for Direct Lake and SQL. It remains valid Parquet that any tool can read.

§2.1.3Reaching OneLake from outside Fabric

OneLake speaks the ADLS Gen2 and Blob APIs, so existing tools work with a OneLake path:

abfss://Sales - Model [Prod]@onelake.dfs.fabric.microsoft.com/SalesGold.Lakehouse/Tables/fact_orders

Workspace and item GUIDs can replace names, which is more robust to renames.

  • Azure Databricks, Azure Synapse Spark and other Spark engines can read and write with Entra ID authentication.
  • Azure Storage Explorer and azcopy work against OneLake endpoints.
  • The OneLake file explorer app for Windows shows OneLake like OneDrive.

Access is always authenticated with Entra ID and checked against Fabric permissions. There are no storage account keys.

§2.1.4Iceberg and other formats

OneLake can present tables in other formats too:

  • Shortcuts to Apache Iceberg tables in other storage can be virtualised so Fabric engines read them as Delta, without copying.
  • Delta tables in OneLake can be exposed with Iceberg metadata for engines such as Snowflake that prefer Iceberg.

This format virtualisation is what makes Fabric workable next to Snowflake and Databricks estates.

§2.1.5The OneLake catalog

The OneLake catalog is where users discover and manage data items across the tenant:

  • Explore: search and filter items by workspace, domain, type, owner, endorsement and tags.
  • Govern: governance insights such as ownership gaps, sensitivity label coverage and lineage, generally available since early 2026.

Endorse important items as Promoted or Certified so users can tell trusted data from experiments.

§2.1.6Storage costs

OneLake storage is billed per GB per month, separately from capacity compute, at rates similar to ADLS Gen2 hot storage. Two things drive storage growth unexpectedly:

  • Delta history. Old file versions remain until VACUUM removes them.
  • Soft-deleted data retained for recovery.

Table maintenance is covered in the data engineering module.

§2.1.7What good looks like

  • Tables written as Delta in lakehouses, not as loose CSV and Parquet files in Files/.
  • External engines reading OneLake directly instead of exporting copies.
  • Important items endorsed and discoverable in the OneLake catalog.
  • Storage growth monitored alongside capacity usage.

§2.1.8Red flags

  • Nightly CSV exports from one Fabric item into another.
  • A "lake" that is really a folder of spreadsheets nobody can query.
  • Paths hard-coded to workspace names that get renamed.
  • Nobody running VACUUM, with storage doubling every quarter.

§2.2.1Shortcuts: reference instead of copy

A shortcut is a pointer in a lakehouse (or KQL database) to data stored somewhere else. It appears as a normal folder or table, but no data is copied.

Shortcut source Notes
OneLake (another Fabric item) Share a gold table with another workspace without copying
Azure Data Lake Storage Gen2 Existing Azure lake data
Amazon S3 and S3-compatible storage Multi-cloud data; enable shortcut caching to reduce egress costs
Google Cloud Storage Multi-cloud data
Dataverse Dynamics 365 and Power Platform data
Other sources supported by the platform Check current documentation as the list grows

Shortcuts under Tables/ must point at Delta tables, or at Iceberg tables that Fabric can virtualise. Shortcuts under Files/ can point at any files.

How permissions work#

  • OneLake shortcuts pass through the caller's identity: the user must have access to the target data in the other workspace.
  • External shortcuts (ADLS, S3, GCS) use a connection with stored credentials, such as a service principal, workspace identity or key. Anyone who can read the shortcut can read the data through that connection.

That second point is a governance trap: an external shortcut with broad credentials effectively re-shares that storage with everyone who has access to the lakehouse.

§2.2.2Mirroring: continuous replication into OneLake

Mirroring replicates a database into OneLake as Delta tables, continuously and in near real time, with no pipelines to build.

Mirroring source Status as of 2026
Azure SQL Database, Azure SQL Managed Instance, SQL Server Generally available
Azure Cosmos DB Generally available
Azure Database for PostgreSQL Generally available
Snowflake Generally available
Oracle, SAP Datasphere Generally available
Google BigQuery, Azure Databricks Unity Catalog Supported
Open mirroring partners APIs for vendors and your own code to land change data

A mirrored database item provides:

  • Delta tables in OneLake that stay in sync with the source.
  • A SQL analytics endpoint for T-SQL queries.
  • Direct Lake-ready tables for Power BI.

Cost#

Replication compute for mirroring is free, and mirrored data gets free OneLake storage up to a limit based on capacity size (1 TB per capacity unit). Querying the mirrored data consumes capacity as usual. This makes mirroring very attractive compared with building and paying for ingestion pipelines.

Things to check before mirroring#

  • Source impact. Mirroring usually reads change data from the source's transaction log or change feed. Check database settings, such as change feed or CDC requirements, and load on busy systems.
  • Supported types and limits. Some data types, table counts or features are not supported.
  • Networking. Sources behind firewalls or private networks may need a gateway or specific network configuration.
  • Schema changes. Understand how added or dropped columns flow through.

§2.2.3Shortcut, mirror or copy?

Situation Choose
Delta or Iceberg tables already in ADLS, S3 or GCS, maintained elsewhere Shortcut
Share a table between Fabric workspaces OneLake shortcut
Operational database you want in analytics with minimal latency and no pipelines Mirroring
Snowflake data you want Power BI to query in Direct Lake Mirroring or Iceberg interoperability
Source not supported by mirroring, or needing heavy reshaping on the way in Copy job, pipeline or Dataflow Gen2
Files in unusual formats needing parsing Pipeline or notebook into a lakehouse

§2.2.4Designing with shortcuts

A clean pattern is a "hub" lakehouse per consuming team that contains only shortcuts to certified gold tables from producer workspaces. Consumers get one place to query, producers keep ownership, and there is still only one copy of the data.

Avoid long shortcut chains, where a shortcut points to a shortcut that points to another. They make lineage and permission troubleshooting miserable.

§2.2.5What good looks like

  • Mirroring used for supported operational sources instead of hand-built CDC pipelines.
  • OneLake shortcuts for sharing between workspaces, not copies.
  • External shortcuts using workspace identities or narrowly scoped credentials.
  • A documented list of which data is shortcut, mirrored and copied, and who owns the source.

§2.2.6Red flags

  • An S3 shortcut using an access key with read access to the whole bucket.
  • Mirroring enabled on a critical production database with no one checking source load.
  • Five copies of the same customer table, each refreshed by a different pipeline.
  • Shortcut chains three levels deep.

§3.1.1What a lakehouse is

A lakehouse is a Fabric item that combines a data lake folder structure with managed tables. It is the natural home for data engineering with Spark.

Area Contents Managed by
Tables/ Delta tables, registered automatically as tables Spark, pipelines, Dataflows Gen2, shortcuts
Files/ Any files: raw CSV, JSON, Parquet, images, PDFs Anything that writes files

Creating a lakehouse also creates a SQL analytics endpoint, a read-only T-SQL interface over its tables.

Lakehouse schemas let you organise tables into schemas, such as sales.orders and finance.ledger, instead of one flat list. Use them for new lakehouses with more than a handful of tables.

§3.1.2Writing to a lakehouse

Tool Typical use
Spark notebooks and Spark job definitions Transformations, merges, complex logic
Pipelines and copy jobs Landing data from sources
Dataflows Gen2 Low-code shaping with Power Query
Eventstreams Streaming events into Delta tables
Shortcuts Referencing data stored elsewhere

Writing a Delta table with Spark:

orders = spark.read.format("json").load("Files/landing/orders/2026/09/")
(orders
   .withColumnRenamed("orderTs", "order_ts")
   .write.mode("append")
   .format("delta")
   .saveAsTable("bronze.orders"))

Upserting into a silver table:

from delta.tables import DeltaTable

target = DeltaTable.forName(spark, "silver.orders")
(target.alias("t")
   .merge(updates.alias("s"), "t.order_id = s.order_id")
   .whenMatchedUpdateAll()
   .whenNotMatchedInsertAll()
   .execute())

§3.1.3The SQL analytics endpoint

The SQL analytics endpoint lets analysts query lakehouse tables with T-SQL and connect tools such as SQL Server Management Studio, Azure Data Studio's successors, and Power BI.

What it does:

  • Read-only T-SQL over Delta tables: SELECT, views, table-valued functions, stored procedures that read data.
  • Row-level security, column-level security and dynamic data masking defined in T-SQL.
  • Cross-database queries with warehouses and other endpoints in the same workspace.

What it does not do:

  • Write to lakehouse tables. Use Spark, pipelines or Dataflows.
  • Read loose files in Files/.

Metadata sync#

The endpoint discovers new and changed Delta tables through an automatic metadata sync. There can be a short delay between Spark writing a table and the endpoint showing the change. In pipelines that write with Spark and then immediately query through SQL, trigger or wait for a sync, or the query may return stale data.

§3.1.4Semantic models

Earlier, every lakehouse and warehouse automatically created a default semantic model. Microsoft has moved away from that: create semantic models explicitly, with the tables, relationships and measures you intend people to use. Explicit models are easier to govern and version.

§3.1.5When a lakehouse is the right choice

Choose a lakehouse when Consider a warehouse when
Engineers work mainly in Python and Spark The team works mainly in T-SQL
Data arrives as files or semi-structured formats Workloads need multi-table transactions
You need to store unstructured data alongside tables You want stored procedures to own all transformations
You follow a medallion architecture with Spark Migrating from Synapse dedicated pools or SQL Server

Many estates use both: lakehouses for bronze and silver, and either a lakehouse or a warehouse for gold.

§3.1.6What good looks like

  • Raw files in Files/, structured data in Delta tables under Tables/.
  • Schemas used to organise tables in larger lakehouses.
  • Explicit semantic models over curated tables.
  • Pipelines that account for SQL endpoint metadata sync.

§3.1.7Red flags

  • Critical data kept only as CSV files in Files/.
  • Hundreds of tables in one flat lakehouse with no naming scheme.
  • Analysts complaining the SQL endpoint shows yesterday's data after an engineering run.
  • Reports built on an automatically generated model nobody owns.

§3.2.1A T-SQL data warehouse on OneLake

The Fabric Warehouse is a fully transactional, T-SQL data warehouse. Its tables are stored as Delta in OneLake, so Spark and Power BI can read them, but only the warehouse engine writes to them.

Lakehouse SQL analytics endpoint Warehouse
Write with T-SQL (INSERT, UPDATE, MERGE) No Yes
Multi-table transactions No Yes
CREATE TABLE, ALTER TABLE No (Spark owns tables) Yes
Stored procedures that transform data Read-only Yes
Who writes the tables Spark, pipelines, Dataflows Warehouse engine only

There is no infrastructure to size. The engine scales compute automatically and consumes capacity.

§3.2.2Loading data

COPY INTO dbo.stg_orders
FROM 'https://onelake.dfs.fabric.microsoft.com/<workspace-id>/<lakehouse-id>/Files/landing/orders/*.parquet'
WITH (FILE_TYPE = 'PARQUET');

Other options:

  • INSERT INTO ... SELECT from lakehouse tables in the same workspace using three-part names.
  • CREATE TABLE AS SELECT (CTAS) for fast full rebuilds.
  • Pipelines with the Copy activity writing to warehouse tables.
  • Dataflows Gen2 with a warehouse destination.

§3.2.3Transforming with T-SQL

A typical gold-layer load in a stored procedure:

CREATE OR ALTER PROCEDURE gold.load_fact_orders
AS
BEGIN
    BEGIN TRANSACTION;

    DELETE FROM gold.fact_orders
    WHERE order_date >= DATEADD(day, -3, CAST(GETDATE() AS date));

    INSERT INTO gold.fact_orders (order_id, customer_key, order_date, net_amount)
    SELECT o.order_id, c.customer_key, o.order_date, o.net_amount
    FROM SalesSilver.dbo.orders AS o
    JOIN gold.dim_customer AS c ON c.customer_id = o.customer_id
    WHERE o.order_date >= DATEADD(day, -3, CAST(GETDATE() AS date));

    COMMIT TRANSACTION;
END;

Transactions use snapshot isolation. Readers see a consistent version while loads run, and concurrent writers to the same table can conflict. Design loads so two processes don't update the same table at once.

§3.2.4Zero-copy clones and time travel

  • Table clones create a new table that references the same underlying files, instantly and without duplicating storage:

    CREATE TABLE gold.fact_orders_backup AS CLONE OF gold.fact_orders;

  • Time travel queries data as it was at a point in the retention window:

    SELECT * FROM gold.fact_orders OPTION (FOR TIMESTAMP AS OF '2026-09-01T08:00:00');

  • Warehouse snapshots give a stable, read-only view of the whole warehouse at a point in time, useful so reports don't see half-finished nightly loads.

  • Restore points let you restore the warehouse to an earlier state.

§3.2.5Performance habits

  • Keep statistics current; the engine creates many automatically, but check after large loads.
  • Prefer set-based T-SQL over cursors and row-by-row loops.
  • Use appropriate data types; avoid VARCHAR(MAX) for keys and joins.
  • Avoid huge numbers of tiny inserts. Batch them, or land data in a lakehouse and load in bulk.
  • Check the query insights views (queryinsights.exec_requests_history and related) for slow and expensive queries.

§3.2.6Migrating from Synapse dedicated SQL pools

Microsoft provides a migration assistant for Synapse dedicated pools and SQL Server-based warehouses. It converts schema and code and flags incompatibilities. Plan for:

  • Differences in supported T-SQL features and data types.
  • Replacing distribution and index design, which Fabric handles itself.
  • Rewriting loading processes that used PolyBase or specific external table patterns.
  • Re-testing performance and capacity consumption, which behave differently from reserved DWUs.

§3.2.7What good looks like

  • Warehouse used where teams genuinely work in T-SQL and need transactions.
  • Loads wrapped in transactions, idempotent, and not overlapping on the same tables.
  • Warehouse snapshots or equivalent patterns to shield reports from partial loads.
  • Query insights reviewed for the most expensive queries.

§3.2.8Red flags

  • Spark and warehouse teams both expecting to write the same gold tables.
  • Row-by-row cursor logic migrated unchanged from an on-premises warehouse.
  • Thousands of single-row inserts per minute from an application.
  • A migration declared complete without capacity load testing.

§3.3.1SQL database in Fabric

SQL database in Fabric, generally available since November 2025, is an operational (OLTP) database built on the Azure SQL Database engine and delivered as a Fabric item.

  • Create it in a workspace in seconds, with no server settings to manage.
  • Use it for application data, metadata stores, configuration tables and small operational apps.
  • It automatically replicates its data into OneLake as Delta tables in near real time, so analytics can query it without pipelines.
  • It supports Entra ID authentication, a SQL analytics endpoint over the replicated data, Git integration for schema, and GraphQL APIs through Fabric's API for GraphQL item.

It consumes Fabric capacity and scales compute automatically with load.

When to use it, and when not#

Use SQL database in Fabric Prefer Azure SQL Database
Internal apps and tools whose data should flow straight into analytics Customer-facing applications needing dedicated performance guarantees
Writeback from Power BI reports and data apps Workloads needing features Fabric's database doesn't support yet
Metadata and control tables for data pipelines Apps whose load would compete badly with shared analytics capacity
Prototypes that may grow into analytics products Strict network isolation requirements beyond Fabric's options

For existing Azure SQL databases, use mirroring instead of moving them.

§3.3.2The Eventhouse

An Eventhouse hosts one or more KQL databases, optimised for large volumes of time-stamped event data: telemetry, logs, clickstreams and IoT. It is the Real-Time Intelligence store, covered in its own module. Choose it when queries are mostly time-window aggregations over fast-arriving events.

§4.1.1How Spark runs in Fabric

Every notebook and Spark job definition runs on a Spark session drawn from a pool, and consumes capacity while running.

Pool type Behaviour Use for
Starter pool Pre-warmed; sessions typically start in seconds Most interactive work and small to medium jobs
Custom pool You choose node size and autoscale range; sessions take longer to start Heavy jobs needing larger nodes or specific limits

Capacity administrators control which pools workspaces may use and the maximum size of Spark compute, which stops one workspace from consuming the whole capacity.

§4.1.2Environments

An environment item bundles:

  • The Spark runtime version (Spark, Delta and Python versions).
  • Libraries from PyPI, Conda or uploaded wheel and JAR files.
  • Spark properties, such as shuffle partitions.
  • The pool to use.

Attach an environment to notebooks and Spark job definitions, or set a workspace default. This replaces ad hoc %pip install in production notebooks, which slows every session start and drifts between runs.

§4.1.3High concurrency mode

High concurrency mode lets several notebooks share one Spark session, each with isolated variables. It reduces session start-ups and capacity use when an engineer works across several notebooks, or when a pipeline runs many small notebooks in sequence.

§4.1.4The native execution engine

The native execution engine runs supported Spark operations in a vectorised native C++ engine instead of the Java virtual machine, often speeding up queries significantly with no code changes. Enable it in the environment. Unsupported operations fall back to normal Spark automatically.

§4.1.5Python notebooks

Not every task needs Spark. Python notebooks run on a single small node with libraries such as pandas, polars and duckdb. They start quickly and cost far less for small data:

import polars as pl

df = pl.read_delta("/lakehouse/default/Tables/silver/orders")
daily = df.group_by("order_date").agg(pl.col("net_amount").sum())
daily.write_delta("/lakehouse/default/Tables/gold/daily_sales", mode="overwrite")

A few thousand to a few million rows is usually faster and cheaper without Spark.

§4.1.6notebookutils

notebookutils (formerly mssparkutils) provides platform helpers:

# Read a secret from Azure Key Vault using the notebook's identity
api_key = notebookutils.credentials.getSecret("https://kv-data-prod.vault.azure.net/", "partner-api-key")

# Run another notebook with parameters
notebookutils.notebook.run("load_customers", 600, {"load_date": "2026-09-17"})

# Work with files in OneLake
notebookutils.fs.ls("Files/landing/orders")

Never paste secrets into notebook cells. Notebook contents are versioned, shared and exported.

§4.1.7From exploration to production

Notebooks start life as exploration. Before one runs in a production pipeline:

Habit Why
Parameter cell at the top Pipelines pass dates, environments and paths
Idempotent writes: MERGE or overwrite by partition Safe reruns after failure
No display() of large data frames Wastes capacity and memory
Logic in functions or shared modules, not 40 cells of copy-paste Testable and reusable
Explicit schemas when reading files Catches bad source data early
Default lakehouse set deliberately, or full table names used Avoids writing to the wrong place after deployment
Stored in Git through workspace Git integration Reviewed and versioned

§4.1.8Spark job definitions

A Spark job definition runs a Python file or JAR as a batch job, without notebook cells. Use it for mature, code-first pipelines built and tested in a normal repository with unit tests.

§4.1.9What good looks like

  • Environments with pinned libraries attached to production notebooks.
  • Python notebooks for small data; Spark only where it earns its keep.
  • Native execution engine enabled and tested.
  • Secrets read from Key Vault; parameter cells; idempotent writes.

§4.1.10Red flags

  • %pip install at the top of every scheduled notebook.
  • A custom pool with huge nodes used for a 50,000-row CSV.
  • Production pipelines running notebooks named Untitled 14.
  • Connection strings typed into cells.

§4.2.4Data quality in silver

  • Reject or quarantine rows that fail rules, such as null business keys or negative quantities.
  • Deduplicate on business keys with a deterministic rule, such as latest updated_at wins.
  • Record rule failures in a quality table so trends are visible.
  • Fail the pipeline when failure rates exceed a threshold, rather than silently loading bad data.

§4.2.5Why Delta tables slow down

Frequent small writes create many small Parquet files. Updates and deletes create old file versions that are no longer current. Over time:

  • Queries open thousands of files, which is slow.
  • Storage grows with files kept only for time travel.

§4.2.6Maintenance commands

OPTIMIZE compacts small files into larger ones and can apply V-Order:

OPTIMIZE silver.orders VORDER;

Z-ORDER co-locates data by commonly filtered columns in the compaction:

OPTIMIZE silver.orders ZORDER BY (customer_id) VORDER;

VACUUM deletes files no longer referenced by the table and older than the retention period (default 7 days):

VACUUM silver.orders RETAIN 168 HOURS;

After VACUUM, time travel to versions older than the retention period no longer works. Don't shorten retention below 7 days without understanding concurrent readers and recovery needs.

The lakehouse UI offers table maintenance for running these on demand, and you can schedule them in notebooks or pipelines. Spark optimize write and auto-compaction settings reduce small files at write time.

§4.2.7Partitioning, carefully

Partitioning splits a table into folders by a column, such as order_date. It helps only when:

  • Tables are large (hundreds of gigabytes or more).
  • Queries filter on the partition column.
  • Each partition holds a sensible amount of data, ideally at least a gigabyte.

Over-partitioning small tables, for example by date and customer, creates millions of tiny files and makes everything slower. When in doubt, don't partition, and rely on compaction and V-Order.

Task Frequency

§4.2.9What good looks like

  • Bronze kept immutable and replayable; quality enforced in silver; consumers on gold.
  • Load metadata columns on every bronze and silver table.
  • Scheduled OPTIMIZE and VACUUM with retention decisions documented.

  • Choose source tables or folders and a destination.
  • Choose full or incremental copy. Incremental mode tracks a watermark column, or uses change data capture where the source supports it.
  • Schedule it.

§5.1.7Apache Airflow jobs

§5.2.1Dataflows Gen2

Dataflows Gen2 use Power Query, the same experience as Excel and Power BI Desktop, to connect, clean and shape data, then write it to a destination.

  • More than 150 connectors, including files, databases, SaaS apps and APIs.
  • Hundreds of transformations through a visual editor, with the M language underneath.

  • Scheduling, or running from a pipeline.
  • Git integration and deployment pipeline support, generally available, plus variable library integration for per-environment values.

§5.2.2Staging and performance

By default, Dataflows Gen2 use a staging lakehouse and warehouse to process queries at scale, then write to the destination. Useful habits:

  • Query folding: keep transformations that the source can execute, such as filters and column selection, early in the query, so work is pushed down to the source. Check the folding indicators.
  • Enable Fast Copy for large data volumes from supported sources.
  • Disable staging for small queries where it adds overhead.
  • Avoid merging huge tables in Power Query; do heavy joins in Spark or SQL.
  • Filter to incremental data rather than reloading everything.

Dataflows consume capacity like everything else. A poorly folded dataflow over millions of rows can be one of the most expensive items on a capacity.

§5.2.4Gateways

On-premises data gateway practices#

  • Install on dedicated servers, not someone's desktop.
  • Run a cluster of at least two gateway members for high availability.
  • Keep gateways updated; old versions stop working with new features.
  • Size the servers for concurrent refreshes; monitor CPU and memory.
  • Control who can create connections on the gateway.

VNet data gateway practices#

  • Delegate a dedicated subnet with enough addresses.
  • Ensure DNS resolves private endpoints from that subnet.
  • Remember it runs on capacity-linked infrastructure; check regional availability.

  • Actions: Teams messages, emails, running a Fabric pipeline or notebook, or calling Power Automate flows.

§7.1.1Why semantic models matter

A semantic model (formerly dataset) sits between data and reports. It defines tables, relationships, measures written in DAX, hierarchies, formatting and row-level security. A good model means every report calculates "net revenue" the same way. A bad model means every report invents its own.

§7.1.2Storage modes

Mode Where data lives when queried Freshness Performance Main cost
Import Compressed copy in the model's memory As of last refresh Excellent Refresh time and capacity; model size limits
DirectQuery Queries sent to the source each time Live Depends on the source; often slower Source load
Direct Lake Delta tables in OneLake, loaded into memory on demand Near real time after framing Close to Import Capacity memory; guardrails by SKU
Composite Mix of modes per table Mixed Mixed Complexity

Direct Lake is the Fabric-native mode. It reads Delta tables written by Spark, the warehouse, mirroring or Dataflows directly, so there is no import refresh copying data into the model.

§7.1.3Two flavours of Direct Lake

Direct Lake on SQL endpoints Direct Lake on OneLake
Reads tables through A lakehouse SQL analytics endpoint or warehouse OneLake Delta tables directly
Can combine tables from several items No, one source Yes
Falls back to DirectQuery Yes, when guardrails are exceeded or SQL-only features like views or SQL security are involved No; queries stay in Direct Lake
Security Can respect SQL endpoint security through fallback Uses OneLake security and model security

For new models on Fabric data, Direct Lake on OneLake is usually the better default. Direct Lake on SQL endpoints remains useful where you depend on SQL views or SQL-level security.

§7.1.4Framing and refresh

A Direct Lake model points at a specific version of each Delta table. Framing updates the model to the latest versions. It is fast, because it copies metadata, not data.

  • Automatic updates reframe when the underlying Delta tables change.
  • For multi-step loads, turn automatic updates off and refresh (reframe) at the end of the pipeline, so reports never see a half-finished load where facts are updated but dimensions are not.

§7.1.5Guardrails and fallback

Each capacity SKU has guardrails for Direct Lake, such as maximum rows per table, number of Parquet files per table and model memory. When a Direct Lake on SQL endpoints model exceeds them, queries fall back to DirectQuery, which is usually much slower. Direct Lake on OneLake returns an error instead of falling back.

Avoid surprises:

  • Keep gold tables compacted, with sensible file counts, by running OPTIMIZE.
  • Use V-Order on tables read by Direct Lake.
  • Check fallback behaviour in performance testing, and set the model's fallback behaviour deliberately (for example "Direct Lake only" to surface problems rather than hide them).

§7.1.6Modelling habits that still matter

  • A star schema: fact tables surrounded by dimension tables with single-direction relationships.
  • Measures for calculations rather than calculated columns where possible.
  • Only the columns reports need; high-cardinality text columns, such as GUIDs and free text, cost memory.
  • Date tables marked as date tables.
  • Clear names and descriptions, which also help Copilot and data agents answer questions correctly.

Direct Lake doesn't fix a bad model. It just reads a bad model faster.

§7.1.7Models as code

Develop semantic models and reports as files so they can be reviewed and deployed:

  • Power BI Project (PBIP) format saves reports and models as folders of text files.
  • TMDL (Tabular Model Definition Language) represents models in readable text, one file per table, friendly to Git diffs.
  • Fabric Git integration syncs semantic models and reports between workspaces and Azure DevOps or GitHub repositories.
  • Tools such as Tabular Editor and semantic link in notebooks help with bulk changes, testing and documentation.

§7.1.8Security in models

  • Row-level security (RLS) roles filter data per user, for example by region.
  • Object-level security (OLS) hides tables or columns from roles.
  • With Direct Lake on SQL endpoints, SQL-level security can also apply through fallback. With Direct Lake on OneLake, OneLake security roles apply.

Test RLS with "view as role" and with real test accounts.

§7.1.9What good looks like

  • Shared, endorsed semantic models reused by many reports.
  • Direct Lake on OneLake for new Fabric-native models; import only where justified.
  • Reframing controlled at the end of multi-step loads.
  • Models developed as PBIP and TMDL in Git, with descriptions on tables and measures.

§7.1.10Red flags

  • Every report with its own imported copy of the same data.
  • Direct Lake models silently falling back to DirectQuery because gold tables have 40,000 files.
  • Reports showing mismatched totals mid-load.
  • Measures named Measure 17.

Build Build reports on a semantic model
Reshare Share the item onwards

A common mistake is granting ReadAll to analysts who only need SQL access, which lets them bypass SQL row-level security by reading the files directly.

§8.1.4OneLake security

OneLake security defines data access roles on lakehouses and other items. A role grants access to specific tables or folders, and can include row-level and column-level rules. Because it is enforced on OneLake data itself, it applies consistently across engines that honour it, including Spark, SQL analytics endpoints and Direct Lake on OneLake.

It moved towards general availability through 2026. Check which engines and item types honour it in your tenant before relying on it as the only control.

§8.1.5SQL security in warehouses and SQL endpoints

-- Column-level security
GRANT SELECT ON dbo.employees (employee_id, department, job_title) TO [analysts];

-- Dynamic data masking
ALTER TABLE dbo.customers ALTER COLUMN email ADD MASKED WITH (FUNCTION = 'email()');

-- Row-level security
CREATE FUNCTION security.fn_region_filter(@region AS varchar(20))
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS allowed
   WHERE @region = (SELECT region FROM security.user_regions WHERE upn = USER_NAME());

CREATE SECURITY POLICY security.region_policy
ADD FILTER PREDICATE security.fn_region_filter(region) ON dbo.fact_sales
WITH (STATE = ON);

SQL security protects SQL access paths only. Users with ReadAll or workspace roles can read the files another way.

§8.1.6A least-privilege pattern

Audience Access
Data engineers for a domain Contributor on dev ingest workspaces; Viewer or deploy-only in production
Platform automation Service principal or workspace identity with the roles pipelines need
Analytics engineers Contributor on the model workspace; read on gold data
Analysts Item permissions: Read and ReadData on gold SQL endpoints or warehouses, Build on certified semantic models
Business users Access to reports and apps only
Data scientists ReadAll on specific gold or silver lakehouses through OneLake security roles

Use Entra security groups everywhere, owned by the business area.

§8.1.7Sharing outside the organisation

  • B2B guests can be given access to workspaces and reports, controlled by tenant settings.
  • External data sharing lets you share OneLake data in place with another Fabric tenant, without copying.
  • Publish to web creates public, anonymous report links. Disable it tenant-wide unless there is an approved need.

§8.1.8What good looks like

  • Workspace roles for builders; item permissions and OneLake security for consumers.
  • ReadAll granted deliberately and rarely.
  • Row and column rules defined once and tested per engine.
  • Groups, not individuals, in every role.

§8.1.9Red flags

  • Business users as workspace Viewers on engineering workspaces "so they can see the data".
  • SQL row-level security carefully built, while the same users have ReadAll.
  • Publish to web enabled for everyone.
  • Access requests approved by adding people as Members.

§8.2.1The starting point

By default, Fabric is reachable over the internet with Entra ID authentication, and workloads can connect out to public endpoints. For many organisations, identity controls are the first and strongest layer.

§8.2.2Inbound: who can reach Fabric

Control Scope Effect
Entra Conditional Access Tenant Require MFA, compliant devices, trusted locations to sign in
Tenant-level Private Link Whole tenant Fabric reachable only through private endpoints from your networks, with public access blocked
Workspace-level private links Individual workspaces Specific workspaces reachable only privately, while others remain public

Tenant-level Private Link is a big switch. Blocking public access affects every user and every feature, and some features have limitations when it is enabled. Test thoroughly.

Workspace-level private links, now generally available, are more targeted: put sensitive workspaces behind private connectivity while keeping the rest of the tenant easy to use. Inbound access protection at workspace level lets workspace admins restrict public access to those workspaces.

§8.2.3Outbound: where Fabric can send data

Outbound access protection (OAP), generally available since March 2026, is the key data exfiltration control. When enabled on a workspace:

  • Outbound connections from Spark and other supported workloads are blocked by default.
  • Administrators allow specific destinations: approved storage accounts, other workspaces and connectors.

Without it, anyone who can run a notebook can send data to any internet endpoint.

§8.2.4Reaching private resources

Feature Lets Notes
Managed private endpoints Spark in a workspace reach private Azure resources such as storage, SQL, Key Vault Created in a managed virtual network for the workspace; approved on the target resource

VNet data gateway Dataflows, semantic models and pipelines reach private sources Subnet delegated in your virtual network
On-premises data gateway Reach on-premises and firewalled sources Servers you run

§8.2.5Encryption

  • Data is encrypted at rest with Microsoft-managed keys by default, and in transit with TLS.
  • Customer-managed keys at workspace level let you use keys in Azure Key Vault for supported items, for organisations whose policies require it. Check which items support it, and plan key rotation and access carefully; losing the key means losing access to the data.

§8.2.6Data residency

  • The tenant has a home region; each capacity has a region, which determines where workspace data is stored.
  • Multi-geo capacities place specific workspaces' data in other regions.
  • AI features may process data outside the region if tenant settings allow; review them for regulated data.

§8.2.7A practical rollout

  1. Conditional Access with MFA and device requirements for Fabric users.
  2. Tenant settings reviewed for sharing, export and publishing.
  3. Outbound access protection on workspaces holding sensitive data.
  4. Managed private endpoints and trusted workspace access instead of opening storage firewalls.
  5. Workspace-level private links for the most sensitive workspaces.
  6. Tenant-level Private Link only if policy requires it, after a thorough pilot.

§8.2.8What good looks like

  • Identity controls first, then outbound protection for sensitive workspaces.
  • No storage firewalls opened to all networks for Fabric's sake.
  • Private links targeted at workspaces that need them.
  • Customer-managed keys only where required, with a key management runbook.

§8.2.9Red flags

  • Notebooks able to post confidential data to any website.
  • Tenant-level Private Link switched on without a pilot, breaking reports for remote staff.
  • Storage accounts left public because "Fabric couldn't connect otherwise".
  • Customer-managed keys with no tested recovery plan.

§8.3.1Governance goals

Good governance answers five questions quickly:

  1. What data do we have? Catalogue.
  2. Can I trust it? Endorsement, ownership, quality.
  3. Where did it come from and what uses it? Lineage.
  4. How sensitive is it? Classification and labels.
  5. Who did what? Audit.

§8.3.2Endorsement and ownership

Endorsement Meaning Who can apply
Promoted The owner thinks it's ready to share Item contributors
Certified Meets the organisation's quality bar Authorised reviewers set in tenant settings
Master data Authoritative core reference data Authorised reviewers

Define what "Certified" means: documented owner, descriptions, tested refresh, quality checks, support contact. Then use it consistently, or it means nothing.

§8.3.3The OneLake catalog

The OneLake catalog is the discovery and governance hub:

  • Explore lets users find items by domain, workspace, type, endorsement, tags and owner, and preview details they have access to.
  • Govern gives data owners and admins insights: items without owners or descriptions, sensitivity label coverage, endorsement gaps, and recommended actions. It became generally available in 2026.

Encourage "search the catalog first" before anyone builds a new copy of data.

§8.3.4Lineage and impact analysis

The lineage view shows how data flows between items in a workspace and across workspaces: sources to pipelines to lakehouses to semantic models to reports. Impact analysis shows what depends on an item before you change or delete it, and can notify contacts of affected items.

Use impact analysis before renaming columns in gold tables. It is the easiest way to avoid breaking reports you didn't know existed.

§8.3.5Microsoft Purview integration

Sensitivity labels (Information Protection) Label items such as Confidential or Highly Confidential; labels flow to downstream items and to exported files such as Excel and PDF

§8.3.6Auditing and monitoring usage

  • Purview audit captures user and admin activities: viewing reports, exporting, sharing, changing permissions, creating items.
  • The admin monitoring workspace provides usage and activity reports for administrators.
  • Workspace monitoring captures detailed logs and metrics for items in a workspace into an Eventhouse for KQL analysis.

Useful recurring checks:

  • Exports of data from sensitive reports.
  • New external shares and guest access.
  • Items without owners after staff leave.
  • Workspaces with no activity in 90 days, for archiving.

§8.3.7Domains and federated governance

Combine domains with delegated settings: a central team sets tenant-wide guardrails, while domain owners handle certification, access requests and quality for their data. This scales better than one central team approving everything.

§8.3.8What good looks like

  • Clear certification criteria, applied to a small set of trusted items.
  • Sensitivity labels with defaults and inheritance, covering most items.
  • Impact analysis as a standard step before breaking changes.
  • Audit data reviewed for exports, sharing and ownership gaps.

§8.3.9Red flags

  • Everything "Promoted", nothing trusted.
  • Sensitive semantic models exported to Excel with no label or DLP.
  • Deleted columns breaking dozens of reports discovered from user complaints.
  • Governance run by one person approving tickets for 5,000 users.

§9.1.1Git integration

Workspace Git integration connects a workspace to a branch in Azure DevOps or GitHub. Supported items are serialised as files, such as notebooks as .py, semantic models as TMDL, reports as PBIR, pipelines as JSON.

  • Commit changes from the workspace to Git.
  • Update the workspace from Git.
  • Each developer can use a private dev workspace connected to a feature branch, then merge through a pull request.

Supported items include notebooks, Spark job definitions, environments, lakehouses (metadata, not data), warehouses, SQL databases, pipelines, Dataflows Gen2, semantic models, reports, Eventhouses, KQL items, variable libraries and more. Check the current list for anything unusual.

Git stores definitions, not data. Tables and files in OneLake are not versioned by Git.

§9.1.2A branching model that works

Branch Connected workspace Purpose
feature/* Personal or feature dev workspace Individual development
main Shared dev or integration workspace Integrated, reviewed changes
Releases Test and production workspaces via deployment Promotion, not direct editing

Nobody edits production workspaces by hand.

§9.1.3Option 1: deployment pipelines

Deployment pipelines are built into Fabric. They connect workspaces as stages, typically Development, Test and Production (up to ten stages), and deploy items between them.

  • Compare stages to see differences.
  • Deploy selected items or everything.
  • Use deployment rules and variable libraries to change data source connections and parameters per stage.
  • Automate through REST APIs.

They are the simplest route for teams without strong DevOps skills, and work well for Power BI-heavy workspaces.

§9.1.4Option 2: code-first CI/CD with fabric-cicd

fabric-cicd is a Python library for deploying Fabric items from a Git repository into workspaces. Since FabCon 2026 it is officially supported by Microsoft.

from fabric_cicd import FabricWorkspace, publish_all_items, unpublish_all_orphan_items

target = FabricWorkspace(
    workspace_id="00000000-0000-0000-0000-000000000000",
    environment="PROD",
    repository_directory="./workspace",
    item_type_in_scope=["Notebook", "DataPipeline", "Environment", "SemanticModel", "Report"],
)
publish_all_items(target)
unpublish_all_orphan_items(target)

A parameter.yml file replaces environment-specific values, such as lakehouse IDs and connection IDs, at deploy time. Run it from GitHub Actions or Azure Pipelines using a service principal or workload identity federation.

§9.1.5Variable libraries

A variable library item holds named values with different value sets per environment: connection IDs, lakehouse names, API URLs, feature switches. Pipelines, notebooks, Dataflows Gen2 and shortcuts can reference variables, so the same item definition works in every stage.

§9.1.7Testing

  • Notebooks: unit test transformation functions in a normal Python project; run data quality checks after loads.
  • Semantic models: rules with Best Practice Analyser; DAX query tests comparing measures to known values.
  • Pipelines: run in test workspaces against representative data before promotion.

§9.1.8What good looks like

  • Every production workspace deployed from Git, never edited directly.
  • Environment differences held in variable libraries or deployment parameters.
  • Service principals with least privilege running deployments.

§9.1.9Red flags

§9.2.2Investigating a slow or throttled capacity

  1. Open the Capacity Metrics app and select the time of the problem.
  2. Check throttling charts: interactive delay, interactive rejection or background rejection.
  3. Look at utilisation split into interactive and background.
  4. Drill into the timepoint to see top items and operations by CU consumption.
  5. Identify the culprits: often a large Dataflow, an unoptimised notebook, a semantic model refresh, or a burst of Copilot or report queries.
  6. Decide: optimise the item, reschedule it, move it to another capacity, or scale up.

Remember smoothing. A heavy background job at 02:00 can still be consuming capacity at 10:00.

§9.2.3Reducing consumption

Pipelines Incremental loads; avoid unnecessary full copies; parallelism sized to capacity
Eventhouses Right-size minimum consumption; retention and cache policies

  • Give large teams or domains their own capacities, which makes allocation simple.
  • For shared capacities, use Capacity Metrics data to apportion CU consumption by workspace and domain.
  • Allocate OneLake storage by workspace from storage reports.
  • Tag capacities in Azure with owner and cost centre.

§9.2.6Operational alerts worth having

  • Capacity utilisation above 80% sustained, and any throttling event.
  • Pipeline and refresh failures for production items.
  • Gateway offline.
  • Eventstream or Eventhouse ingestion lag.
  • Storage growth anomalies.

§9.2.7What good looks like

  • Cost reported to domains, creating incentives to optimise.

§9.2.8Red flags

  • Nobody has installed the Capacity Metrics app.
  • Every morning's reports slow because all refreshes start at 06:00.
  • An F128 bought to cope with one badly written Dataflow.

§S1.2Context

Power BI import models held copies of the same gold tables in 14 separate models. Nightly refreshes took four hours and often failed, so morning reports showed yesterday's or older data. Analysts exported data to Excel to join it with their own files.

§S1.3The design

Component Choice
Engineering Databricks remains the engineering platform, writing gold Delta tables to ADLS Gen2

§S1.4What went well

  • No copies. Gold data stayed in one place, owned by the engineering team.
  • Freshness. Reports reframed within minutes of Databricks jobs completing, instead of waiting for nightly refreshes.
  • Consolidation. Fourteen overlapping models became four certified ones with consistent measures.
  • Self-service. Analysts combined gold data with their own files in Fabric instead of Excel exports.

§S1.5What went wrong

  • File counts. Some Databricks tables had tens of thousands of small files. Direct Lake guardrails were exceeded and early models fell back to DirectQuery and ran slowly. Engineering added regular compaction.
  • V-Order. Tables written by Databricks lacked V-Order, so Direct Lake performance was good rather than great. The team accepted this rather than rewriting tables in Fabric.
  • Permissions confusion. Analysts assumed the shortcut credential restricted them to certain tables, but the workspace identity could read the whole container. The team narrowed the storage role assignment to the gold container and added OneLake security roles.

§S1.6Outcome

Morning reports were current by 07:00 every day for six months. Capacity use for reporting dropped because import refreshes disappeared. The engineering team kept its existing Databricks investment.
