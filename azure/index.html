§1.1.1The hierarchy in one picture

Everything you create in Azure sits in a strict hierarchy. Getting it right early saves months of rework, because permissions, policies and budgets all flow down it.

Level What it is What you use it for
Microsoft Entra tenant Your organisation's identity directory Users, groups, app registrations, sign-in policies
Management group A folder for subscriptions, nestable up to six levels Applying policy and access to many subscriptions at once
Subscription A billing and scale boundary Separating environments, teams or workloads, and their bills
Resource group A container for resources that share a lifecycle Deploying, securing and deleting things together
Resource An individual service instance A web app, a database, a key vault

A tenant can contain many subscriptions. A subscription trusts exactly one tenant for identity. A resource belongs to exactly one resource group, and a resource group belongs to exactly one subscription.

§1.1.2Subscriptions are boundaries, not folders

People new to Azure often put everything in one subscription and use resource groups to separate environments. That works for a prototype and becomes a problem quickly, because a subscription is where several hard boundaries live:

  • Access. Anyone with Owner or Contributor on a subscription can change every resource in it. Separate subscriptions make it easy to give developers broad rights in development and almost none in production.
  • Limits. Many service quotas are per subscription per region, such as vCPU counts.
  • Cost. Invoices, budgets and cost reports break down naturally by subscription.
  • Policy. Azure Policy can be assigned at subscription level with different rules per environment.

A common, sensible starting point for a product team:

Subscription Contents
sub-platform-connectivity Shared networking: hub virtual network, DNS zones, firewall
sub-app-dev Development environment for the application
sub-app-test Test or staging environment
sub-app-prod Production only, tightly controlled

These sit under management groups such as Platform and Landing zones, with Corp for private internal apps and Online for internet-facing ones. This is the shape Microsoft's Cloud Adoption Framework calls an Azure landing zone.

§1.1.3Resource groups: group by lifecycle

A resource group should contain things that are created, updated and deleted together. The test is simple: if you deleted the group, would you want everything in it gone?

  • Good: rg-orders-api-prod containing the Container App, its managed identity and its Application Insights resource.
  • Bad: rg-shared containing a production database, a test web app and a VM someone created last year.

Resource groups have a location, but it only stores the group's metadata. Resources inside can live in other regions. Keep them aligned anyway, because it reduces confusion.

§1.1.4Regions, availability zones and region pairs

A region is a set of datacentres in a geography, such as UK South or West Europe. Choose regions for data residency, latency to users, service availability and price, which varies by region.

Most major regions have availability zones: physically separate datacentres with independent power, cooling and networking. Services use them in two ways:

  • Zone-redundant. The service spreads itself across zones automatically. Examples include zone-redundant storage, Azure SQL with zone redundancy enabled, and App Service plans with zone redundancy.
  • Zonal. You pin a resource, such as a VM, to a specific zone and arrange redundancy yourself.

Many regions also have a paired region in the same geography, used for some platform replication and staged updates. Pairing matters less for application design than it used to. Design disaster recovery around the regions your services support, and test it.

§1.1.5Naming and tagging

Names are hard to change later. Most resources cannot be renamed at all. Adopt a convention before the first deployment. A widely used pattern is type-workload-environment-region-instance:

rg-orders-prod-uks-001
app-orders-api-prod-uks-001
kv-orders-prod-uks-001

Some names must be globally unique, because they become DNS names. Storage accounts and key vaults are the usual surprises. Storage account names also cannot contain hyphens.

Tags are name-value pairs used for cost reporting and ownership. A minimum useful set:

Tag Example
owner orders-team@contoso.com
environment prod
costCentre CC-1042
application orders

Tags do not inherit from resource groups by default. Use Azure Policy to require or inherit them.

§1.1.6What good looks like

  • Separate subscriptions for production and non-production at minimum.
  • Management groups that let the platform team apply guardrails once.
  • Resource groups that follow lifecycle, with a naming convention written down.
  • Zone redundancy chosen deliberately for production data and compute.

§1.1.7Red flags

  • One subscription with dozens of people holding Owner.
  • Resource groups named after people, or test, new and temp.
  • No tags, so nobody can say who owns a costly resource.
  • A production workload in a region chosen because it was the portal default.

§1.2.1Everything goes through Azure Resource Manager

The portal, the Azure CLI, PowerShell, Bicep, Terraform and the SDKs all do the same thing underneath: they call the Azure Resource Manager (ARM) API. ARM authenticates the caller with Entra ID, checks Azure RBAC permissions, evaluates Azure Policy, and then asks the relevant resource provider, such as Microsoft.Web or Microsoft.Sql, to do the work.

This matters for three reasons:

  1. One permission model. Access to create or change resources is controlled in one place.
  2. One audit trail. The Activity Log records control-plane operations whichever tool made them.
  3. Everything is declarative underneath. Every resource has a JSON representation with an API version, which is what infrastructure-as-code tools generate.

ARM covers the control plane: creating a storage account, changing a web app's settings. Reading blobs or querying a database is the data plane, which has its own endpoints and often its own permissions. Keep the distinction in mind, because it explains most "I'm Owner but I can't read the data" confusion.

§1.2.2Why infrastructure as code

Clicking through the portal is fine for learning. For anything that matters, define resources in code, commit it to Git, and deploy it through a pipeline.

Portal changes Infrastructure as code
No record of why something changed Pull requests with review and history
Environments drift apart Dev, test and prod come from the same templates
Rebuilding after a mistake is guesswork Redeploy from source
Hard to review security settings Settings are visible in code review and scannable

§1.2.3Bicep

Bicep is Microsoft's language for ARM deployments. It compiles to ARM JSON, supports every resource type on the day it ships, and needs no state file, because ARM itself is the source of truth.

param location string = resourceGroup().location
param appName string

resource plan 'Microsoft.Web/serverfarms@2024-04-01' = {
  name: 'asp-${appName}'
  location: location
  sku: { name: 'P0v3', tier: 'PremiumV3' }
  kind: 'linux'
  properties: { reserved: true }
}

resource app 'Microsoft.Web/sites@2024-04-01' = {
  name: 'app-${appName}'
  location: location
  identity: { type: 'SystemAssigned' }
  properties: {
    serverFarmId: plan.id
    httpsOnly: true
    siteConfig: {
      linuxFxVersion: 'DOTNETCORE|8.0'
      minTlsVersion: '1.2'
      ftpsState: 'Disabled'
    }
  }
}

output principalId string = app.identity.principalId

Deploy it to a resource group:

az deployment group create \
  --resource-group rg-orders-dev-uks-001 \
  --template-file main.bicep \
  --parameters appName=orders-dev

Use what-if before production deployments. It shows what will be created, changed or deleted:

az deployment group what-if --resource-group rg-orders-prod-uks-001 --template-file main.bicep

§1.2.4Terraform

Terraform with the azurerm and azapi providers is the other common choice, especially in organisations that also run AWS or Google Cloud. The main differences from Bicep:

Bicep Terraform
State None; ARM is the state State file that must be stored securely, usually in a storage account
New Azure features Available immediately azurerm may lag; azapi covers the gap
Multi-cloud Azure only Many providers
Plan and preview what-if terraform plan

Both are good choices. The worst choice is a mix with no rules about which tool owns what.

§1.2.5Azure Verified Modules

Writing every resource from scratch leads to inconsistent security settings. Azure Verified Modules (AVM) are Microsoft-maintained Bicep and Terraform modules for common resources and patterns, with secure defaults, diagnostics settings, private endpoint support and role assignment inputs built in.

module kv 'br/public:avm/res/key-vault/vault:0.9.0' = {
  name: 'keyVault'
  params: {
    name: 'kv-orders-prod-uks-001'
    enablePurgeProtection: true
    publicNetworkAccess: 'Disabled'
  }
}

Pin module versions and upgrade deliberately, just like application dependencies.

§1.2.6Deployment stacks and resource locks

Two tools help protect deployed infrastructure:

  • Deployment stacks manage a set of resources as one unit. They can delete resources that are removed from the template, and they can apply deny settings that block changes made outside the stack, so nobody quietly edits production in the portal.
  • Resource locks (CanNotDelete or ReadOnly) protect critical resources, such as a production database, from accidental deletion. ReadOnly can break things in surprising ways, because some reads are implemented as POST operations. Prefer CanNotDelete unless you have tested it.

§1.2.7What good looks like

  • All production infrastructure defined in Bicep or Terraform and deployed by a pipeline.
  • what-if or plan output reviewed before production changes.
  • Shared modules, ideally AVM, for security-sensitive resources.
  • Portal access in production limited to reading, with break-glass procedures for emergencies.

§1.2.8Red flags

  • Production resources that exist only because someone clicked them into being.
  • Terraform state in a laptop folder, or in a storage account anyone can read.
  • Templates with hard-coded secrets or connection strings.
  • A different template for each environment rather than one template with parameters.

  • Cross-region traffic. An app in one region talking to a database in another.

§2.1.1Identity is the perimeter

Microsoft Entra ID (formerly Azure Active Directory) is Microsoft's cloud identity service. Every sign-in to the Azure portal, Microsoft 365 or an app you build with Entra ID goes through it. Networks still matter, but most modern cloud breaches start with an identity: a stolen password, a phished token, or an over-privileged application.

Entra ID is not the same as on-premises Active Directory Domain Services. It has no organisational units or Group Policy, and it speaks web protocols such as OAuth 2.0, OpenID Connect and SAML rather than Kerberos and LDAP. Many organisations synchronise on-premises accounts into Entra ID with Entra Connect or Entra Cloud Sync.

§2.1.2Tenants

A tenant is a dedicated instance of Entra ID for one organisation. It has:

  • A tenant ID, a GUID you will paste into configuration files constantly.
  • One or more domains, starting with contoso.onmicrosoft.com plus custom domains you verify.
  • Its own users, groups, app registrations and policies.

Most organisations need exactly one workforce tenant. Extra tenants for testing are common, but each one is a security boundary that needs the same care. A forgotten test tenant with no MFA and a privileged app is how Microsoft itself was breached in 2023 and 2024, covered in the scenarios section.

§2.1.3Users, groups and roles

Object Notes
Member user An employee account in your tenant
Guest user An external person invited through B2B collaboration, signing in with their own organisation's identity
Security group Used to grant access to apps and Azure resources
Microsoft 365 group Also creates a shared mailbox, calendar and Teams space
Dynamic group Membership calculated from user attributes, such as department

Grant access to groups, not individuals. When someone changes team, one membership change removes all their old access.

Entra roles, such as Global Administrator, Application Administrator and Cloud Application Administrator, control what someone can do in the directory. They are separate from Azure RBAC roles, such as Owner and Contributor, which control Azure resources. A Global Administrator can elevate themselves to manage all Azure subscriptions, which is one reason that role must be tightly controlled.

§2.1.4Workforce versus customer identity

There are two different jobs:

Scenario Use
Employees and partners signing in to internal apps Your workforce tenant, with B2B guests for partners
Members of the public signing up to your product Microsoft Entra External ID in an external tenant

Entra External ID is Microsoft's current customer identity and access management (CIAM) product. It supports self-service sign-up, social identity providers such as Google and Facebook, email one-time passcodes, and customisable branding.

Azure AD B2C, the previous CIAM product, stopped being sold to new customers on 1 May 2025. Existing B2C customers can continue to use it, with Microsoft committing to support until at least May 2030. New projects should use External ID.

§2.1.5Licensing that changes what you can do

Capability Licence needed
Basic sign-in, users, groups, app registrations Free, included with Azure
Conditional Access, dynamic groups Entra ID P1
Privileged Identity Management, risk-based Conditional Access, access reviews Entra ID P2 or Entra ID Governance
Workload identity protections such as Conditional Access for service principals Workload Identities Premium

The free tier still gets security defaults: enforced MFA registration, blocking legacy authentication and protecting privileged actions. Turn security defaults off only when you replace them with Conditional Access policies.

§2.1.6Sign-in logs and audit logs

Entra ID records every sign-in and every directory change:

  • Sign-in logs show who signed in, from where, to which app, whether MFA was satisfied, and which Conditional Access policies applied. Separate logs exist for service principal and managed identity sign-ins.
  • Audit logs show changes: new app registrations, consent grants, role assignments, credential additions.

Default retention is short: 7 days on the free tier and 30 days with P1 or P2. Send both logs to a Log Analytics workspace or a SIEM on day one. During an incident, the logs you did not keep are the ones you need.

§2.1.7What good looks like

  • One workforce tenant, with any extra tenants inventoried and secured to the same standard.
  • Access granted through groups, with owners who review membership.
  • Few Global Administrators, all with phishing-resistant MFA.
  • Sign-in and audit logs exported to long-term storage.

§2.1.8Red flags

  • Shared admin accounts, or admins using their everyday account for admin work.
  • Test tenants nobody owns.
  • Security defaults disabled with no Conditional Access policies in their place.
  • New customer-facing projects starting on Azure AD B2C.

§2.2.1Two objects, not one

When you register an application in Entra ID, two related objects exist, and most confusion comes from mixing them up.

Application object Service principal
Portal location App registrations Enterprise applications
What it represents The global definition of the app: its identity, redirect URIs, permissions it may request, roles it defines The app's presence in one specific tenant: who can use it, what consent was granted, who is assigned
How many One, in the tenant where the app was registered One per tenant where the app is used
Identifier Application (client) ID, plus an object ID Same client ID, plus its own object ID

A useful analogy: the application object is the class, and each service principal is an instance of it in a tenant. For a single-tenant internal app, there is one of each, created together. For a multi-tenant SaaS app, the application object lives in the vendor's tenant, and every customer tenant that signs in gets its own service principal.

Permissions granted by consent, user assignments and Conditional Access apply to the service principal. That is why an admin who wants to block an app in their tenant disables its enterprise application.

§2.2.2Anatomy of an app registration

Setting What it controls
Application (client) ID The identifier your code sends to Entra ID
Directory (tenant) ID The tenant the app is registered in
Supported account types Single tenant, multi-tenant, or multi-tenant plus personal Microsoft accounts
Platform configurations Web, single-page application, mobile and desktop; each has its own redirect URI rules

Token configuration Optional claims, such as group membership

§2.2.3Public and confidential clients

The OAuth specification splits clients into two kinds:

  • Confidential clients run on a server and can keep a credential secret. A web app backend, an API calling another API, or a background job.
  • Public clients run on a user's device and cannot keep a secret. A browser single-page application, a mobile app, or a desktop app.

Public clients must never be given a client secret, because anything shipped to a browser or device can be extracted. They use the authorisation code flow with PKCE instead, covered in the tokens lesson.

§2.2.4Redirect URIs matter for security

After sign-in, Entra ID sends the result to a redirect URI. If an attacker could register their own URI, they could receive users' tokens. So:

  • Use exact HTTPS URIs in production. http://localhost is allowed for local development.
  • Avoid wildcards. Entra ID restricts them, and they are dangerous where allowed.
  • Remove stale URIs, especially ones pointing at domains you no longer own. A dangling subdomain that someone else can claim becomes a token-stealing endpoint.
  • Keep single-page application URIs under the SPA platform, which enables CORS for the token endpoint and forces PKCE.

§2.2.5Single-tenant or multi-tenant

  • Single tenant. Only accounts in your tenant can sign in. Correct for almost all internal line-of-business apps.
  • Multi-tenant. Accounts from any Entra tenant can sign in. Correct for SaaS products sold to other organisations. Your code must then validate the issuer properly and decide which tenants are allowed. Accepting tokens from any tenant without checking is a common and serious bug.

§2.2.6Credentials: certificates, secrets and federation

Confidential clients prove who they are with one of these, from least to most preferred:

Credential Risk Notes
Client secret High A password. Leaks through config files, logs and screenshots. Maximum lifetime is limited, so it also causes expiry outages
Certificate Medium Private key must be stored securely, ideally in Key Vault
Federated identity credential Low No stored secret. The app trusts tokens from another identity provider, such as GitHub Actions or Kubernetes
Managed identity Lowest For code running in Azure. No app registration credential at all

Where your code runs in Azure, a managed identity usually replaces the need for an app registration credential entirely. Where it runs in GitHub Actions or another cloud, use a federated credential. Keep client secrets as the last resort, and use short lifetimes when you must.

Many organisations enforce this with app management policies, which can block new secrets or limit credential lifetimes tenant-wide.

§2.2.7Ownership and hygiene

Every app registration should have at least two named owners and a documented purpose. Review regularly for:

  • Registrations with no owners or with owners who have left.
  • Credentials about to expire, and credentials that should not exist.
  • High-privilege permissions such as Directory.ReadWrite.All, Mail.ReadWrite or full_access_as_app.
  • Multi-tenant registrations that should be single tenant.
  • Apps with no sign-ins in 90 days.

§2.2.8What good looks like

  • Separate registrations per environment, such as orders-api-dev and orders-api-prod.
  • No client secrets for workloads that run in Azure or GitHub Actions.
  • Exact, current redirect URIs only.
  • Owners, a description and tags on every registration.

§2.2.9Red flags

  • One registration shared by every environment and several unrelated apps.
  • A client secret with a two-year lifetime in a pipeline variable.
  • A multi-tenant app that trusts any tenant's tokens.
  • Legacy test apps holding broad Microsoft Graph or Exchange application permissions.

§2.3.1Two kinds of permission

Every permission an app requests in Entra ID is one of two types. The difference is the most important security concept in app registrations.

Delegated permission (scope) Application permission (app role)
Who is signed in A user No user; the app acts as itself
Effective access The intersection of what the app is allowed and what the user can do Everything the permission allows, across the whole tenant
Token claim scp, space-separated scopes roles, a list of app roles
Typical flow Authorisation code Client credentials
Example Mail.Read delegated lets the app read the signed-in user's mail Mail.Read application lets the app read every mailbox

Application permissions are powerful because there is no user to limit them. They always need admin consent. Treat any app holding broad application permissions, particularly to Microsoft Graph or Exchange, as a privileged identity.

§2.3.2Exposing your own API

When you build an API protected by Entra ID, you register it and define what callers can ask for.

1. Set an Application ID URI. This identifies the API as a resource, usually api://<client-id> or a verified domain URI such as https://api.contoso.com/orders.

2. Add scopes for delegated access. Scopes describe what a signed-in user can let a client do on their behalf:

Scope Admin consent required? Meaning
Orders.Read No Read orders the user can see
Orders.ReadWrite No Create and update orders as the user
Orders.Admin Yes Administrative operations

A client requests them with the full URI, such as api://1f7c.../Orders.Read.

3. Add app roles for application access. App roles with allowed member type Applications are what daemon clients receive through the client credentials flow:

{
  "allowedMemberTypes": ["Application"],
  "displayName": "Orders sync job",
  "value": "Orders.Sync",
  "description": "Allows a background service to synchronise all orders",
  "isEnabled": true
}

App roles with member type Users/Groups are a clean way to do role-based authorisation for people. Assign groups to roles on the enterprise application, and the roles claim appears in their tokens.

§2.3.3Consent

Consent is how a permission actually gets granted to a service principal.

  • User consent. A user agrees to let an app access their own data with low-risk delegated permissions. Most organisations restrict this to verified publishers and low-risk permissions, or disable it and use an admin consent workflow where users request approval.
  • Admin consent. An administrator grants permissions for the whole tenant. Required for all application permissions and for high-risk delegated permissions.

Illicit consent grant attacks trick users into consenting to a malicious multi-tenant app, which then reads their mail or files with valid tokens and no password. Restricting user consent is one of the highest-value settings in Entra ID.

§2.3.4The .default scope

In the client credentials flow, a daemon cannot choose scopes dynamically. It asks for https://graph.microsoft.com/.default or api://orders-api/.default, which means "give me every application permission already granted to me for this resource". The token's roles claim then lists them.

.default is also useful in delegated flows when you want all statically configured permissions at once.

§2.3.5Authorising in your API

Validating the token is not the same as authorising the request. After the token is validated, your API must check the claims:

// ASP.NET Core with Microsoft.Identity.Web
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("ReadOrders", p => p.RequireAssertion(ctx =>
        ctx.User.HasClaim(c => c.Type == "scp" && c.Value.Split(' ').Contains("Orders.Read")) ||
        ctx.User.IsInRole("Orders.Sync")));
});

app.MapGet("/orders", GetOrders).RequireAuthorization("ReadOrders");

The rules:

  • A delegated call must carry the right scope, and then your code must also check that this user may see this data. Scopes are not row-level security.
  • An application call must carry the right app role.
  • Never accept a token just because it is signed by Entra ID. Check the audience is your API, the issuer is the tenant you expect, and the scope or role is present.

§2.3.6Groups in tokens

You can ask Entra ID to include group membership in tokens. It is convenient and has two traps:

  • Overage. If a user is in more than a limit of groups (200 for JWTs), the token contains a pointer to call Microsoft Graph instead of the list. Code that assumes the list is complete will silently deny access.
  • Coupling. Authorisation logic tied to group object IDs is brittle across environments.

App roles assigned to groups usually solve both problems.

§2.3.7What good looks like

  • APIs expose narrow, meaningful scopes and app roles.
  • User consent restricted, with an admin consent workflow.
  • Daemons hold only the app roles they need, on your APIs rather than broad Graph access.
  • API code checks audience, issuer, and scope or role on every request.

§2.3.8Red flags

  • An API that accepts any valid Entra ID token.
  • A reporting job with Directory.ReadWrite.All "because it was easier".
  • Delegated scopes treated as if they replaced data-level authorisation.
  • Users allowed to consent to any app from any publisher.

§2.4.1Two protocols, one sign-in

  • OAuth 2.0 is about authorisation: an app obtains an access token to call an API.
  • OpenID Connect (OIDC) sits on top of OAuth and is about authentication: the app learns who the user is from an ID token.

A typical web app uses both at once. It signs the user in with OIDC and gets an access token to call its API with OAuth.

Entra ID's endpoints for a tenant:

https://login.microsoftonline.com/<tenant-id>/v2.0/.well-known/openid-configuration
https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/authorize
https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token

The discovery document at the first URL lists the others and the signing keys (jwks_uri).

§2.4.2Choosing a flow

App type Flow Notes
Server-rendered web app Authorisation code Confidential client; exchanges the code server-side
Single-page app (React, Angular) Authorisation code with PKCE Public client; no secret; tokens in the browser
Mobile or desktop app Authorisation code with PKCE Uses the system browser or a broker
API calling another API as the user On-behalf-of (OBO) Exchanges the incoming user token for a downstream token
Background job, no user Client credentials Uses a managed identity, certificate or federated credential
Device with no browser, CLI tools Device code User signs in on another device; restrict with Conditional Access

Flows to avoid:

  • Implicit flow. Tokens returned in the URL fragment. Replaced by authorisation code with PKCE.
  • Resource owner password credentials (ROPC). The app collects the user's password directly. Breaks MFA and Conditional Access. Do not use it.

§2.4.3Authorisation code with PKCE, step by step

  1. The app generates a random code verifier and sends its hash, the code challenge, with the sign-in request.
  2. The user signs in at Entra ID, satisfying MFA and Conditional Access.
  3. Entra ID redirects back to the registered redirect URI with a short-lived authorisation code.
  4. The app exchanges the code and the original verifier at the token endpoint.
  5. Entra ID checks the verifier matches the challenge and returns tokens.

PKCE means that an intercepted authorisation code is useless without the verifier, which never left the app.

§2.4.4The tokens

Token Audience Purpose Lifetime
ID token Your client app Tells the app who signed in About an hour
Access token An API Presented as a bearer token to call the API Typically 60–90 minutes, varies
Refresh token Entra ID Obtains new tokens without prompting Much longer; revocable; shorter for SPAs

Access tokens and ID tokens are JSON Web Tokens (JWTs): a header, a payload of claims and a signature. Key claims in an access token for your API:

Claim Meaning Check it?
aud Audience: which API the token is for Yes, must be your API
iss Issuer: which tenant issued it Yes, must be a tenant you trust
exp, nbf Expiry and not-before times Yes
tid Tenant ID Yes, for multi-tenant apps
oid The user or service principal's object ID; stable Use as the user key
sub Subject, unique per app Don't use across apps
scp Delegated scopes Authorise on it
roles App roles Authorise on it
azp or appid The client app that requested the token Check if you only accept certain callers

A token for Microsoft Graph is meant for Graph. Your code should never try to validate or parse Graph access tokens; treat them as opaque.

§2.4.5Validating tokens

Your API must validate every incoming token:

  1. Signature, using Entra ID's published signing keys, which rotate. Fetch and cache them from jwks_uri, never hard-code them.
  2. Issuer, matching your tenant, or an allow-list of tenants for multi-tenant APIs.
  3. Audience, matching your Application ID URI or client ID.
  4. Lifetime, with small clock skew allowance.
  5. Scopes or roles, as covered in the previous lesson.

The Storm-0558 incident in 2023 involved forged tokens that should have been rejected, because a validation path accepted a key from the wrong system. Proper issuer and key validation is not theory. It is the control that stops token forgery.

§2.4.6Use MSAL and the platform libraries

Do not implement these flows by hand. Use the Microsoft Authentication Library (MSAL) for your language, or higher-level wrappers:

Stack Library
ASP.NET Core Microsoft.Identity.Web
Node.js @azure/msal-node
React and SPAs @azure/msal-browser with @azure/msal-react
Python msal, or azure-identity for Azure SDK calls
Java msal4j

MSAL handles caching, refresh, PKCE, clock skew, key rotation and the endless edge cases.

§2.4.7Tokens in browsers

Single-page apps must hold access tokens in the browser, where cross-site scripting can steal them. Two mitigations:

  • Keep token lifetimes short, request narrow scopes, and use strict Content Security Policy.
  • Consider the backend for frontend (BFF) pattern: a small server-side component performs a confidential authorisation code flow, keeps tokens server-side, and gives the browser only an HTTP-only, secure, same-site session cookie.

For internal apps on App Service or Container Apps, built-in authentication (Easy Auth) does a BFF-like job with no code, covered in the hosting module.

§2.4.8What good looks like

  • Authorisation code with PKCE for every interactive client; no implicit flow or ROPC.
  • MSAL or platform libraries handling protocols, with no hand-rolled JWT parsing.
  • APIs validating signature, issuer, audience, lifetime and scope or role.
  • The BFF pattern or built-in authentication for sensitive browser apps.

§2.4.9Red flags

  • Tokens logged in application logs or stored in localStorage for long periods.
  • APIs that decode the JWT and trust it without verifying the signature.
  • A device code flow enabled for everyone with no Conditional Access restrictions.
  • Code that uses sub or email address as a stable user key.

§3.1.1A role assignment has three parts

Azure RBAC answers "who can do what, where". Every role assignment combines:

Part Question Example
Security principal Who? A user, group, service principal or managed identity
Role definition What actions? Storage Blob Data Reader
Scope Where? A management group, subscription, resource group or single resource

Assignments inherit downwards. A role at subscription scope applies to every resource group and resource in it. That is convenient and dangerous. Assign at the narrowest scope that works.

az role assignment create \
  --assignee-object-id <managed-identity-principal-id> \
  --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Reader" \
  --scope /subscriptions/<sub>/resourceGroups/rg-orders-prod/providers/Microsoft.Storage/storageAccounts/storders

§3.1.2The roles you meet first

Role Can do Caution
Owner Everything, including granting access Can hand anyone else any access
Contributor Create and manage resources, but not grant access Can read many secrets indirectly, such as listing storage keys
Reader View resources Cannot see data-plane content in most services
User Access Administrator Manage role assignments only As dangerous as Owner in practice
Role Based Access Control Administrator Manage role assignments, optionally limited by conditions Safer delegation of access management

Contributor looks safe and often is not. A Contributor on a storage account can call listKeys, get the account key, and read all the data, unless shared key access is disabled. The same pattern applies to many services with connection strings or keys.

§3.1.3Control plane versus data plane

Most Azure services now have separate data-plane roles:

Service Control-plane role Data-plane roles
Storage Storage Account Contributor Storage Blob Data Reader / Contributor / Owner, Storage Queue Data Contributor
Key Vault (RBAC mode) Key Vault Contributor Key Vault Secrets User, Key Vault Crypto User, Key Vault Administrator
Cosmos DB DocumentDB Account Contributor Cosmos DB built-in data reader and contributor, assigned with the Cosmos DB data-plane RBAC commands
Service Bus Contributor Azure Service Bus Data Sender / Receiver
Azure SQL SQL Server Contributor Database users mapped to Entra identities, inside SQL itself

Applications need data-plane roles, not Contributor. An API that reads blobs needs Storage Blob Data Reader on that one account or container.

§3.1.4Conditions and deny assignments

  • Role assignment conditions (attribute-based access control) narrow an assignment further. For example, allow blob reads only where a blob index tag project equals orders, or allow a delegated administrator to assign only specific roles to specific principal types.
  • Deny assignments block actions even where a role allows them. You cannot create them directly; they come from features such as deployment stack deny settings and managed applications.

§3.1.5Custom roles

Built-in roles cover most needs. Create a custom role when a built-in one is too broad for a real job, such as operators who can restart web apps but not change their settings:

{
  "Name": "Web App Operator",
  "Description": "Restart and view web apps",
  "Actions": [
    "Microsoft.Web/sites/read",
    "Microsoft.Web/sites/restart/action"
  ],
  "NotActions": [],
  "AssignableScopes": ["/providers/Microsoft.Management/managementGroups/landing-zones"]
}

Avoid wildcards in Actions for custom roles. New actions added to a provider would be granted automatically.

§3.1.6Designing access for a product team

A pattern that holds up:

Group Dev subscription Prod subscription
app-orders-developers Contributor Reader, plus eligible Contributor through PIM
app-orders-operators Contributor Custom operator role
app-orders-readers Reader Reader
Deployment identity for prod none Contributor on the product's resource groups, plus a scoped role-assignment right if templates assign roles
Application managed identities Data-plane roles on specific resources Data-plane roles on specific resources

People get standing access in development and just-in-time access in production through Privileged Identity Management, covered in a later lesson.

§3.1.7Reviewing access

Access grows over time. Build habits that shrink it:

  • Export role assignments per subscription regularly and look for individuals rather than groups, Owner assignments, and assignments at subscription or management group scope.
  • Use access reviews for privileged groups.
  • Remove assignments for deleted principals. They show as "Identity not found".
  • Watch the Activity Log for new Owner or User Access Administrator assignments.
az role assignment list --all --include-inherited \
  --query "[?roleDefinitionName=='Owner'].{who:principalName, scope:scope}" -o table

§3.1.8What good looks like

  • Groups and managed identities in assignments, not individual users.
  • Applications holding data-plane roles on specific resources only.
  • No standing Owner in production for day-to-day users.
  • Custom roles with explicit actions, reviewed like code.

§3.1.9Red flags

  • Contributor on the subscription for an application's identity.
  • Dozens of Owners, including people who have left.
  • "Identity not found" assignments nobody has cleaned up.
  • Shared keys enabled everywhere, making data-plane roles irrelevant.

§3.2.1The problem managed identities solve

Code needs credentials to call Azure services. The traditional answer, a connection string or a client secret in configuration, creates a secret that can leak, expire and be copied. A managed identity is an identity in Entra ID that Azure manages for a resource. The platform issues tokens to the code running on that resource. There is nothing to store, rotate or leak.

Supported on App Service, Functions, Container Apps, AKS workloads, VMs, Logic Apps, Data Factory and many more.

§3.2.2System-assigned or user-assigned

System-assigned User-assigned
Lifecycle Created and deleted with the resource Independent resource you create and delete
Sharing One per resource Can be attached to many resources
Role assignments survive redeploying the app No, a new identity means new assignments Yes
Can exist before the app No Yes, so permissions can be granted in advance
Typical use Simple apps, one identity per resource Apps rebuilt often, slots and revisions, identities needed before first start

A pragmatic default: user-assigned identities for production apps deployed with infrastructure as code. You can create the identity, grant it Key Vault and database roles, and then deploy the app, avoiding a race where the app starts before its permissions exist.

Do not share one user-assigned identity across unrelated apps. That recreates the shared service account problem.

§3.2.3How code gets a token

Inside Azure, the platform exposes a local endpoint that returns tokens for the resource's identity. You should never call it directly. Use the Azure Identity library:

using Azure.Identity;
using Azure.Storage.Blobs;

var credential = new DefaultAzureCredential(new DefaultAzureCredentialOptions
{
    ManagedIdentityClientId = builder.Configuration["AZURE_CLIENT_ID"] // for user-assigned
});

var blobs = new BlobServiceClient(new Uri("https://storders.blob.core.windows.net"), credential);

from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

credential = DefaultAzureCredential()
client = SecretClient(vault_url="https://kv-orders-prod.vault.azure.net", credential=credential)

DefaultAzureCredential tries a chain of sources in order: environment variables, workload identity, managed identity, then developer sign-ins such as the Azure CLI and Visual Studio. The same code works on a laptop, where it uses your az login session, and in Azure, where it uses the managed identity.

Two cautions:

  • In production, the chain can pick up something unexpected, and trying several sources adds latency when the first ones fail. Many teams use ManagedIdentityCredential directly in production and DefaultAzureCredential only in development, or configure the chain explicitly.
  • With a user-assigned identity, set its client ID, or the library may pick the wrong identity or none.

§3.2.4Granting access to the identity

The identity is just a principal. Grant it data-plane roles on exactly what it needs:

resource uami 'Microsoft.ManagedIdentity/userAssignedIdentities@2023-01-31' = {
  name: 'id-orders-api-prod'
  location: location
}

resource kvSecretsUser 'Microsoft.Authorization/roleAssignments@2022-04-01' = {
  name: guid(keyVault.id, uami.id, 'Key Vault Secrets User')
  scope: keyVault
  properties: {
    roleDefinitionId: subscriptionResourceId('Microsoft.Authorization/roleDefinitions', '4633458b-17de-408a-b874-0445c86b69e6')
    principalId: uami.properties.principalId
    principalType: 'ServicePrincipal'
  }
}

Use built-in role definition IDs, which are the same in every tenant. Role assignments can take a few minutes to take effect, so design start-up code to retry.

§3.2.5Workload identity federation

Managed identities only work for code running on Azure resources. For everything else, such as GitHub Actions, Azure DevOps, Kubernetes clusters in other clouds, or Google Cloud workloads, use workload identity federation.

The idea: your workload already has a token from its own identity provider. You configure an app registration or user-assigned managed identity to trust tokens from that issuer with a specific subject. The workload exchanges its token for an Entra ID token. No secret is stored anywhere.

For GitHub Actions deploying to production from the main branch:

az identity federated-credential create \
  --name github-main \
  --identity-name id-orders-deploy-prod \
  --resource-group rg-orders-identities \
  --issuer https://token.actions.githubusercontent.com \
  --subject repo:contoso/orders:environment:production \
  --audiences api://AzureADTokenExchange

The subject is the security control. repo:contoso/orders:environment:production means only jobs in that repository running in the production GitHub environment can get the token. Combine it with GitHub environment protection rules, such as required reviewers, and a pull request from a fork cannot deploy to production.

The delivery module shows the full pipeline.

§3.2.6Where secrets still appear

Some things cannot yet use identities, such as certain third-party APIs or older SDKs. When you must hold a secret:

  • Store it in Key Vault and read it with a managed identity.
  • Give it the shortest workable lifetime and automate rotation.
  • Alert on its expiry date.

§3.2.7What good looks like

  • Every Azure-hosted workload uses a managed identity for Azure services.
  • User-assigned identities for production, granted permissions before the app deploys.
  • Pipelines deploy with federated credentials scoped to repository, branch or environment.
  • No client secrets in pipeline variables or app settings.

§3.2.8Red flags

  • One user-assigned identity shared by every app in the subscription.
  • A federated credential with a subject that matches any branch or pull request.
  • Code that falls back to a connection string "just in case".
  • DefaultAzureCredential in production picking up an environment variable nobody knew was set.

§3.3.1Conditional Access in one sentence

Conditional Access evaluates every sign-in: if these conditions are true, then grant access with these requirements, or block. It needs Entra ID P1.

Part Examples
Assignments: users All users, a group, directory roles, guests, workload identities
Assignments: target resources All cloud apps, Microsoft Azure Management, a specific app
Conditions Sign-in risk, device platform, location, client app type
Grant controls Require MFA, require an authentication strength, require a compliant device, block
Session controls Sign-in frequency, persistent browser session, app-enforced restrictions

§3.3.2A baseline policy set

Most organisations should have at least:

  1. Require MFA for all users, excluding only emergency accounts.
  2. Block legacy authentication, which cannot do MFA.
  3. Require phishing-resistant MFA for administrators, using an authentication strength.
  4. Require MFA for Azure management, targeting the Microsoft Azure Management app.
  5. Require a compliant or hybrid-joined device for sensitive apps, where devices are managed.
  6. Block or require MFA for risky sign-ins, with Entra ID P2.

Always create new policies in report-only mode first, check the impact in the sign-in logs, then enable.

§3.3.3Mandatory MFA for Azure

Microsoft now enforces MFA for Azure resource management, independently of your own policies:

  • Phase 1, from October 2024: the Azure portal, Microsoft Entra admin centre and Intune admin centre.
  • Phase 2, rolling out gradually from 1 October 2025: the Azure CLI, Azure PowerShell, the Azure mobile app, REST APIs, SDKs and infrastructure-as-code tools, for user accounts performing create, update and delete operations. Tenants could postpone Phase 2 until 1 July 2026.

Workload identities are not affected: managed identities and service principals do not do MFA. The practical consequence: any automation still running as a user account with a password will break. Move it to a managed identity or a federated service principal. Recent versions of the Azure CLI and Azure PowerShell handle the MFA prompts correctly.

§3.3.4Phishing-resistant authentication

Not all MFA is equal:

Method Phishing resistance
SMS or voice call Low; vulnerable to SIM swaps and relays
Push approval in Authenticator Medium; number matching helps against fatigue attacks
Time-based codes Low to medium; can be relayed by a proxy phishing site
FIDO2 security keys and passkeys High
Windows Hello for Business High
Certificate-based authentication High

Attackers now routinely use adversary-in-the-middle phishing kits that relay a real sign-in and steal the session cookie, defeating code-based MFA. Require phishing-resistant methods for admins first, then widen.

§3.3.5Privileged Identity Management

Privileged Identity Management (PIM), part of Entra ID P2, removes standing privilege:

  • Users are made eligible for a role rather than permanently assigned.
  • To use it, they activate for a limited time, such as two hours, with a justification.
  • Activation can require MFA, approval, or a ticket number.
  • Every activation is logged and alerts can fire.

PIM covers Entra roles, Azure RBAC roles on any scope, and membership of privileged groups (PIM for Groups). Use it for Global Administrator, Privileged Role Administrator, Application Administrator, and Owner or Contributor on production subscriptions.

§3.3.6Emergency access accounts

Conditional Access mistakes can lock everyone out. Keep two break-glass accounts:

  • Cloud-only accounts on the onmicrosoft.com domain, not synchronised from on-premises.
  • Global Administrator permanently, excluded from most Conditional Access policies.
  • Protected with FIDO2 keys stored securely, rather than no MFA at all, since mandatory MFA applies to them too.
  • Monitored: any sign-in raises an immediate alert.

§3.3.7Protecting workload identities

Service principals can be protected too:

  • Conditional Access for workload identities (Workload Identities Premium) can restrict service principal sign-ins by location or risk.
  • Review app credentials and permissions, as covered in the app registrations lesson.
  • Alert on new credentials added to existing applications. Attackers add their own secret to a privileged app because it survives password resets.

§3.3.8What good looks like

  • A small, documented Conditional Access policy set, all tested in report-only first.
  • Phishing-resistant MFA for every admin.
  • No standing Owner, Global Administrator or Application Administrator assignments for daily users.
  • Two monitored break-glass accounts, tested twice a year.

§3.3.9Red flags

  • Automation running under a named user's account with a password.
  • A "temporary" exclusion group in Conditional Access with 40 people in it.
  • Break-glass accounts that nobody can find the credentials for.
  • No alert when a credential is added to a high-privilege application.

§4.1.1What Key Vault is for

Azure Key Vault stores three kinds of object:

Object Examples Notes
Secrets API keys, third-party passwords, connection strings you cannot yet remove Any string up to 25 KB; versioned
Keys RSA and elliptic-curve keys for encryption and signing Private key never leaves the vault; operations happen inside it
Certificates TLS certificates Key Vault can generate, renew with supported CAs, and alert on expiry

There are two tiers: Standard (software-protected keys) and Premium (adds HSM-protected keys). Managed HSM is a separate, single-tenant service for organisations needing FIPS 140-3 Level 3 validated HSMs and full control of the security domain.

§4.1.2One vault per application per environment

A good default: one vault per application, per environment, such as kv-orders-prod-uks.

  • Blast radius stays small; a compromised app reads only its own secrets.
  • Permissions are simple, because the app's identity gets a role on its own vault.
  • Throttling limits apply per vault, so one noisy app does not slow others.

Avoid one giant shared vault for everything.

§4.1.3Permission model: Azure RBAC

Key Vault has two access models:

  • Vault access policies, the original model, defined on the vault itself.
  • Azure RBAC, using roles like Key Vault Secrets User, assignable at vault or individual secret scope.

Use Azure RBAC. It is consistent with the rest of Azure, works with PIM and conditions, and separates who manages the vault from who reads secrets. With Key Vault control-plane API version 2026-02-01 and later, Azure RBAC is the default for newly created vaults. Older control-plane API versions retire on 27 February 2027, so update Bicep, Terraform and SDK code before then. Existing vaults keep their current model until you switch them.

A critical subtlety of access policies: anyone with Contributor on the vault can edit access policies and grant themselves secret access. Under RBAC, only roles that can write role assignments can do that.

Role Use for
Key Vault Secrets User Applications reading secrets
Key Vault Secrets Officer Pipelines or people managing secrets
Key Vault Certificate User Reading certificates, such as App Service importing a TLS cert
Key Vault Crypto User Apps performing encrypt, decrypt, sign or verify operations
Key Vault Administrator Break-glass and platform admins only

§4.1.4Soft delete and purge protection

  • Soft delete is always on. Deleted vaults and objects are recoverable for 7 to 90 days, 90 by default.
  • Purge protection prevents anyone, including admins, from permanently deleting a soft-deleted vault or object before the retention period ends.

Enable purge protection for production. It is required when Key Vault keys protect other services through customer-managed keys, and it defends against an attacker or mistaken script destroying keys. It cannot be disabled once enabled, so vault names stay reserved during retention. Plan naming for environments you tear down often.

§4.1.5Networking

A production vault should not accept connections from the whole internet:

  • Set public network access to disabled and use a private endpoint in the app's virtual network, with the privatelink.vaultcore.azure.net private DNS zone.
  • Or, for simpler setups, use the vault firewall to allow selected networks, plus the trusted Microsoft services exception where platform services need access.

Remember that deployment pipelines need to reach the vault too, if they write secrets.

§4.1.6Reading secrets well

  • Read secrets at start-up and cache them, rather than on every request. Key Vault throttles high request rates per vault.
  • Where the platform supports it, use Key Vault references so the app never calls Key Vault itself (next lesson).
  • Reference secrets without a version to get the latest, and design for rotation by reloading periodically.
builder.Configuration.AddAzureKeyVault(
    new Uri("https://kv-orders-prod-uks.vault.azure.net/"),
    new ManagedIdentityCredential(builder.Configuration["AZURE_CLIENT_ID"]));

§4.1.7Rotation and expiry

Secrets that never change are secrets that leak eventually. For each secret, decide:

  1. Who rotates it, a person, a pipeline, or an Azure Function triggered by Key Vault's SecretNearExpiry event through Event Grid.
  2. How consumers pick up the new value without an outage, usually by holding two valid credentials during the switch.
  3. Its expiry date, set on the secret so alerts can fire.

Certificates issued through Key Vault with an integrated CA can renew automatically. App Service and Front Door can then pick up the renewed certificate.

§4.1.8Logging

Enable diagnostic settings to send AuditEvent logs to Log Analytics. Every secret read is then recorded with the caller's identity. Useful alerts:

  • Secret reads by an identity that does not normally read them.
  • Spikes in Forbidden responses, which suggest probing.
  • Purge or delete operations in production.

§4.1.9What good looks like

  • One vault per app per environment, Azure RBAC, purge protection on.
  • Private endpoints for production, public access disabled.
  • Every secret has an owner, an expiry date and a rotation method.
  • Audit logs flowing to Log Analytics with a few meaningful alerts.

§4.1.10Red flags

  • A shared vault with hundreds of secrets and Contributor for every developer.
  • Secrets with no expiry that were created five years ago.
  • Access policies granting all permissions to a pipeline identity.
  • Templates pinned to Key Vault control-plane API versions that retire in February 2027.

§4.2.1Configuration versus secrets versus code

Keep three things apart:

Kind Examples Where it belongs
Code Business logic The container image or deployment package, identical in every environment
Configuration API base URLs, feature flags, log levels, timeouts App settings or App Configuration, varying per environment
Secrets Third-party API keys Key Vault, referenced rather than copied

The same build artefact should move from dev to test to production with only configuration changing. If you rebuild per environment, you are not testing what you ship.

§4.2.2App settings on App Service and Functions

App settings are exposed to your app as environment variables. Connection strings are a separate section with a type prefix, mostly kept for .NET compatibility. Both are encrypted at rest by the platform, but anyone with sufficient Azure access can read them in the portal or with az webapp config appsettings list. They are not a secret store.

Mark settings that should not move with a deployment slot swap as deployment slot settings, for example an environment name or a slot-specific database.

§4.2.3Key Vault references

A Key Vault reference is an app setting whose value points at a secret:

@Microsoft.KeyVault(SecretUri=https://kv-orders-prod-uks.vault.azure.net/secrets/PaymentsApiKey/)

or

@Microsoft.KeyVault(VaultName=kv-orders-prod-uks;SecretName=PaymentsApiKey)

The platform resolves it using the app's managed identity, and your code just reads an environment variable. Points to know:

  • The identity used defaults to the system-assigned identity. For a user-assigned identity, set the site's keyVaultReferenceIdentity property.
  • Omit the version to follow the latest version. The platform refreshes references periodically (currently within 24 hours), and any configuration change or restart forces a refresh.
  • If the vault uses a private endpoint, the app needs VNet integration and DNS resolution for the private endpoint, or the reference fails.
  • The portal shows a green tick or a red error per reference. Check it after every deployment.

§4.2.4Container Apps secrets

Azure Container Apps has its own secrets at the app level, which can hold a value or reference Key Vault:

az containerapp secret set \
  --name ca-orders-api --resource-group rg-orders-prod \
  --secrets payments-key=keyvaultref:https://kv-orders-prod-uks.vault.azure.net/secrets/PaymentsApiKey,identityref:/subscriptions/<sub>/resourceGroups/rg-orders-identities/providers/Microsoft.ManagedIdentity/userAssignedIdentities/id-orders-api-prod

Environment variables then reference the secret with secretref:payments-key. Container Apps refreshes Key Vault-backed secrets periodically; new revisions pick up changes.

§4.2.5Azure App Configuration

Azure App Configuration is a central store for settings and feature flags, shared across many apps and services. It is worth it when:

  • Several services share configuration and you want one place to change it.
  • You need dynamic refresh without restarting apps.
  • You want feature flags with targeting, such as enabling a feature for 10% of users or one customer.
  • You want labelled values per environment and snapshots for releases.

It integrates with Key Vault: a configuration value can be a Key Vault reference that the client library resolves with the app's identity.

builder.Configuration.AddAzureAppConfiguration(options =>
{
    var credential = new ManagedIdentityCredential(builder.Configuration["AZURE_CLIENT_ID"]);
    options.Connect(new Uri("https://appcs-orders-prod.azconfig.io"), credential)
           .Select("Orders:*", labelFilter: "prod")
           .ConfigureKeyVault(kv => kv.SetCredential(credential))
           .UseFeatureFlags();
});

Connect with Entra ID, as above, and disable access keys on the store. For a single small app, plain app settings are simpler and fine.

§4.2.6Feature flags as a release tool

Feature flags separate deploying code from releasing a feature:

  1. Deploy the new code with the flag off.
  2. Turn it on for internal users.
  3. Widen gradually, watching errors and metrics.
  4. Remove the flag and the old code path once stable.

Step 4 is the one teams skip. Old flags become permanent branching logic nobody understands.

§4.2.7What good looks like

  • One build artefact promoted through environments.
  • No secret values typed into app settings; Key Vault references or identities instead.
  • Key Vault reference status checked after deployments.
  • Feature flags with owners and removal dates.

§4.2.8Red flags

  • Production connection strings with passwords visible in the portal's app settings blade.

§4.3.2Storage without keys

§4.3.3Azure SQL with Entra ID only

  1. Set an Entra group as the Entra admin of the logical server.
  2. Enable Microsoft Entra-only authentication, which disables SQL logins.
  3. Create a contained database user for the app's managed identity and grant it only what it needs:
CREATE USER [id-orders-api-prod] FROM EXTERNAL PROVIDER;
ALTER ROLE db_datareader ADD MEMBER [id-orders-api-prod];
ALTER ROLE db_datawriter ADD MEMBER [id-orders-api-prod];
  1. Connect with no password:
Server=tcp:sql-orders-prod.database.windows.net,1433;Database=orders;Authentication=Active Directory Managed Identity;User Id=<uami-client-id>;Encrypt=True;

Grant schema-level or object-level permissions rather than db_owner. Run migrations with a separate, more privileged identity from the pipeline, not with the runtime app identity.

§4.3.4PostgreSQL with Entra ID

Azure Database for PostgreSQL flexible server supports Entra ID. The app requests a token for the https://ossrdbms-aad.database.windows.net/.default scope and uses it as the password. Tokens expire, so use a connection pool or driver integration that refreshes them. Libraries such as the Azure Identity extensions for common Postgres drivers handle this for you.

§4.3.5Enforcing it with policy

Deploy Azure Policy definitions that deny or audit:

  • Storage accounts with shared key access enabled.
  • Cosmos DB accounts with local authentication enabled.
  • SQL servers without Entra-only authentication.
  • Service Bus and Event Hubs namespaces with local auth enabled.
  • Azure AI services with local authentication enabled.

Run them in Audit first, because you will find surprises.

§4.3.6Where secrets remain

Some secrets are unavoidable today:

  • Third-party SaaS API keys. Store in Key Vault; rotate; restrict by IP at the provider if possible.
  • Webhook signing secrets. Same treatment.
  • Certificates for mutual TLS with partners. Key Vault certificates with auto-renewal.
  • Legacy components that do not support Entra ID. Record them as tracked exceptions with an owner and a plan.

§4.3.7The payoff

A secretless app means:

  • Nothing to leak in a Git commit, a log line or a screenshot.
  • No expiry outages from forgotten secrets.
  • Access that can be revoked instantly by removing a role assignment.
  • Every data access attributable to a specific identity in the logs.

§4.3.8What good looks like

  • Local authentication disabled on storage, Cosmos DB, messaging and AI services in production.
  • Entra-only authentication on Azure SQL; the app identity with least-privilege database roles.
  • A short, owned list of remaining secrets, all in Key Vault with expiry dates.
  • Policies that stop new resources reintroducing keys.

§4.3.9Red flags

  • AccountKey= visible anywhere in a repository.
  • The app connecting to SQL as the server admin.

§5.2.1Plans and apps

An App Service plan is a set of virtual machines of a given size and count. Apps run on a plan. Every app on a plan runs on every instance of the plan and shares its CPU and memory.

  • Scale up by changing the plan's tier or size.
  • Scale out by changing the number of instances.
  • Put apps together on one plan when they have similar scaling needs and lifecycles. Separate noisy or critical apps.

§5.2.2Tiers

Tier Use for Notes

Premium v3 and Premium v4 Most production Faster hardware, more memory options, zone redundancy, more slots

Enable zone redundancy on production plans in regions that support it. It requires at least two instances, and three is the usual minimum recommendation.

§5.2.3Deployment slots

A slot is a live copy of the app with its own hostname, such as app-orders-prod-staging.azurewebsites.net. The standard release pattern:

  1. Deploy to the staging slot.
  2. The slot warms up; run smoke tests against it.
  3. Swap staging into production. App Service warms the instances before routing traffic, so there is no cold start for users.
  4. If something breaks, swap back.

Settings marked deployment slot setting stay with the slot rather than moving in the swap. Use them for anything environment-specific.

Configure warm-up with applicationInitialization or the WEBSITE_SWAP_WARMUP_PING_PATH setting so the swap waits for a health endpoint rather than just the root URL.

§5.2.4Built-in authentication (Easy Auth)

App Service built-in authentication handles sign-in in front of your app, without code:

  • Configure an identity provider, usually Microsoft Entra ID.
  • Choose what happens to unauthenticated requests: redirect to sign-in, return 401, or allow and let the app decide.
  • The platform manages the OIDC flow, stores tokens server-side in a token store, and passes identity headers such as X-MS-CLIENT-PRINCIPAL to your app.

It is excellent for internal apps: a React front end and API on App Service can be protected with Entra ID in minutes, with tokens never exposed to browser JavaScript. Limits to know:

  • The headers are only trustworthy if every request passes through Easy Auth. Do not expose the app another way.
  • Fine-grained authorisation still belongs in your code, using the roles claim.
  • For APIs called by other apps, validate tokens in the app too if you need detailed claim checks.

The same feature exists in Azure Functions and Azure Container Apps.

§5.2.5Scaling

  • Manual instance counts for predictable load.
  • Rules-based autoscale on CPU, memory, HTTP queue length or a schedule.
  • Automatic scaling, where the platform scales based on HTTP traffic with pre-warmed instances, for Premium plans.

Scale-out must be backed by a stateless app: no in-memory sessions, no files written to local disk that other instances need. Turn off ARR affinity (sticky sessions) unless you truly depend on it.

§5.2.6Networking

  • Inbound private access: a private endpoint gives the app a private IP in your virtual network and can disable public access.
  • Outbound to private resources: VNet integration lets the app reach private endpoints, databases and on-premises networks through your virtual network.

§5.3.3Cold starts

When no instance is running, the first request waits for one to start. Mitigations:

  • Always-ready instances on Flex Consumption, or pre-warmed instances on Premium.
  • Smaller deployment packages and fewer heavy dependencies loaded at start-up.
  • Lazy initialisation of clients, reused across invocations rather than created per call.
  • Put latency-sensitive user-facing APIs on App Service or Container Apps if cold starts are unacceptable.

§5.3.4Identity-based connections

Functions need a storage account (AzureWebJobsStorage) and connections for triggers. Use identity-based connections instead of connection strings:

AzureWebJobsStorage__accountName = stfuncordersprod
ServiceBusConnection__fullyQualifiedNamespace = sb-orders-prod.servicebus.windows.net
ServiceBusConnection__credential = managedidentity
ServiceBusConnection__clientId = <uami-client-id>

Grant the identity the right data roles: Storage Blob Data Owner, Storage Queue Data Contributor and Storage Table Data Contributor on the host storage account depending on features used, and Azure Service Bus Data Receiver on the namespace.

§5.3.5Design rules

  1. Keep functions short. Timeouts vary by plan. Long work belongs in Durable Functions, a queue with chunked processing, or a Container Apps job.
  2. Make them idempotent. Triggers deliver at least once. A retried message must not charge a customer twice. Use natural keys, upserts or a processed-message table.
  3. Handle poison messages. Service Bus and Storage queues move messages to a dead-letter or poison queue after repeated failures. Monitor and alert on them.
  4. Don't hold state in memory. Instances come and go.
  5. Reuse clients. Create HTTP, SDK and database clients once per instance, not per invocation, or you will exhaust sockets.
  6. Control concurrency. Set maxConcurrentCalls or batch sizes so a burst of messages does not overwhelm a downstream database.

§5.3.6Durable Functions

Durable Functions add stateful workflows in code:

Pattern Example
Function chaining Validate order, then reserve stock, then charge card
Fan-out and fan-in Process 1,000 files in parallel and aggregate results
Async HTTP API Start a long job, poll a status endpoint
Human interaction Wait up to three days for an approval event
Aggregator (entities) Maintain a running total per device

Orchestrator code must be deterministic, because it replays from history. No DateTime.Now, random numbers or direct I/O in the orchestrator; do those in activities. Choose a storage provider carefully: the default Azure Storage provider, or the Durable Task Scheduler managed backend for higher throughput and better observability.

§5.3.7Security

  • Use AuthorizationLevel.Anonymous plus built-in authentication or API Management for real user or app authentication. Function keys are shared secrets suitable only for simple service-to-service calls.
  • Disable basic auth publishing credentials and FTP.
  • Put function apps processing sensitive data on plans with VNet integration.

§5.3.8What good looks like

  • Flex Consumption for new serverless apps, with identity-based connections.
  • Idempotent functions with dead-letter monitoring.
  • Durable Functions or jobs for anything long-running.
  • Application Insights with sampling and alerts on failure rates.

§5.3.9Red flags

  • Function keys shared by email as the API's only protection.
  • A new HttpClient created in every invocation.
  • Functions calling each other over HTTP in long synchronous chains.
  • Timer-triggered jobs that assume they run exactly once.

§5.4.2Environments and workload profiles

§5.4.3Revisions and traffic splitting

Container Apps runs in single revision mode by default: a new revision replaces the old one once healthy. Multiple revision mode lets you run several and split traffic:

  --name ca-orders-api --resource-group rg-orders-prod \
  --revision-weight ca-orders-api--v42=90 ca-orders-api--v43=10

That gives canary releases: send 10% of traffic to the new revision, watch errors, then move to 100%. Revision labels give a stable URL to a specific revision for testing before it gets any traffic.

Define health probes: startup, readiness and liveness. Without a readiness probe, traffic can reach a replica before it is ready.

§6.1.1Virtual networks and subnets

A virtual network (VNet) is a private network in one region, defined by one or more address ranges such as 10.20.0.0/16. It is divided into subnets. Resources that live in a network, such as VMs, private endpoints, App Service VNet integration, Container Apps environments and Azure Firewall, each take addresses from a subnet.

Key rules:

  • Azure reserves five addresses in every subnet.
  • Many services need a dedicated subnet, sometimes delegated to that service. App Service VNet integration, Container Apps environments, API Management and Application Gateway all have their own subnet requirements.
  • Address ranges must not overlap with other VNets you peer with or with on-premises networks you connect to. Overlaps are extremely painful to fix.

§6.1.2Planning address space

Plan with your network team before building, not after:

Subnet Example range Purpose

Allocate generously. Addresses in a private range are free; recreating a subnet because it is full is not.

§6.1.3Network security groups

A network security group (NSG) is a stateful set of allow and deny rules on source, destination, port and protocol, applied to subnets or network interfaces. Rules are processed by priority, lowest number first.

Useful features:

  • Service tags, such as AzureFrontDoor.Backend, Storage.UKSouth or AzureMonitor, stand in for Microsoft's changing IP ranges.
  • Application security groups let you write rules like "web tier to data tier" instead of IP lists.
  • NSG flow logs or the newer VNet flow logs record traffic for troubleshooting and investigation.

NSG rules on a private endpoint subnet are only enforced if network policies for private endpoints are enabled on that subnet.

§6.1.4Hub and spoke

Most organisations connect many application networks through a central hub:

Component Lives in
Azure Firewall or a third-party network appliance Hub
VPN or ExpressRoute gateway to on-premises Hub
Private DNS zones and DNS resolver Hub or a shared connectivity subscription
Application workloads Spoke VNets, one per application or environment

Spokes peer with the hub. Traffic between spokes and to the internet is routed through the firewall with user-defined routes (UDRs). Azure Virtual WAN provides a Microsoft-managed version of the hub for larger estates.

§6.1.5Outbound traffic: default outbound access is ending

Historically, a VM with no public IP could still reach the internet through an implicit, Microsoft-owned address, called default outbound access. That is being retired:

  • New virtual networks default to private subnets, with no implicit outbound internet access. This shipped through API versioning: VNets created with API versions released after 31 March 2026 (starting with 2025-07-01), and VNets created in the portal from 1 April 2026.
  • Existing VNets are unchanged, and new VMs in existing subnets keep default outbound access until those subnets are made private.

Resources in private subnets need an explicit outbound method:

Method Use
NAT gateway Simple, scalable outbound with static public IPs; ideal for allow-listing at partners
Azure Firewall or a network appliance with UDRs Central inspection and FQDN filtering
Standard Load Balancer outbound rules Where a load balancer is already in use
Public IP on the resource Rarely the right answer for app workloads

Platform services like App Service and Functions have their own outbound paths, but when you route their traffic through VNet integration with route all enabled, the same rules apply: provide a NAT gateway or firewall route.

§6.1.6Static outbound IPs

Third parties often ask for your outbound IP addresses to allow-list:

  • App Service without VNet integration uses a set of shared outbound IPs for the scale unit that can change when you change tier.
  • With VNet integration and route all through a NAT gateway, outbound traffic uses the NAT gateway's static public IPs, which you control.

§6.1.7What good looks like

  • An IP address plan agreed with the network team, with no overlaps.
  • Dedicated, generously sized subnets for services that need them.
  • Explicit outbound through a NAT gateway or firewall, with known public IPs.
  • Flow logs enabled for production networks.

§6.1.8Red flags

  • 10.0.0.0/16 used by every team's VNet because it was the default.
  • An NSG rule allowing Any inbound on port 3389 or 22 from the internet.
  • Outbound connectivity that works only because of default outbound access in an old subnet.
  • A subnet so small that the next scale-out fails.

§6.2.1Three features that sound alike

Feature Direction What it does
Private endpoint Inbound to a service Gives a PaaS resource a private IP in your subnet. Traffic stays on Microsoft's network; public access can be disabled
Service endpoint Outbound from a subnet Lets a subnet reach a service's public endpoint with the subnet's identity, so the service firewall can allow that subnet
VNet integration (App Service, Functions) Outbound from an app Lets the app send traffic into your VNet, to reach private endpoints and private resources

A private web app that reads a private database uses two of them: VNet integration on the app for outbound, and a private endpoint on the database for inbound.

§6.2.2Private endpoints in detail

A private endpoint is a network interface in your subnet connected to one specific resource and sub-resource, such as blob on a storage account or sqlServer on a SQL server.

  • The resource can then have public network access disabled entirely.
  • It is per resource. A storage account used for blobs and queues needs an endpoint for each sub-resource used.
  • It costs a small hourly charge plus data processed.
  • Access still needs authentication. A private IP is not a permission.

Service endpoints are simpler and free but keep the service's public endpoint in use and do not work from on-premises. Prefer private endpoints for production data services.

§6.2.3DNS is where it breaks

Applications connect to names like sql-orders-prod.database.windows.net, not IP addresses. After you add a private endpoint, that name must resolve to the private IP from inside your network, and to the public address (or nothing useful) from outside.

Azure does this with a CNAME chain:

sql-orders-prod.database.windows.net
  CNAME sql-orders-prod.privatelink.database.windows.net
  -> 10.20.4.5 (from your private DNS zone), or the public IP if the zone isn't linked

You make the private answer work by:

  1. Creating a private DNS zone with the right name, such as privatelink.database.windows.net.
  2. Linking that zone to the VNets that must resolve it.
  3. Having the private endpoint register its A record in the zone, through a DNS zone group.

Common zone names:

Service Private DNS zone
Blob storage privatelink.blob.core.windows.net
Azure SQL privatelink.database.windows.net
PostgreSQL flexible server privatelink.postgres.database.azure.com
Key Vault privatelink.vaultcore.azure.net
Cosmos DB (NoSQL) privatelink.documents.azure.com
App Service and Functions privatelink.azurewebsites.net
Container Registry privatelink.azurecr.io
Service Bus privatelink.servicebus.windows.net

§6.2.4DNS in hub and spoke

In a real estate, create one private DNS zone per service type, centrally in the connectivity subscription, and link it to the hub and spoke VNets. Do not let every application create its own copy of privatelink.blob.core.windows.net. Multiple zones with the same name cause unpredictable resolution depending on which one a VNet is linked to.

A common enterprise pattern uses Azure Policy with DeployIfNotExists to automatically attach new private endpoints to the central zones.

For on-premises clients to resolve private endpoints, forward the public zones such as database.windows.net from on-premises DNS to an Azure DNS Private Resolver inbound endpoint in the hub, which answers from the linked private zones.

§6.2.5A working private web app pattern

Component Configuration
App Service or Container Apps VNet integration into snet-app; public inbound restricted to Front Door
Key Vault Private endpoint in snet-private-endpoints; public access disabled
Azure SQL Private endpoint; public access disabled; Entra-only authentication
Storage Private endpoints for blob and queue; shared keys disabled
Private DNS zones Central zones linked to the spoke VNet
App configuration WEBSITE_VNET_ROUTE_ALL=1 or the vnetRouteAllEnabled site property, so all outbound goes through the VNet

§6.2.6Troubleshooting

When the app cannot reach a private resource, check in this order:

  1. DNS. From inside the app, resolve the name. App Service has a console and the Kudu tools:

    nslookup sql-orders-prod.database.windows.net

    A public IP answer means the private DNS zone is missing, not linked, or the record is absent.

  2. Routing. Is outbound traffic going through the VNet? Is route all enabled?

  3. NSGs and firewall. Is the port allowed from the integration subnet to the endpoint subnet?

  4. The resource firewall. Is public access disabled while the connection still resolves publicly?

  5. Authentication. Once connected, is the identity allowed?

Nine times out of ten it is step 1.

§6.2.7Pipelines and private resources

Once public access is disabled, a GitHub-hosted runner cannot deploy database migrations or write Key Vault secrets. Options: self-hosted runners inside the network, Azure DevOps managed pools or GitHub-hosted runners with Azure private networking, or deployment steps that run inside Azure, such as a Container Apps job.

§6.2.8What good looks like

  • Private endpoints for production data services with public access disabled.
  • Central private DNS zones, linked by policy, with no duplicates.
  • Route all enabled for apps that must reach private resources.
  • A tested plan for how pipelines reach private resources.

§6.2.9Red flags

  • A private endpoint created, public access disabled, and the app now failing with timeouts.
  • Several copies of the same privatelink zone in different resource groups.
  • Private endpoints but NSG rules allowing everything anyway.
  • "Temporarily" enabling public access to run a migration and never turning it off.

§6.3.2Azure Front Door

Front Door is the default front door for internet-facing web apps:

  • Users connect to the nearest Microsoft edge location, which improves latency and absorbs volumetric attacks.
  • It routes to origins, such as App Service apps, Container Apps, storage static websites or Application Gateway, with health probes and failover across regions.
  • Premium adds managed WAF rule sets, bot protection and Private Link origins, so Front Door reaches your app over a private endpoint and the app needs no public access at all.

§6.3.3Locking the origin

A WAF in front of an app is useless if attackers can go straight to app-orders-prod.azurewebsites.net. Lock origins down:

Approach How
Private Link origin (Front Door Premium) App public access disabled; Front Door connects through a private endpoint you approve
Access restrictions with service tag and header check Allow only the AzureFrontDoor.Backend service tag and require the X-Azure-FDID header to equal your Front Door profile ID
Application Gateway in the VNet Origin reachable only from the gateway subnet

Checking only the service tag is not enough, because every Front Door customer shares it. The header check ties traffic to your profile.

§6.3.4Application Gateway v2

Use Application Gateway when you need a regional, VNet-native layer 7 load balancer:

  • Internal apps reached from on-premises over private addresses.
  • Workloads in a VNet where traffic must stay regional.
  • Front Door plus Application Gateway for defence in depth in regulated estates.

Application Gateway v1 retired on 28 April 2026. Any remaining v1 gateways are unsupported and should already be on v2.

§6.3.5WAF policies

A WAF policy combines:

  • Managed rule sets, the default rule set based on OWASP Core Rule Set patterns for SQL injection, cross-site scripting and similar.
  • Bot manager rules.
  • Custom rules, such as geo-filtering, rate limits per client IP, or blocking specific paths.

Roll out in Detection mode first, review logs for false positives, add targeted exclusions, then switch to Prevention. A WAF permanently in detection mode is a logging service.

§6.3.6API Management

APIM is an API gateway and management layer. It earns its place when you:

  • Publish APIs to many consumers, internal or external, with subscriptions, quotas and a developer portal.
  • Need consistent policies across many backend services: JWT validation, rate limiting, caching, header manipulation, request transformation.
  • Want versioning and revisions of APIs independently of backend deployments.
  • Front AI model endpoints with token limits, load balancing and usage tracking.

A typical inbound policy validating Entra ID tokens:

<inbound>
  <validate-azure-ad-token tenant-id="{{tenant-id}}">
    <audiences>
      <audience>api://orders-api</audience>
    </audiences>
    <required-claims>
      <claim name="roles" match="any">
        <value>Orders.Read</value>
      </claim>
    </required-claims>
  </validate-azure-ad-token>
  <rate-limit-by-key calls="100" renewal-period="60" counter-key="@(context.Request.IpAddress)" />
  <base />
</inbound>

APIM should authenticate to backends with its managed identity, and backends should still validate tokens rather than trusting that APIM did.

Tier choice matters for networking: the v2 tiers offer VNet integration and private endpoints with faster deployment; the classic Developer and Premium tiers support full VNet injection. Check current tier capabilities before designing.

Internal line-of-business app Private endpoint or internal Container Apps environment, reached over VPN or ExpressRoute; optionally Application Gateway

§6.3.8What good looks like

  • Every internet-facing app behind Front Door or Application Gateway with WAF in Prevention mode.

  • No Front Door classic profiles left, and no Application Gateway v1.

§6.3.9Red flags

  • WAF in Detection mode for a year.
  • Origin still publicly reachable, bypassing the WAF.
  • APIM subscription keys as the only authentication for sensitive APIs.
  • A CDN caching authenticated responses because cache rules ignored the Authorization header.

§7.2.4Connection management

Cloud databases have connection limits, and apps that open too many connections fail in confusing ways.

  • Use the built-in connection pool in your driver, and reuse it across requests.
  • For PostgreSQL, enable the built-in PgBouncer on flexible server for many short-lived connections, especially from serverless compute that scales out.
  • Size pools per instance with scale-out in mind: 20 instances with a pool of 50 each is 1,000 connections.
  • Implement retries with backoff for transient errors. Failovers, scaling and maintenance briefly drop connections. .NET's SqlClient and Entity Framework have retry strategies built in.
services.AddDbContext<OrdersDb>(options =>
    options.UseSqlServer(connectionString, sql =>
        sql.EnableRetryOnFailure(maxRetryCount: 5, maxRetryDelay: TimeSpan.FromSeconds(10), errorNumbersToAdd: null)));

  • Keep migrations in source control with the app: Entity Framework migrations, Flyway, Liquibase, sqitch or DbUp.

  • Make changes backward compatible across one release so slot swaps and rollbacks work: add columns before using them, remove columns a release after code stops using them.
  • Never let the runtime app identity hold db_owner just so it can migrate on start-up.

§7.3.1The model

Cosmos DB for NoSQL stores JSON items in containers inside databases in an account. Every item has an id and belongs to a logical partition defined by the value of the container's partition key, such as /customerId.

  • A point read by id plus partition key is the cheapest, fastest operation in Cosmos DB.
  • Queries within one partition are efficient.
  • Cross-partition queries fan out to many physical partitions and cost more.
  • A single logical partition is limited to 20 GB.

§7.3.2Choosing the partition key

The partition key cannot be changed without copying data to a new container. Choose it for:

  1. High cardinality: many distinct values, so data and load spread out.
  2. Common filter: most queries include it, so they stay in one partition.
  3. Even distribution: no single value dominates writes or storage.
Scenario Partition key Why
Shopping carts /userId Every cart operation is for one user
Multi-tenant SaaS /tenantId Queries are per tenant; very large tenants may need hierarchical keys
IoT telemetry /deviceId, or hierarchical /deviceId then /day Spreads writes; keeps device queries local
Orders /customerId Customers look at their own orders

Hierarchical partition keys (up to three levels) solve the large-tenant problem: partition by /tenantId then /userId, and queries by tenant remain efficient while large tenants spread across physical partitions.

Bad keys: a boolean, a status field, or a date that concentrates today's writes in one partition.

§7.3.3Model for access patterns

Relational habits hurt in Cosmos DB. Design documents around how the app reads:

  • Embed data read together and bounded in size, such as an order with its line items.
  • Reference data that grows without bound or changes independently.
  • Denormalise deliberately, and use the change feed to update copies.
  • Keep item size small. Large items cost more request units to read and write.

§7.3.4Request units and capacity modes

All operations cost request units (RUs). A 1 KB point read costs 1 RU; queries and writes cost more depending on size, indexing and complexity. Every response includes the RU charge, which you should log while designing.

Mode Billing Best for
Provisioned, standard RU/s reserved per container or database Steady traffic
Provisioned, autoscale Scales between 10% and 100% of a maximum; billed per hour at the highest level reached Variable traffic with known peaks
Serverless Per RU consumed Dev, test and low, bursty traffic

When a request exceeds provisioned throughput, Cosmos DB returns 429 Too Many Requests with a retry-after hint. The SDKs retry automatically. Frequent 429s mean under-provisioning, a hot partition or inefficient queries.

§7.3.5Consistency levels

Cosmos DB offers five levels, from strongest to weakest:

Level Guarantee Notes
Strong Reads see the latest committed write Higher latency; limits on multi-region writes
Bounded staleness Reads lag by at most K versions or T time Predictable staleness
Session Within a client session, reads see their own writes The default and right for most apps
Consistent prefix Reads never see out-of-order writes
Eventual Replicas converge eventually Lowest latency and cost

§7.3.6Indexing

By default every property is indexed. For write-heavy containers, customise the indexing policy to exclude paths you never filter on, which reduces write RU costs. Add composite indexes for queries that filter and sort on multiple properties. Vector indexes support similarity search for AI workloads.

§7.3.7Change feed

The change feed is an ordered log of inserts and updates per partition. Use it to:

  • Update materialised views and denormalised copies.
  • Stream changes to search indexes, caches or analytics.
  • Trigger Azure Functions.

The default mode does not capture deletes; use soft deletes with a TTL, or the all-versions-and-deletes mode where available.

§7.3.8Global distribution

Add regions to an account for low-latency reads and availability. Multi-region writes allow writes in every region, with conflict resolution by last-writer-wins or custom logic. Set preferred regions in the SDK client so each deployment reads locally.

§7.3.9Security and cost

  • Disable local authentication (account keys) and use Entra ID with Cosmos DB data-plane role assignments.
  • Use private endpoints and disable public access.
  • Enable continuous backup for point-in-time restore.
  • Use one shared CosmosClient per app instance, in direct mode for the .NET and Java SDKs.
  • Watch normalised RU consumption per partition to find hot partitions before users do.

§7.3.10What good looks like

  • Partition keys chosen from access patterns, validated with realistic data volumes.
  • Point reads for hot paths, and RU charges measured in development.
  • Autoscale or serverless chosen deliberately, with alerts on 429 rates.
  • Keys disabled; Entra ID, private endpoints and continuous backup enabled.

§7.3.11Red flags

  • /id as a partition key with every query scanning all partitions.
  • Throughput raised repeatedly to hide a hot partition.
  • A new CosmosClient created per request.
  • Strong consistency chosen "to be safe" for a global app, with unexplained latency.

§7.4.1Blob storage

Blob storage holds unstructured data: uploads, documents, images, exports, backups and static website files.

Concept Notes

Uploads from browsers#

Do not proxy large uploads through your API. Instead:

  1. The API authenticates the user and checks what they may upload.
  2. The API issues a short-lived user delegation SAS for one blob path with write permission only.
  3. The browser uploads directly to Blob storage.
  4. An Event Grid BlobCreated event triggers processing, such as virus scanning, and only then marks the file as available.

Configure CORS on the storage account for your front-end origin only.

§7.4.2Azure Managed Redis

A cache sits in front of slower stores:

Pattern Use
Cache-aside App checks cache, falls back to the database, writes result to cache with a TTL
Session state Distributed sessions for scaled-out apps that truly need sessions
Rate limiting and counters Atomic increments with expiry
Distributed locks Short-lived coordination, with care

Azure Managed Redis is the current service, built on Redis Enterprise software, with better performance per cost than Azure Cache for Redis. The older Azure Cache for Redis Basic, Standard and Premium tiers retire on 30 September 2028, and Microsoft provides migration tooling that keeps hostnames.

Cache rules:

  • Always set a TTL.
  • Decide what happens when the cache is down: fall back to the database with limits, not crash.
  • Beware cache stampedes when a popular key expires; use jittered TTLs or request coalescing.
  • Never treat the cache as the only copy of data.
  • Use Entra ID authentication and private endpoints.

§7.4.3Messaging: pick the right service

Service Model Use for Not for
Service Bus Enterprise message broker: queues and topics with subscriptions Commands and business transactions: "process this order". Ordering with sessions, dead-lettering, duplicate detection, transactions, scheduled delivery Telemetry at millions of events per second
Event Grid Push-based event routing Reacting to discrete events: blob created, resource changed, custom domain events; fan-out to webhooks, Functions, queues Large payloads, guaranteed ordering
Event Hubs Partitioned event streaming log, Kafka-compatible High-volume telemetry, clickstreams, logs, streaming analytics; consumers replay from offsets Per-message acknowledgement workflows
Storage queues Simple queue Very simple, high-volume, low-cost background work Topics, sessions, ordering, larger messages

A helpful distinction:

  • A message is a request that someone must act on, such as ChargeCard. Use Service Bus.
  • A discrete event is a notification that something happened, such as OrderPlaced. Use Event Grid, or Service Bus topics when you need broker guarantees.
  • A stream is a continuous flow of data points. Use Event Hubs.

§7.4.4Reliable messaging patterns

  • Peek-lock and complete. Receive a message, process it, then complete it. If processing crashes, the lock expires and the message is redelivered.
  • Idempotent consumers. Redelivery happens. Use a message ID or business key to skip duplicates.
  • Dead-letter queues. Messages that fail repeatedly or expire move there. Alert on them and have a way to replay.
  • Transactional outbox. When you update the database and publish a message, write the message to an outbox table in the same database transaction, then publish from the outbox. This avoids "saved the order but never published the event".
  • Sessions in Service Bus give first-in-first-out ordering per session ID, such as per order.

§7.4.5Security

  • Disable SAS and local authentication on Service Bus and Event Hubs namespaces; use Entra ID with Data Sender and Data Receiver roles.
  • Private endpoints for namespaces; Premium tier for Service Bus when you need VNet features and predictable performance.
  • Validate Event Grid webhook subscriptions and secure delivery with Entra ID authentication.

§7.4.6What good looks like

  • Files in Blob storage with direct, short-lived SAS uploads and scanning before use.
  • Redis with TTLs, a documented fallback, and a plan off Azure Cache for Redis.
  • Service Bus for commands, Event Grid for discrete events, Event Hubs for streams.
  • Idempotent consumers, dead-letter alerts and an outbox where consistency matters.

§7.4.7Red flags

  • Uploads streamed through the API server, timing out on large files.
  • Account-key SAS URLs valid for a year, shared in emails.
  • Event Hubs used as a job queue with custom locking.
  • Dead-letter queues with thousands of messages nobody has looked at.

§8.1.1Defender for Cloud: posture and protection

Microsoft Defender for Cloud has two halves:

Half What it does Cost
Cloud security posture management (CSPM) Assesses configuration against the Microsoft cloud security benchmark and gives recommendations and a secure score Foundational CSPM is free; Defender CSPM adds attack path analysis, agentless scanning and governance features

Plans relevant to web apps include Defender for App Service, Defender for Storage (including malware scanning of uploads), Defender for Databases, Defender for Key Vault, Defender for Containers, Defender for Resource Manager, and Defender for APIs.

§8.1.2Using secure score well

Secure score measures how many recommendations you have resolved, weighted by severity. It is useful and easy to misuse:

  • Do use it to find high-impact gaps: public network access, missing MFA, no endpoint protection, weak TLS.
  • Do assign owners and due dates to recommendations with the governance feature.
  • Don't chase a perfect score by exempting everything. Exemptions need a reason and an expiry.
  • Do look at attack paths in Defender CSPM, which chain issues together, such as an internet-exposed app with a vulnerability and a managed identity that can read a sensitive storage account. Fixing one link breaks the path.

§8.1.3Zero Trust in practice

Zero Trust is a set of principles, not a product:

Principle In an Azure web app
Verify explicitly Every request authenticated with Entra ID; tokens validated; Conditional Access on users
Use least privilege Managed identities with data-plane roles on single resources; PIM for admins
Assume breach Private endpoints, segmented networks, logging and alerts, encryption, limited blast radius per app

§8.1.4Threat modelling

Before building anything significant, spend an hour on a threat model with the team. For each component and data flow, ask STRIDE questions:

Threat Question
Spoofing Can someone pretend to be a user or service?
Tampering Can data be modified in transit or at rest?
Repudiation Could someone deny an action because we don't log it?
Information disclosure Can data leak through logs, errors, public endpoints or over-broad roles?
Denial of service What happens under load or attack?
Elevation of privilege Can a low-privilege identity gain more?

Record mitigations as backlog items. Revisit when the architecture changes.

§8.1.5A security baseline for Azure web apps

Identity

  • Entra ID for all user and service authentication; no local accounts or shared keys.
  • Managed identities and federated credentials for workloads; no client secrets.
  • Phishing-resistant MFA and PIM for administrators.

Network

  • Front Door or Application Gateway with WAF in Prevention mode for public apps.
  • Private endpoints for data services; public access disabled.
  • Explicit outbound through NAT gateway or firewall.

Data

  • Encryption at rest (default) and TLS 1.2 or later in transit.
  • Customer-managed keys only where regulation requires them; they add operational risk.
  • Backups with soft delete, tested restores, and immutable copies for critical data.

Application

  • Dependency and container image scanning in CI.
  • Secrets scanning in repositories, with push protection.
  • Security headers: HSTS, Content Security Policy, X-Content-Type-Options, frame restrictions.
  • Input validation, parameterised queries, output encoding.

Operations

  • Defender for Cloud enabled with relevant plans.
  • Activity Log, Entra logs, Key Vault logs and app logs retained centrally.
  • Alerts routed to an on-call team with runbooks.

§8.1.6Supply chain security

Many breaches now start in the build pipeline:

  • Pin GitHub Actions to commit SHAs rather than mutable tags for third-party actions.
  • Use least-privilege permissions: in workflows; default the GITHUB_TOKEN to read-only.
  • Protect branches and require reviews for infrastructure and workflow changes.
  • Sign container images and verify signatures on deployment where possible.
  • Generate a software bill of materials (SBOM) for releases.

§8.1.7What good looks like

  • Defender for Cloud enabled, with recommendations owned and triaged weekly.
  • A threat model for each significant system, kept current.
  • A written baseline that templates and policies enforce by default.
  • Pipeline hardening treated as production security.

§8.1.8Red flags

  • Secure score at 95% with half the recommendations exempted "until next quarter" years ago.
  • Defender alerts going to an unmonitored mailbox.
  • No threat model because "it's just an internal app".
  • Third-party GitHub Actions referenced by @main.

Application Insights now uses OpenTelemetry. Use the Azure Monitor OpenTelemetry distro for your language:

Add what matters to the business yourself:

§8.2.3KQL you will use constantly

Failed requests by operation in the last hour:

requests
| where timestamp > ago(1h) and success == false
| summarize failures = count() by operation_Name, resultCode
| order by failures desc

Slowest dependencies:

dependencies
| where timestamp > ago(24h)
| summarize p95 = percentile(duration, 95), calls = count() by target, type
| order by p95 desc

Follow one request end to end:

union requests, dependencies, exceptions, traces
| where operation_Id == "4bf92f3577b34da6a3ce929d0e0e4736"
| order by timestamp asc

Key Vault secret reads by caller:

AzureDiagnostics
| where ResourceProvider == "MICROSOFT.KEYVAULT" and OperationName == "SecretGet"
| summarize reads = count() by identity_claim_appid_g, bin(TimeGenerated, 1h)

§8.2.4Designing alerts people act on

Bad alerting is worse than none, because people learn to ignore it.

Principle Example
Alert on symptoms users feel Error rate above 2% for 5 minutes; p95 latency above 1.5 s
Use causes for dashboards and diagnosis CPU at 80% is interesting, not urgent
Every alert has an owner and a runbook link What to check first, how to mitigate
Severity reflects urgency Sev 1 pages someone; Sev 3 creates a ticket
Review alerts monthly Delete ones nobody acted on

Use availability tests (standard tests from multiple locations) to know the app is down before users tell you. Use smart detection and dynamic thresholds cautiously; tune them.

Define service level objectives (SLOs), such as "99.9% of checkout requests succeed in under 1 second over 30 days", and alert on burning the error budget too fast rather than every blip.

§8.2.5Controlling cost

Log Analytics charges mainly for ingestion. To keep costs sensible:

  • Sampling in Application Insights for high-volume apps.
  • Log at Information in production, not Debug; use dynamic log levels for troubleshooting.
  • Send noisy verbose logs to Basic or Auxiliary table plans, which cost less to ingest and more to query.
  • Filter diagnostic settings to the categories you need.
  • Set retention per table: short for verbose data, long for security data.
  • Use a daily cap carefully; hitting it silently drops data during an incident.

§8.2.6What good looks like

  • Every production resource sending diagnostics to a known workspace.
  • OpenTelemetry-based Application Insights with distributed tracing across services.
  • A short list of symptom-based alerts with owners and runbooks, and SLOs for key journeys.
  • Log costs reviewed monthly.

§8.2.7Red flags

  • Logs containing tokens, passwords or full payment details.
  • Hundreds of alerts firing into a channel everyone muted.
  • No way to trace a request from front end to database.
  • A workspace daily cap hit every afternoon.

§8.3.1Start with numbers

Reliability decisions are cost decisions. Agree two numbers per system with the business:

Term Meaning Example

§8.3.2The Azure Well-Architected Framework

Microsoft's Well-Architected Framework has five pillars: reliability, security, cost optimisation, operational excellence and performance efficiency. Its service guides give recommendations per Azure service, and the Well-Architected Review assessment is a useful checklist before launching something important. Trade-offs between pillars are normal: more redundancy costs more.

§8.3.3Redundancy layers

Layer Protects against Typical cost Complexity
Multiple instances Instance failure, deployments Low Low
Availability zones Datacentre failure Moderate Low for zone-redundant services
Multi-region active-passive Regional outage High Medium to high
Multi-region active-active Regional outage with no failover time Highest High, especially for data

For most business web apps, zone redundancy in one region plus a tested restore or failover plan to a second region meets realistic RTO and RPO targets at sensible cost.

§8.3.4Zone-redundant web app stack

Component Zone redundancy setting
Front Door Global by design

PostgreSQL flexible server Zone-redundant high availability
Storage ZRS or GZRS

Service Bus Premium Zone-redundant in supported regions
Azure Managed Redis Zone redundancy option

Several of these can only be set at creation. Decide before deploying production.

§8.3.5Regional disaster recovery

For a regional DR plan, work through each layer:

  1. Data: SQL failover groups, Postgres cross-region replicas, GZRS storage, Cosmos DB multi-region, Key Vault backup or a second vault populated by the pipeline.
  2. Compute: the same infrastructure-as-code deployed to a second region, either running (warm) or deployable on demand (cold).
  3. Traffic: Front Door routing to the healthy region.
  4. Dependencies: identity is global, but check every other dependency, including third parties and private DNS.
  5. Runbook: who decides to fail over, how, and how to fail back.

A DR plan never tested is a hope, not a plan.

§8.3.6Resilience in code

Infrastructure redundancy does not help if the app falls over on the first transient error.

Pattern Purpose
Retries with exponential backoff and jitter Survive brief failures and throttling
Timeouts on every outbound call Avoid threads hanging forever
Circuit breaker Stop hammering a failing dependency; fail fast
Bulkheads Isolate resources so one slow dependency doesn't exhaust all threads or connections
Graceful degradation Serve cached or partial data when a non-critical dependency is down
Queue-based load levelling Absorb spikes by processing work asynchronously

In .NET, Microsoft.Extensions.Http.Resilience adds a standard resilience pipeline to HttpClient in one line. The Azure SDKs have retry policies built in; don't wrap them in extra retries that multiply attempts.

§8.3.7Backups

  • Rely on platform backups for databases, configured to meet RPO and retention needs.
  • Azure Backup covers VMs, file shares, blobs (operational and vaulted), PostgreSQL flexible server long-term retention and more, with immutable vaults protecting against deletion.
  • Keep at least one copy of critical data that an attacker with your production admin credentials cannot delete. The UniSuper incident in the Google Cloud guide shows why an independent copy matters.

§8.3.8Test it

  • Restore drills quarterly for critical databases, timing each step against RTO.
  • Failover drills for regional DR, in a maintenance window, at least yearly.
  • Azure Chaos Studio can inject faults, such as zone outages, CPU pressure, or blocking network traffic to a dependency, in a controlled experiment.
  • Game days where the team practises the runbook.

§8.3.9What good looks like

  • RTO, RPO and availability targets agreed and documented per system.
  • Zone redundancy in production, set at creation.
  • Retries, timeouts and circuit breakers in application code.
  • Restores and failovers tested on a schedule, with timings recorded.

§8.3.10Red flags

  • "Microsoft handles DR" with no plan for application data and configuration.
  • Single-instance production apps.
  • Retries without timeouts or backoff, turning a blip into an outage.
  • Backups deletable by the same account that runs production.

on:

    branches: [main]

permissions:
  contents: read

    permissions:
      contents: read

          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID_SHARED }}
      - id: meta
        run: echo "image=crorders.azurecr.io/orders-api:${GITHUB_SHA}" >> "$GITHUB_OUTPUT"
      - run: |
          az acr login --name crorders
          docker build -t "${{ steps.meta.outputs.image }}" .
          docker push "${{ steps.meta.outputs.image }}"

  deploy-prod:
    needs: build
    runs-on: ubuntu-latest
    environment: production
    permissions:
      contents: read
      id-token: write
    steps:
      - uses: actions/checkout@v4
      - uses: azure/login@v2
        with:
          client-id: ${{ vars.AZURE_CLIENT_ID }}
          tenant-id: ${{ vars.AZURE_TENANT_ID }}
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}

            --resource-group rg-orders-prod-uks-001 \
            --template-file infra/main.bicep \
            --parameters infra/prod.bicepparam image="${{ needs.build.outputs.image }}"

The client, tenant and subscription IDs are variables, not secrets. They identify but do not authenticate. Authentication comes from GitHub's signed OIDC token, which azure/login exchanges using the federated credential, and which only exists because id-token: write is granted.

§9.1.4Build once, promote everywhere

  • Build the container image or package once, tag it with the commit SHA, and deploy that exact artefact to every environment.
  • Keep environment differences in parameter files (dev.bicepparam, prod.bicepparam) and configuration, not in the build.
  • Record which commit is running in each environment, for example as an app setting or image tag.

§9.1.5Hardening workflows

  • Set permissions: at the top of every workflow, defaulting to read-only.
  • Pin third-party actions to full commit SHAs. First-party actions pinned to major versions are a reasonable trade-off.
  • Never run deployment jobs on pull_request_target or for forks.
  • Require code owner reviews for .github/workflows/ and infra/ directories.
  • Enable secret scanning with push protection and Dependabot for dependencies and actions.
  • Use artifact attestations to record build provenance for images.

§9.1.6Azure DevOps

Azure Pipelines supports the same model through workload identity federation service connections. Convert any older service connections that use client secrets.

§9.1.7What good looks like

  • One deployment identity per environment, federated to a specific GitHub environment.
  • Required reviewers and branch restrictions on production.
  • An immutable artefact promoted through environments.
  • Least-privilege workflow permissions and pinned actions.

§9.1.8Red flags

  • AZURE_CREDENTIALS JSON with a client secret in repository secrets.
  • A federated credential for pull_request with Contributor on production.
  • Rebuilding the image for each environment.
  • Anyone with write access able to edit the production workflow without review.

Environment Purpose Data

Keep production-like environments genuinely like production: same SKUs where behaviour differs, same network isolation, same identity model. "It worked in dev" usually means dev had public access and production didn't.

§9.2.2The Azure Developer CLI

The Azure Developer CLI (azd) bundles infrastructure-as-code, app deployment and pipeline setup into a developer-friendly workflow:

azd init --template todo-csharp-sql      # start from a template, or your own repo
azd env new orders-dev                   # an environment is a named set of parameters
azd up                                   # provision infrastructure and deploy the app
azd pipeline config                      # set up GitHub Actions with federated credentials
azd down --purge                         # tear down, purging soft-deleted vaults

An azure.yaml describes services and where they deploy:

name: orders
services:
  api:
    project: ./src/Orders.Api
    language: dotnet
    host: containerapp
  web:
    project: ./src/web
    language: js
    host: staticwebapp

azd is excellent for getting new projects to a secure, working baseline quickly, and many Microsoft reference templates use it. Larger organisations often keep azd for developer and preview environments and use their standard pipeline tooling for production.

§9.2.3Parameter files

Use one Bicep template and a parameter file per environment:

// prod.bicepparam
using './main.bicep'

param environment = 'prod'
param appServiceSku = 'P1v4'
param zoneRedundant = true
param minReplicas = 3
param publicNetworkAccess = 'Disabled'

Keep secrets out of parameter files. Reference Key Vault in the template or let identities remove the need.

§9.2.4Release strategies

Strategy How on Azure Rollback Best for
Slot swap (blue-green) App Service deployment slots Swap back, seconds App Service apps
Revision traffic split (canary) Container Apps multiple revision mode Shift weight back Container Apps APIs
Feature flags App Configuration Toggle off Risky features, gradual exposure
Rolling Default for many services Redeploy previous version Low-risk changes
Regional rings Deploy region by region behind Front Door Stop the rollout, route away Multi-region apps

Pair any progressive strategy with automated checks: error rate and latency compared with the previous version, gating the next step.

§9.2.5Rollback is part of the design

  • Database changes must be backward compatible, or rollback breaks. Use expand-and-contract: add new schema, deploy code using both, migrate data, then remove old schema in a later release.
  • Keep the previous artefact deployable, by tag or package version.
  • Practise rollback. Time it.
  • Decide in advance what signals trigger a rollback, so the call is not made in a panic.

§9.2.6Preview environments

Per-pull-request environments give reviewers a working app:

  • Container Apps revisions with labels, or Static Web Apps preview environments, make these cheap.
  • Use a dedicated subscription or resource group with strict budgets and automatic clean-up.
  • Never give preview environments access to production data or production identities.

§9.2.7What good looks like

  • Environments defined by the same templates, differing only by parameters.
  • A release strategy per service with a practised rollback path.
  • Backward-compatible schema changes as a team rule.
  • Preview environments cleaned up automatically.

§9.2.8Red flags

  • Staging on a public network while production is private, so network issues appear only in prod.
  • Rollback that requires restoring the database.
  • Preview environments running for months after their pull requests closed.
  • Production deployments on Friday evening with no automated health gates.

§9.3.3Request flow

  1. A customer opens https://orders.contoso.com. Front Door serves the static front end from its cache and origin.
  2. The SPA signs the customer in with External ID using authorisation code with PKCE via MSAL, receiving an access token for the Orders API scope.
  3. The SPA calls https://orders.contoso.com/api/.... Front Door applies WAF rules and forwards to the Container App over Private Link.
  4. The API validates the token: signature, issuer (the External ID tenant), audience, and scope. It then authorises per order: customers see only their own orders.
  5. The API reads and writes Azure SQL as its managed identity, and caches reference data in Redis.
  6. When an order is placed, the API writes the order and an outbox row in one transaction. A background publisher sends OrderPlaced to Service Bus.
  7. The job processes the message idempotently: calls the payment provider with a key from Key Vault, updates the order, and emits telemetry.

§9.3.6Review checklist

Use this for your own designs:

Identity: every call authenticated with Entra; tokens validated on audience, issuer and scope; no secrets for workloads; PIM for admins.

Network: WAF in prevention mode; origins locked; data services private; explicit outbound; central DNS.

Data: Entra-only database access; backups and restores tested; zone redundancy; DR matching RTO and RPO.

App: idempotent consumers; outbox for consistency; retries with timeouts and circuit breakers; no state in memory.

Operations: diagnostics everywhere; SLO-based alerts with runbooks; Defender enabled; cost budgets.

Delivery: infrastructure as code; federated deployments; build once; progressive release with a practised rollback.

§9.3.7Scaling the pattern down

For an internal tool with 50 users, much of this is unnecessary. A sensible minimum: App Service with built-in authentication for the workforce tenant, a managed identity, Azure SQL with Entra-only auth, Key Vault only if a third-party secret exists, Application Insights, and a GitHub Actions pipeline with a federated credential. Add private networking and WAF as data sensitivity and exposure grow.

§S1.2Context

The old API had grown for eight years. A security review found:

  • SQL server admin credentials in app settings, used by the API directly.
  • A storage account key copied into three apps and a developer's local config.
  • Two client secrets that expired unexpectedly in the previous year, each causing an outage.
  • The SQL server firewall allowing "all Azure services", which means any Azure customer's resources.

§S1.3The design

Change Detail
Hosting Container Apps workload profiles environment, VNet-integrated, zone redundant

Network Private endpoints for SQL, storage, Service Bus and Key Vault; central DNS zones
Edge Front Door Premium with WAF and Private Link origin
Delivery GitHub Actions with federated credentials per environment; canary revisions
Remaining secrets Two third-party API keys in Key Vault with expiry dates and rotation runbooks

§S1.4What went well

  • The secret inventory fell from 23 to 2. Rotation and expiry outages disappeared.
  • Revocation became instant. When a worker behaved unexpectedly in testing, removing its role assignment stopped it immediately, with no hunt for copies of a key.
  • Canary releases caught two bad deployments at 10% traffic, rolled back in under five minutes.
  • Audit trails improved. SQL auditing and Key Vault logs now named a specific identity for every access.

§S1.5What went wrong

  • DNS broke the first private endpoint cut-over. The team created a new privatelink zone in the app's resource group instead of using the central one. Dev worked; test resolved to the public IP and timed out. Two days were lost before they found the duplicate zone.
  • Role assignment propagation. New revisions sometimes started before role assignments were effective, failing health checks. Creating identities and assignments in an earlier deployment stage fixed it.
  • A reporting tool needed shared keys. An old BI connector could not use Entra ID for storage. They created a separate, isolated storage account for exports rather than re-enabling keys.
  • Migrations and private networks. GitHub-hosted runners could no longer reach SQL. They moved migrations into a Container Apps job triggered by the pipeline.

§S1.6Outcome

After a year: no secret-related incidents, two canary rollbacks with no customer impact, and a Defender for Cloud secure score that rose mainly through real fixes rather than exemptions. Monthly cost rose about 12%, mostly private endpoints, Front Door Premium and zone redundancy, which the business accepted.

§S1.7Lessons

  • Create identities and permissions before the apps. It removes a whole class of start-up failures.
  • Centralise private DNS from day one. Duplicate zones are the most common private endpoint failure.
  • Plan for pipelines once networks go private. Decide where migrations and secret writes run.
  • Isolate legacy exceptions instead of weakening the main design.

§S2.1Snapshot

Composite scenario built from common patterns. Names and figures are illustrative.

Item Detail
Organisation Ticketing start-up, 8 engineers

§S2.2Context

Traffic was spiky: quiet overnight, then thousands of users in minutes when tickets went on sale. Consumption hosting looked perfect: scale to zero at night, scale out at launch, pay very little.

§S2.3What went well

  • Scaling during launches was excellent. The platform scaled out quickly under sustained load.
  • Costs were very low for a year.
  • Developer productivity was high: triggers and bindings kept code small.

§S2.4What went wrong

  • Cold starts on the first requests. When a sale opened after a quiet period, the first wave of users waited several seconds while instances started. Analytics showed higher checkout abandonment in the first minute of each sale.
  • Heavy start-up. Each function app loaded a large dependency graph, created a new Cosmos client per invocation in one function, and fetched configuration from Key Vault on every call.
  • No virtual network support. The team wanted private access to Cosmos DB, which the Linux Consumption plan could not provide.
  • Retirement. In 2025, Microsoft announced the Linux Consumption plan would retire on 30 September 2028 with no new language versions, forcing a migration anyway.

Key Vault references instead of per-call fetches Fewer calls and faster execution
Trimmed dependencies and enabled ReadyToRun compilation Faster start-up
Scheduled scale-up before announced sales Capacity ready before the spike

§S2.6Outcome

§S2.7Lessons

  • Serverless cost savings can hide revenue costs. Measure latency where it matters to the business.
  • Client reuse and start-up work matter as much as the hosting plan.
  • Know the lifecycle of your platform. Check retirement announcements before building on a plan.
  • Scale ahead of known events instead of relying on reactive scaling alone.

In brief

A composite scenario. A finance company disabled public access to a production SQL server after adding a private endpoint. The app's VNet couldn't resolve the private address. The change was right; the rollout was not.

  2. S3.2Context

§S3.1Snapshot

Composite scenario built from common patterns. Names and figures are illustrative.

Item Detail
Organisation UK lending company, platform team of 6
Change Private endpoint for production Azure SQL; public network access disabled
Impact 90-minute outage of the customer portal
Root cause Private DNS zone not linked to the app's VNet
Verdict Mixed: correct security change, poor change execution

§S3.2Context

An audit required public network access to be disabled on all production data services. The team had done this successfully in development, where the app and database shared a VNet and a private DNS zone created alongside them.

In production, networking was hub and spoke. Private DNS zones lived centrally in the connectivity subscription, managed by a separate network team.

§S3.3What happened

  1. The platform team created the SQL private endpoint in the production spoke and let the portal create a new privatelink.database.windows.net zone in their own resource group, linked only to that resource group's VNet.
  2. The App Service's VNet integration subnet was in a different spoke VNet, linked to the central zone, which had no record for the new endpoint.
  3. From the app, sql-portal-prod.database.windows.net still resolved to the public IP.
  4. Public access was then disabled. Every database connection from the app failed with a login timeout.
  5. Health checks failed, App Service replaced instances, and the portal showed errors.

Diagnosis took an hour because the first responders checked NSGs and SQL firewall rules first. Running nslookup from the App Service console revealed the public IP immediately.

§S3.4What went well

  • Rollback was simple. Re-enabling public access restored service within minutes of diagnosis.
  • The post-incident review was blameless and produced concrete changes.
  • The security goal was achieved the following week, correctly.

§S3.5What went wrong

  • Dev did not match prod. Development had a flat network and local DNS zones; production did not.
  • No pre-check. Nobody verified name resolution from the app's network before disabling public access.
  • Split ownership. DNS zones were owned by another team that was not involved in the change.
  • Troubleshooting order. Responders checked everything except DNS first.

§S3.6What changed

Change Detail
Azure Policy DeployIfNotExists policy attaches new private endpoints to central DNS zones; a Deny policy blocks creating privatelink zones outside connectivity
Change runbook Step 1: create endpoint. Step 2: verify resolution from every consuming network. Step 3: test connection. Step 4: disable public access
Staging parity Staging rebuilt with the same hub and spoke DNS design as production
Troubleshooting guide "Resolve the name first" at the top of the connectivity runbook

§S3.7Lessons

  • DNS is the private endpoint. The endpoint is useless if clients resolve the public address.
  • Separate "add private path" from "remove public path", with verification between them.
  • Make non-production networks mirror production where networking changes are tested.
  • Use policy to make the right thing automatic, especially across team boundaries.

Item Detail
Organisation Insurance broker, small in-house dev team plus contractors
Exposure Storage account connection string with the account key in a public GitHub repository
Duration About five weeks from commit to rotation
Impact Tens of thousands of customer documents accessed by an unknown party; regulator notification

§S4.2Context

The broker stored scanned policy documents in a blob container. The web app used a connection string with the account key. The same connection string was in a shared appsettings.Development.json used by all developers, because "it's only the dev settings". But dev pointed at the production account, because the dev account was missing some test data.

§S4.3What happened

  1. A contractor extracted a small helper tool from the codebase to publish as an open-source utility, and pushed it to a public repository with the settings file included.
  2. Automated credential scanners, run continuously by attackers against public GitHub commits, picked up the AccountKey= pattern within hours.
  3. Over the following weeks, storage logs later showed listing and downloading of the documents container from IP addresses in several countries.
  4. The exposure was discovered when a customer received a phishing email quoting their policy number.

§S4.4Why the damage was so large

  • Account keys are all-powerful. They grant full access to every container, queue, table and file share in the account, and bypass Entra ID, Conditional Access and RBAC.
  • No logging was enabled on the storage account at first. Storage diagnostic logs had to be reconstructed from limited metrics and the partial logs enabled mid-incident.
  • No alerting on unusual download volumes or unfamiliar IP addresses.
  • Public network access was enabled, so the key worked from anywhere.
  • Production data in development workflows multiplied the places the key lived.

§S4.5Response

  • Both account keys rotated, invalidating the leaked one.
  • Public network access restricted; storage diagnostic logging enabled.
  • Forensic review of available logs, customer notification and regulator reporting.
  • A review found the same key in four other places, including a CI variable and a laptop backup.

§S4.6What should have been in place

Control Effect
allowSharedKeyAccess: false with managed identities The leaked string would not have worked at all
Private endpoint and public access disabled The key would not have worked from the internet
Secret scanning with push protection on the organisation's GitHub The push would have been blocked
Separate dev storage with synthetic data No production data exposed by dev settings
Defender for Storage Alerts on unusual access patterns and access from suspicious IPs
Diagnostic logs to Log Analytics Full, queryable record of every read

§S4.7Lessons

  • Assume any secret in code will leak. Design so a leaked string is useless.
  • Account keys and connection strings are root credentials. Disable them.
  • Never point development at production data.
  • Turn logging on before you need it. Retrospective logging does not exist.

§S5.1Snapshot

Real incident. Summarised from Microsoft's own disclosures and public security analysis. Details are simplified; check primary sources before quoting.

Item Detail
Victim Microsoft corporate environment
Threat actor Midnight Blizzard (also known as Nobelium or APT29), attributed to Russian state intelligence
Initial access Password spray against a legacy, non-production test tenant account with no MFA
Period Starting late November 2023; detected 12 January 2024; disclosed 19 January 2024
Impact Access to email and attachments of senior leadership, cybersecurity and legal staff
Verdict Bad

§S5.2What happened

  1. Password spraying. The attackers tried a small number of common passwords against many accounts, from residential proxy IP addresses to avoid detection. They found a working password for an account in a legacy, non-production test tenant. It did not have MFA.
  2. A legacy test OAuth application. In that environment was a legacy test OAuth application that had elevated access to Microsoft's corporate tenant.
  3. Creating more access. The attackers used their foothold to create additional malicious OAuth applications and a new user account to grant consent in the corporate environment.
  4. Full mailbox access. They used the legacy application to grant themselves the Office 365 Exchange Online full_access_as_app role, an application permission that allows access to every mailbox in an organisation through Exchange Web Services.
  5. Targeted collection. They read email and attachments of senior leaders and staff in security and legal functions, apparently looking for what Microsoft knew about the group itself.

Microsoft later reported that the attackers also tried to use information from the stolen email, including secrets shared in emails, to access other systems.

§S5.3Why it worked

Weakness Control from this guide
A test tenant account with no MFA Every tenant is a security boundary; enforce MFA everywhere, including test tenants
A test tenant with a path into production Inventory tenants and cross-tenant apps; no privileged trust from test to production
A legacy OAuth app with elevated permissions Review app registrations and enterprise apps for high-privilege permissions; remove unused apps
Application permission granting all mailboxes Prefer delegated or scoped permissions; for Exchange, RBAC for Applications limits an app to specific mailboxes
Attackers created apps and granted consent Alert on new apps, new credentials and consent grants involving high-privilege permissions
Password spray from residential proxies Block legacy auth, use risk-based Conditional Access, monitor sign-in failures across many accounts

§S5.4What made detection hard

  • The access used legitimate application permissions, not malware.
  • The OAuth app's activity looked like normal service-to-service API use.
  • Residential proxies meant source IPs did not look like obvious attacker infrastructure.

§S5.5Lessons for teams building on Entra ID

  • Test tenants need production-grade identity hygiene if anything in them can reach production.
  • Application permissions are privileged identities. full_access_as_app, Mail.ReadWrite, Directory.ReadWrite.All and similar deserve the same controls as Global Administrator.
  • Unused apps are attack surface. Delete what nobody uses.
  • Monitor the identity control plane: new service principals, credentials added to apps, admin consent grants, and role assignments to applications.
  • Assume email contains secrets and remove them, because attackers do.

§S6.2What happened

  1. A signing key was acquired. The attackers obtained an MSA consumer signing key created in 2016. Microsoft's investigation suggested it may have been exposed through a crash dump moved to a debugging environment on the corporate network, but it could not demonstrate how the key was actually taken.
  2. The key should have been retired. Microsoft had stopped routinely rotating consumer MSA keys in 2021 after an outage, and the key remained valid for signing.
  3. Tokens were forged. With the private key, the attackers could create tokens that looked genuinely signed by Microsoft.
  4. A validation flaw widened the damage. Consumer keys should only ever have been trusted for consumer accounts. Because of a flaw related to a common OpenID Connect metadata endpoint and how applications validated keys, Exchange Online accepted the consumer-signed tokens for enterprise mailboxes.
  5. Email was accessed through Outlook Web Access and APIs as if by the legitimate users.

§S6.3How it was detected

A US government customer had premium audit logging that recorded MailItemsAccessed events. Its security team created an alert for unusual mailbox access by an unexpected application identifier and reported it to Microsoft. Organisations without that logging tier had far less visibility. Microsoft later expanded default logging for customers.

§S6.4CSRB findings, in brief

The board concluded that the intrusion was preventable and pointed to:

  • A cascade of security failures, including the lack of key rotation and the validation flaw.
  • An inadequate security culture that needed an overhaul, given Microsoft's central role.
  • Inaccurate public statements by Microsoft during the incident that were not corrected promptly.

Microsoft responded with its Secure Future Initiative, including automated key rotation, moving signing keys into hardware-backed systems, and stronger token validation in its SDKs.

§S6.5Mapping to controls you own

You don't run Microsoft's signing infrastructure, but the same failure modes appear in application design:

Failure Your equivalent control
Long-lived keys not rotated Automate rotation of certificates and keys; alert on age; store keys in Key Vault or HSMs
A key trusted beyond its intended scope Validate issuer and audience strictly; for multi-tenant apps, validate the tenant; never accept tokens because they are merely "signed by Microsoft"
Hand-rolled validation Use MSAL and Microsoft.Identity.Web or equivalent, kept up to date
Secrets in debugging artefacts Scrub crash dumps and logs; restrict debugging environments; treat them as sensitive
Detection depended on premium logs Turn on and retain the audit logs that record data access, not just sign-ins

§S6.6Lessons

  • Token validation is a security boundary. Signature alone is not enough; issuer, audience and intended key scope matter.
  • Key rotation must be automated and monitored. Manual rotation stops the first time it causes pain.
  • Logging that records data access is essential, and should be available by default.
  • Even the largest providers make chained mistakes. Defence in depth in your own apps limits the damage.
