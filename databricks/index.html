§1.1.1The lakehouse idea

Databricks describes itself as a data intelligence platform built on the lakehouse architecture: data stored in open formats in cloud object storage, with warehouse-style reliability, governance and performance on top.

Traditional split Lakehouse
Data lake for raw files and data science One storage layer in open formats (Delta Lake, Iceberg)
Separate warehouse for BI, with copies SQL warehouses querying the same tables
Separate governance per system Unity Catalog governing data and AI assets

§1.1.2Control plane and compute plane

Plane Runs in Contains
Control plane Databricks' cloud account Web application, notebooks and job definitions, cluster manager, Unity Catalog services, APIs
Classic compute plane Your cloud account and network Clusters and SQL warehouses you configure; data processed inside your VPC or VNet
Serverless compute plane Databricks' cloud account, isolated per workspace Serverless notebooks, jobs, pipelines, SQL warehouses and model serving, started in seconds

Your data lives in your cloud storage, or in Databricks-managed default storage for serverless workspaces.

The choice between classic and serverless affects networking, cost, start-up time and who manages capacity. Most new work should start on serverless unless a specific requirement prevents it.

§1.1.3Accounts, workspaces and metastores

Level Contains
Account All workspaces, users and groups, Unity Catalog metastores, network and billing configuration, in the account console
Metastore Unity Catalog's top-level container, one per region, attached to workspaces in that region
Workspace The environment people use: notebooks, jobs, pipelines, dashboards, compute

Identities are managed at account level and assigned to workspaces. Data governed by Unity Catalog is visible in every workspace attached to the metastore, subject to permissions and workspace bindings.

§1.1.4How many workspaces

Pattern When
Workspaces per environment: dev, test, prod The common baseline
Workspaces per business unit and environment Large organisations with separate teams and billing
A few shared workspaces with Unity Catalog separation Smaller estates; simpler operations

Unity Catalog makes workspaces less important as data boundaries than they used to be. Use them for environment isolation, compute and network configuration, and team boundaries.

§1.1.5Serverless workspaces

Serverless workspaces need no customer VPC or VNet configuration and use serverless compute only, often with default storage. They are the fastest way to start and suit many analytics teams. Organisations with strict network or data residency controls often still use classic workspaces with customer-managed networking, alongside serverless where approved.

§1.1.6Across clouds

Databricks runs on AWS, Microsoft Azure (as Azure Databricks, a first-party Azure service billed through Azure) and Google Cloud. Concepts are the same; details differ:

Area Differences
Networking VPC on AWS and GCP; VNet injection on Azure; private connectivity options named differently
Identity Azure Databricks integrates closely with Microsoft Entra ID
Storage S3, ADLS Gen2, GCS
Billing Azure through the Azure invoice; AWS and GCP through Databricks or cloud marketplaces

§1.1.7What good looks like

  • Environments separated by workspace, governed centrally by Unity Catalog.
  • Serverless as the default for new workloads where requirements allow.
  • Identities managed at account level from the identity provider.
  • A documented reason for any classic compute use.

§1.1.8Red flags

  • One workspace for development and production.
  • Data governed separately in each workspace with legacy table access controls.
  • Clusters configured by hand in every workspace with no policies.
  • Teams unsure whether their data is in their storage or Databricks default storage.

§1.2.1Databricks Units

Databricks charges in Databricks Units (DBUs), a normalised measure of processing capability per hour. The price per DBU depends on:

Factor Effect
Product Jobs compute, all-purpose compute, SQL warehouses, serverless, model serving and others have different rates
Tier Premium or Enterprise features
Cloud and region Rates vary
Commitment Discounts for committed spend

The same notebook run on all-purpose compute costs noticeably more per DBU than on jobs compute. Scheduling production jobs on interactive clusters is one of the most common and expensive mistakes.

§1.2.2Two bills on classic compute

Compute You pay
Classic clusters and SQL warehouses DBUs to Databricks plus virtual machines, disks and networking to your cloud provider
Serverless DBUs only; infrastructure is included in the serverless rate

Serverless DBU rates look higher, but they include the virtual machines, and serverless compute doesn't bill idle start-up time or clusters left running after work finishes. Compare total cost for real workloads.

§1.2.3Tiers

Tier Status
Standard End of life on AWS and Google Cloud since October 2025. On Azure, new Standard workspaces blocked from April 2026, and remaining ones upgraded to Premium by 1 October 2026
Premium The baseline: Unity Catalog, role-based access control, audit logs, serverless, Databricks SQL, AI features
Enterprise (AWS and GCP) Adds enhanced security and compliance features

Teams moving from Standard to Premium should expect higher DBU rates for the same workloads, commonly around a third higher for interactive compute.

§1.2.4Estimating cost

  1. Identify workloads: scheduled pipelines, interactive development, BI queries, model serving.
  2. Map each to compute type: jobs or serverless jobs, all-purpose, SQL warehouse, serving.
  3. Estimate hours and sizes, or run a pilot and read actual usage from system tables.
  4. Add cloud infrastructure for classic compute, storage and networking.

System tables, covered in the operations module, give exact usage per workspace, job, warehouse and tag.

§1.2.5Commitments

  • Databricks commit contracts discount DBUs in exchange for committed spend.
  • On Azure, Azure Databricks pre-purchase plans buy Databricks Commit Units for one or three years.
  • Cloud reserved instances or savings plans can reduce infrastructure costs for steady classic compute.

Commit to a baseline you're confident in, based on several months of usage data.

§1.2.6Free options

Databricks Free Edition gives individuals a free, limited serverless environment for learning. Trials give time-limited access to full features.

§1.2.7What good looks like

  • Production jobs on jobs compute or serverless, never on all-purpose clusters.
  • Total cost compared, including cloud infrastructure, when choosing classic or serverless.
  • Tier migration costs budgeted before automatic upgrades.
  • Commitments sized from measured usage.

§1.2.8Red flags

  • Nightly ETL scheduled on an interactive cluster that runs all day.
  • A cost estimate that ignores the cloud VM bill.
  • A surprise increase after an automatic tier upgrade.
  • A three-year commit signed during a two-week pilot.

§2.1.1Parquet plus a log

A Delta table is a folder of Parquet data files plus a _delta_log folder. Each write adds a numbered JSON commit describing which files were added and removed. Periodic checkpoints summarise the log for fast reads.

Readers use the log to know exactly which files make up a version of the table. That gives:

Guarantee Meaning
Atomicity A write either fully commits or has no effect
Consistency Readers always see a valid table version
Isolation Concurrent writers are handled with optimistic concurrency; conflicts fail cleanly
Durability Committed data stays committed

Delta Lake is open source and is the default table format in Databricks.

§2.1.2Time travel

DESCRIBE HISTORY main.sales.orders;

SELECT * FROM main.sales.orders VERSION AS OF 142;
SELECT * FROM main.sales.orders TIMESTAMP AS OF '2026-09-16T08:00:00';

RESTORE TABLE main.sales.orders TO VERSION AS OF 142;

Time travel depends on old files still existing. VACUUM removes files older than the retention threshold (7 days by default), after which older versions can't be read.

§2.1.3Schema enforcement and evolution

Delta rejects writes whose schema doesn't match the table, which stops bad data silently corrupting tables. When a change is intended:

(new_data.write
   .format("delta")
   .mode("append")
   .option("mergeSchema", "true")
   .saveAsTable("main.sales.orders"))

For MERGE, enable schema evolution with WITH SCHEMA EVOLUTION or the relevant setting. Use evolution in bronze and silver deliberately; control gold schemas through code changes.

§2.1.4MERGE for upserts

MERGE INTO main.sales.customers AS t
USING updates AS s
ON t.customer_id = s.customer_id
WHEN MATCHED AND s.is_deleted THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED AND NOT s.is_deleted THEN INSERT *;

MERGE performance depends on finding matches efficiently. Clustering on the join key and filtering the target, such as by date range when appropriate, reduce files scanned.

§2.1.5Deletion vectors

Deletion vectors mark deleted or updated rows in small side files instead of rewriting whole Parquet files immediately. Updates, deletes and merges become much faster, and files are rewritten later during maintenance. They are enabled by default for new tables in Databricks.

§2.1.6Change data feed

Change data feed (CDF) records row-level changes:

ALTER TABLE main.sales.orders SET TBLPROPERTIES (delta.enableChangeDataFeed = true);

SELECT * FROM table_changes('main.sales.orders', 150, 160);

Each change includes _change_type (insert, update_preimage, update_postimage, delete) and the commit version. Use it to propagate changes incrementally downstream instead of rescanning whole tables.

§2.1.7Constraints and generated columns

ALTER TABLE main.sales.orders ADD CONSTRAINT positive_amount CHECK (net_amount >= 0);

CREATE TABLE main.sales.events (
  event_ts TIMESTAMP,
  event_date DATE GENERATED ALWAYS AS (CAST(event_ts AS DATE))
);

NOT NULL and CHECK constraints are enforced. Primary and foreign keys are informational: useful for documentation and BI tools, not enforced.

§2.1.8What good looks like

  • All tables in Delta (or Iceberg) under Unity Catalog, not loose Parquet or CSV.
  • MERGE for idempotent upserts, with deletes handled explicitly.
  • Change data feed for incremental downstream processing.
  • Constraints on critical columns.

§2.1.9Red flags

  • Overwriting whole tables every hour to apply a few updates.
  • mergeSchema enabled on gold tables so upstream changes flow straight to reports.
  • VACUUM retention reduced to zero, breaking time travel and concurrent readers.
  • Parquet folders written directly by jobs, bypassing the transaction log.

§2.2.1The small files problem

Frequent writes create many small files. Updates leave obsolete files behind. Both slow queries and increase storage costs. Table layout and maintenance fix this.

§2.2.2Liquid clustering

Liquid clustering replaces partitioning and Z-ordering for most tables:

CREATE TABLE main.sales.orders (
  order_id BIGINT, customer_id BIGINT, order_date DATE, net_amount DECIMAL(12,2)
) CLUSTER BY (order_date, customer_id);

ALTER TABLE main.sales.events CLUSTER BY (event_date, account_id);  -- change keys without rewriting everything
Partitioning Liquid clustering
Choosing keys Must be right at creation; low cardinality only Can change later; works with higher cardinality
Small tables Creates many tiny partitions No penalty
Skewed data Unbalanced partitions Adapts
Writes Must align to partitions Incremental clustering on write and during OPTIMIZE

Automatic liquid clustering (CLUSTER BY AUTO) lets Databricks choose and adjust clustering keys from observed query patterns for Unity Catalog managed tables.

Choose clustering keys from the columns most used in filters and joins.

§3.2.1Privileges and inheritance

Privileges are granted to principals (users, groups, service principals) on securable objects:

GRANT USE CATALOG ON CATALOG prod_sales TO `sales-analysts`;
GRANT USE SCHEMA ON SCHEMA prod_sales.gold TO `sales-analysts`;
GRANT SELECT ON SCHEMA prod_sales.gold TO `sales-analysts`;   -- inherited by all current and future tables in the schema

Key points:

  • To read prod_sales.gold.orders, a user needs USE CATALOG, USE SCHEMA and SELECT.
  • Privileges granted on a catalog or schema inherit to child objects, including objects created later.
  • BROWSE lets users discover objects and metadata without reading data, useful for catalogue search.

Common privileges:

Privilege Allows
SELECT Read tables and views
MODIFY Insert, update, delete
CREATE TABLE, CREATE SCHEMA Create objects
READ VOLUME, WRITE VOLUME Access files in volumes
EXECUTE Run functions and use models
MANAGE Manage privileges and ownership without being owner
READ FILES, WRITE FILES On external locations

§3.2.2Ownership

Every object has an owner with full control, including granting. Set owners to groups, not individuals:

ALTER TABLE prod_sales.gold.orders OWNER TO `sales-data-owners`;

When an individual owner leaves, objects become hard to manage. Service principals that deploy pipelines often own the objects they create; make sure a group can still manage them.

§3.2.3Row filters and column masks

Row filters and column masks are SQL functions attached to tables:

CREATE FUNCTION prod_sales.security.region_filter(region STRING)
RETURN is_account_group_member('sales-global') OR is_account_group_member(CONCAT('sales-', region));

ALTER TABLE prod_sales.gold.orders SET ROW FILTER prod_sales.security.region_filter ON (region);

CREATE FUNCTION prod_sales.security.mask_email(email STRING)
RETURN CASE WHEN is_account_group_member('customer-service') THEN email ELSE '***redacted***' END;

ALTER TABLE prod_sales.gold.customers ALTER COLUMN email SET MASK prod_sales.security.mask_email;

They apply wherever the table is queried through Unity Catalog: notebooks, SQL warehouses, dashboards and Genie.

§3.2.4Attribute-based access control

Per-table filters don't scale to thousands of tables. Attribute-based access control (ABAC) uses governed tags and policies:

  1. Define governed tags, such as pii with values email, phone, name, or data_region with values.
  2. Tag columns and tables, manually or with automatic data classification, which detects sensitive data and suggests tags.
  3. Create policies at catalog or schema level that apply masks or filters to anything with matching tags, for defined groups.

New tables inherit protection as soon as they're tagged, without writing per-table functions.

domain-analysts Identity provider SELECT on gold; BROWSE on the catalog

§4.2.1How Spark runs a job

  1. Your code builds a logical plan; nothing runs until an action such as write, count or collect.
  2. The optimiser produces a physical plan.
  3. Work splits into stages separated by shuffles, where data moves between executors.
  4. Each stage runs many tasks, one per partition of data.

Most slowness comes from shuffles, skew, too many or too few partitions, and reading far more data than needed.

§4.2.2Adaptive query execution

Adaptive query execution (AQE) is on by default. At runtime it:

  • Coalesces small shuffle partitions.
  • Switches join strategies, for example to a broadcast join when one side turns out small.
  • Splits skewed partitions in joins.

Don't hand-tune spark.sql.shuffle.partitions for every job; AQE handles most cases. On serverless compute, much tuning is automatic and some settings aren't configurable.

§4.2.3The usual suspects

Symptom Likely cause Fix
One task takes far longer than others in a stage Data skew: one key has huge volume AQE skew handling; salting keys; filtering or handling hot keys separately
Huge shuffle read and write Wide joins or aggregations on large data Filter and select columns earlier; broadcast small tables; cluster tables on join keys
Out-of-memory errors Collecting to the driver; large broadcasts; skew Avoid collect() and toPandas() on large data; reduce broadcast size; fix skew
Thousands of tiny tasks Many small files OPTIMIZE; liquid clustering; predictive optimisation
Slow MERGE Scanning the whole target Cluster target on merge keys; add partition or date predicates

§4.2.5Read less

  • Filter early on clustered or partitioned columns so data skipping works.
  • Use Delta tables, not CSV or JSON, beyond bronze.
  • Avoid SELECT * from wide tables in production code.

§4.2.6Caching

  • The disk cache on classic compute with suitable instance types speeds repeated reads of the same Parquet data automatically.
  • df.cache() helps only when a DataFrame is reused several times in one job, and it costs memory. Don't cache by habit.

  • Start with autoscaling in a sensible range, then check utilisation in system.compute.node_timeline.
  • Memory-heavy jobs benefit from memory-optimised instances; CPU-heavy from compute-optimised.

§5.1.3Auto Loader

Auto Loader incrementally ingests new files from cloud storage or volumes as they arrive:

   .format("cloudFiles")

   .option("cloudFiles.schemaLocation", "/Volumes/prod_sales/bronze/_schemas/orders")

  • Exactly-once file processing using checkpoints.

§5.2.1From DLT to declarative pipelines

Delta Live Tables (DLT) was renamed Lakeflow Declarative Pipelines in 2025 and is now Lakeflow Spark Declarative Pipelines, reflecting Databricks contributing the declarative pipelines model to open-source Apache Spark. Existing DLT code keeps working; import dlt and the newer from pyspark import pipelines as dp style are both supported.

The idea: you declare datasets and how they're derived. The pipeline engine works out dependencies, orchestration, incremental processing, retries and infrastructure.

§5.2.2Dataset types

Type Behaviour Use for
Streaming table Processes each input record once, incrementally Ingestion and append-heavy transformations
Materialised view Result kept up to date, incrementally where possible Aggregations, joins, gold tables
Temporary view Intermediate logic, not published Readability

§5.2.3A pipeline in SQL

CREATE OR REFRESH STREAMING TABLE bronze_orders
COMMENT 'Raw orders from landing files'
AS SELECT *, current_timestamp() AS _ingested_at
FROM STREAM read_files('/Volumes/prod_sales/bronze/landing/orders/', format => 'json');

CREATE OR REFRESH STREAMING TABLE silver_orders (
  CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW,
  CONSTRAINT positive_amount EXPECT (net_amount >= 0)
)
AS SELECT
  CAST(order_id AS BIGINT) AS order_id,
  CAST(customer_id AS BIGINT) AS customer_id,
  CAST(order_ts AS TIMESTAMP) AS order_ts,
  CAST(net_amount AS DECIMAL(12,2)) AS net_amount
FROM STREAM(bronze_orders);

CREATE OR REFRESH MATERIALIZED VIEW gold_daily_sales
AS SELECT DATE(order_ts) AS order_date, SUM(net_amount) AS net_sales, COUNT(*) AS orders
FROM silver_orders
GROUP BY DATE(order_ts);

§5.2.4The same in Python

from pyspark import pipelines as dp
from pyspark.sql import functions as F

@dp.table(comment="Cleaned orders")
@dp.expect_or_drop("valid_order_id", "order_id IS NOT NULL")
@dp.expect("positive_amount", "net_amount >= 0")
def silver_orders():
    return (spark.readStream.table("bronze_orders")
            .select(F.col("order_id").cast("bigint"), "customer_id", "order_ts", "net_amount"))

§5.2.5Expectations

On violation Effect
(default) warn Keep the row; record metrics
DROP ROW Remove failing rows; record metrics
FAIL UPDATE Stop the pipeline update

Expectation metrics appear in the pipeline UI and event log, giving data quality history without extra tooling. Use FAIL for rules where bad data must never reach consumers, DROP for known noise, and warnings for monitoring.

§5.2.6Change data capture with AUTO CDC

AUTO CDC (formerly APPLY CHANGES) applies change feeds correctly, handling ordering and deletes:

CREATE OR REFRESH STREAMING TABLE silver_customers;

CREATE FLOW customers_cdc AS AUTO CDC INTO silver_customers
FROM STREAM(bronze_customers_cdc)
KEYS (customer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY change_ts
COLUMNS * EXCEPT (operation, change_ts)
STORED AS SCD TYPE 2;
  • SEQUENCE BY resolves out-of-order events.
  • STORED AS SCD TYPE 1 keeps the latest row; SCD TYPE 2 keeps history with validity columns.
  • AUTO CDC FROM SNAPSHOT derives changes by comparing periodic full snapshots from sources without change feeds.

§5.2.7Running pipelines

Setting Guidance
Serverless Recommended; automatic scaling and optimisation
Triggered versus continuous Triggered for scheduled freshness; continuous only for genuine low-latency needs
Development mode Reuses compute and doesn't retry; use while building
Production mode Retries and restarts; use for scheduled runs
Catalog and schema Publish to Unity Catalog with the pipeline's target schema

Full refresh reprocesses everything and resets streaming tables. Restrict who can run full refreshes in production, because sources may no longer hold all history.

§5.2.8When to use declarative pipelines

Good fit Consider plain jobs instead
Medallion pipelines with SQL or DataFrame transformations Heavy procedural logic and API calls
CDC and slowly changing dimensions Existing, stable jobs with no pain
Streaming and batch combined Workloads needing unsupported libraries or configurations
Teams wanting built-in quality metrics

§5.2.9What good looks like

  • Streaming tables for ingestion, materialised views for gold.
  • Expectations on critical columns, with FAIL for rules that protect consumers.
  • AUTO CDC for change feeds and SCD Type 2 dimensions.
  • Serverless, triggered pipelines in production mode.

§5.2.10Red flags

  • Hand-written MERGE and watermark logic for CDC that AUTO CDC would handle.
  • A continuous pipeline running 24/7 for a daily report.
  • Full refreshes run casually in production, wiping history that sources no longer have.
  • No expectations anywhere, so bad data is found by report users.

§8.1.1Account-level identities

Users, groups and service principals are managed in the account, then assigned to workspaces.

  • Sync from your identity provider with SCIM provisioning or automatic identity management (available for Microsoft Entra ID on Azure and other providers), so joiners and leavers flow automatically.
  • Use single sign-on with the identity provider's MFA and Conditional Access or device policies.
  • Grant data access to groups in Unity Catalog; assign workspace access to groups too.

Avoid workspace-local groups, which don't work with Unity Catalog governance.

§8.1.2Admin roles

Role Can

§8.1.4Controlling PATs

  • Set a maximum lifetime.
  • Monitor token usage in audit logs and system.access.audit.

§8.2.1Three network paths

Path Between Controls
Front end Users and tools to the workspace IP access lists, front-end private connectivity, SSO and Conditional Access

Serverless compute plane Databricks-hosted compute to your data and services Network connectivity configurations, private endpoints, egress network policies

§8.2.2Classic compute networking

  • AWS and GCP: deploy workspaces into a customer-managed VPC with your subnets, security groups, routes and egress.
  • Azure: VNet injection puts clusters in your VNet subnets.
  • Secure cluster connectivity (no public IP) means cluster nodes have no public addresses and connect out to the control plane.
  • Route egress through a firewall or NAT with allow rules for Databricks control plane endpoints and your data sources.

On Azure, remember the retirement of default outbound access for new VNets: injected workspaces need explicit outbound such as a NAT gateway or firewall.

§8.2.3Private connectivity

Type Secures
Front-end private link User and API traffic to the workspace over a private endpoint
Back-end private link Classic compute plane to control plane traffic
Private endpoints for storage and services Compute to your storage accounts, buckets, databases and Key Vault

Combine private front-end access with disabling public access to the workspace where required.

§8.2.4Serverless networking

Serverless compute runs in Databricks' account, so you control how it reaches your resources:

  • Network connectivity configurations (NCCs) are account-level, regional objects attached to workspaces. They provide stable egress addresses or subnets for firewall rules and manage private endpoints from serverless compute to your resources, such as storage accounts and databases.
  • Serverless egress control uses network policies to restrict outbound internet access from serverless compute to approved destinations, blocking data exfiltration through arbitrary endpoints.

Databricks recommends sharing an NCC among workspaces in the same business unit and region.

§8.2.5IP access lists

IP access lists restrict access to the workspace and account console to known networks:

databricks ip-access-lists create --json '{
  "label": "corporate-egress",
  "list_type": "ALLOW",
  "ip_addresses": ["203.0.113.0/24"]
}'

Test carefully; wrong lists lock out admins and integrations.

§8.2.6Encryption and keys

  • Data at rest in your storage is encrypted with cloud-managed keys by default.
  • Customer-managed keys can encrypt managed services data (notebooks, secrets, queries), workspace storage and managed disks, depending on cloud and tier.
  • Unity Catalog managed storage can also use customer-managed keys configured on your storage.

§8.2.7Compliance security profile

The compliance security profile enables controls for regulated workloads, such as HIPAA, PCI DSS and others: hardened images, enhanced monitoring, encryption in transit between nodes, and restrictions to compliant compute types. Enabling it limits some features and instance types, so plan before switching on.

Enhanced security monitoring adds antivirus and file integrity monitoring on compute images, with logs in system tables.

§8.2.8A baseline by sensitivity

Data sensitivity Baseline
Internal analytics SSO with MFA, IP access lists, serverless with egress policies, Unity Catalog
Confidential Plus private connectivity for front end and storage, NCC private endpoints, customer-managed keys where required
Regulated Plus compliance security profile, enhanced monitoring, strict egress, audit monitoring

§8.2.9What good looks like

  • Explicit, documented paths for front end, classic and serverless traffic.
  • Serverless egress restricted with network policies.
  • Private endpoints for storage from both classic and serverless compute.
  • Compliance profile and monitoring for regulated workspaces.

§8.2.10Red flags

  • A locked-down classic VNet while serverless compute can call any internet endpoint.
  • Storage firewalls opened to all networks so serverless can reach them.
  • IP access lists that include 0.0.0.0/0 "temporarily".

§9.2.1Cost from system tables

system.billing.usage records every DBU consumed, with workspace, SKU, usage metadata such as job, warehouse and pipeline IDs, and custom tags. Join with system.billing.list_prices for list cost:

SELECT
  u.workspace_id,
  u.sku_name,
  u.usage_metadata.job_id,
  u.custom_tags['cost_centre'] AS cost_centre,
  SUM(u.usage_quantity * p.pricing.default) AS list_cost
FROM system.billing.usage u
JOIN system.billing.list_prices p
  ON u.sku_name = p.sku_name
 AND u.usage_start_time >= p.price_start_time
 AND (p.price_end_time IS NULL OR u.usage_start_time < p.price_end_time)
WHERE u.usage_date >= current_date() - 30
GROUP BY ALL
ORDER BY list_cost DESC;

Databricks also provides prebuilt usage dashboards built on these tables. Remember classic compute also has a cloud infrastructure bill outside Databricks.

§9.2.2Budgets and tags

  • Budgets in the account console alert when spend for a scope, such as tagged workloads or workspaces, crosses thresholds.
  • Tags on compute, jobs, pipelines, warehouses and serverless budget policies flow into billing records. Enforce cost_centre and owner tags with compute policies and serverless budget policies.

§9.2.3Common cost leaks

Leak Fix
Production jobs on all-purpose clusters Serverless jobs or job compute
All-purpose clusters without auto-termination Compute policies enforcing 30–60 minutes
SQL warehouses with long auto-stop or oversized Serverless, short auto-stop, right size
Continuous pipelines for daily needs Triggered mode
Full reprocessing instead of incremental Streaming tables, AUTO CDC, materialised views
Unmaintained tables slowing everything Predictive optimisation on managed tables
Oversized model serving with provisioned capacity Scale to zero; batch inference
ai_query over huge tables repeatedly Materialise results; sample first
Instance pools with idle instances Minimum idle set to zero where start-up time is acceptable

A monthly review of top jobs, warehouses and endpoints by cost, with owners, usually finds the biggest savings quickly.

§9.2.4Lakebase

Lakebase is a fully managed PostgreSQL database service inside Databricks, generally available (including on Azure with autoscaling, scale-to-zero, branching and instant restore):

  • Separated storage and compute, with branching for development and testing copies.
  • Synced tables move data between Unity Catalog Delta tables and Postgres, for example serving curated features or reverse ETL data to applications.
  • Governed and billed within the platform.

Use it for application state behind Databricks Apps, operational data serving, and agent memory. At the 2026 Data + AI Summit, Databricks announced LTAP, building on Lakebase to store transactional data in open lake formats from the point of write, reducing ETL between operational and analytical systems. Treat newly announced capabilities as roadmap until available in your region.

§9.2.5Databricks Apps

Databricks Apps host data and AI applications built with Streamlit, Dash, Gradio, Flask, FastAPI, Node.js and similar frameworks directly in the workspace:

  • Serverless hosting with OAuth sign-in for users.
  • Apps use a service principal identity, or act on behalf of users so Unity Catalog permissions apply per user.
  • Resources such as SQL warehouses, serving endpoints, secrets and Lakebase databases are attached declaratively and can be deployed with bundles.
  • Network controls and private connectivity apply as for other serverless workloads.

Good for internal tools: approval workflows, forecasting interfaces, chat interfaces over agents, and data entry backed by Lakebase.

§9.2.6What good looks like

  • Cost dashboards from system tables, reviewed monthly with owners.
  • Tags enforced on classic and serverless usage.
  • Lakebase used for operational serving needs instead of misusing Delta tables for row-level transactions.
  • Apps using on-behalf-of-user authorisation where data sensitivity varies by user.

§9.2.7Red flags

  • No one has queried system.billing.usage.
  • Serverless costs unattributed because budget policies were never set up.
  • An app's service principal given ALL PRIVILEGES on production catalogs so every user sees everything.
  • High-frequency single-row updates hammering Delta tables to back an application.

§S1.2The starting problems

§S1.5What went wrong

  • Hidden dependencies. Some notebooks read files through mount paths built from string concatenation that scanning missed. Failures appeared in the first week after each cut-over.
  • RDD and legacy libraries didn't run on standard access mode. A few ML jobs moved to dedicated access mode.
  • Group sprawl. Converting per-user ACLs created too many groups. A second pass consolidated them.

§S1.6Lessons

  • Use migration tooling for inventory, then expect a tail of hidden dependencies.
  • Migrate domain by domain with clear cut-over dates.
  • Remove the old access paths or governance is optional.
  • Unity Catalog is a prerequisite for most modern Databricks capabilities.

A composite scenario. A media company moved jobs and SQL warehouses from classic compute to serverless. Operations became simpler and idle costs disappeared, but private network access needed redesign and some large jobs cost more until they were optimised.

Outcome Total spend down about 15% after three months; up in the first month

§S4.2What went well

  • No cluster management. Engineers stopped tuning instance types and runtimes.
  • Idle cost disappeared. Classic warehouses and clusters had been billing during slow start-ups and long auto-termination windows.
  • Faster starts made short jobs practical to run more frequently.
  • Cloud bill simplified: fewer VMs, disks and NAT gateways.

§S4.3What went wrong

  • Private resources unreachable. Jobs reading a database and storage behind private endpoints failed on serverless. The team had to create a network connectivity configuration with private endpoints and update storage firewall rules, which took three weeks with the network team.
  • Egress surprise. Security discovered serverless compute could reach the internet freely and required egress network policies before production data moved.
  • A few heavy jobs cost more. Five large jobs had been heavily tuned on spot instances. On serverless they initially cost about double until code was optimised and incremental processing introduced.
  • Unsupported libraries. Two jobs using custom JARs and init scripts stayed on classic compute.

§S4.4Lessons

  • Plan networking first: NCCs, private endpoints and egress policies before migrating workloads that touch private resources.
  • Compare total cost, including cloud infrastructure and idle time, per workload.
  • Keep classic for genuine exceptions, with policies.
  • Optimise the heaviest jobs as part of the move, not after the bill arrives.

Item Detail
Organisation Travel booking company
Cause Scheduled jobs on all-purpose clusters; auto-termination disabled; oversized nodes; no tags
Effect Monthly Databricks and Azure infrastructure spend roughly tripled over six months
Verdict Bad

§S5.2What happened

  • To avoid slow cluster start-ups, engineers created large all-purpose clusters and disabled auto-termination.
  • Scheduled jobs were attached to these clusters "because they were already running".
  • Every engineer could create clusters of any size; several GPU clusters for experiments were left running.
  • No tags existed, so cost couldn't be attributed.
  • Finance escalated when the monthly Azure bill exceeded the annual budget forecast by a wide margin.

§S5.3The cost mechanics

Factor Effect
All-purpose DBU rate versus jobs or serverless Same work billed at a higher rate
Clusters running 24 hours a day Paying for idle time nights and weekends
Large memory-optimised nodes for small jobs Paying for unused capacity
GPU clusters idle Very expensive idle time
Cloud VM costs on top of DBUs Two bills growing together

§S5.4The fix

  1. Compute policies for all users: maximum sizes, approved instance types, auto-termination at 30 minutes, required tags.
  2. Jobs moved to serverless jobs or job compute.
  3. Unrestricted cluster creation removed; GPU access by request with a separate policy.
  4. System table cost dashboard by team and job; budget alerts.
  5. Weekly review of the top 20 costs for the first quarter.

Spend fell by more than half within two months, below the original level despite more workloads.

§S5.5Lessons

  • Never run production on all-purpose clusters.
  • Policies are the cheapest cost control in Databricks.
  • Tags from day one make cost visible and owned.
  • Idle compute is the biggest leak, not query efficiency.

Item Detail
Organisation Online lender
Credential Personal access token with no expiry, belonging to a senior data engineer
Exposure Committed in a public repository for a personal automation script
Impact Customer tables queried and exported through the SQL API over two days
Verdict Bad

§S6.2What happened

  1. A data engineer wrote a personal script to automate a report and hard-coded a PAT.
  2. The script went into a public GitHub repository.
  3. Automated scanners found the token within hours.
  4. The attackers used the Databricks SQL API from cloud VMs to list catalogs and export customer tables in chunks.
  5. The activity was noticed two days later when a SQL warehouse ran unusually long overnight, triggering a cost alert.

§S6.3Why the damage was large

Weakness Detail
PATs allowed for everyone with no maximum lifetime The token was over a year old
No IP access lists The workspace accepted API calls from any IP
Broad privileges The engineer had SELECT on all production catalogs "for debugging"
No masking Customer personal data unmasked for engineers
No audit alerting Unusual API use from new IPs went unnoticed

§S6.4Response

  • Token revoked; all PATs reviewed and most revoked.
  • Forensic review using system.access.audit to identify accessed tables.
  • Regulator and customer notifications.

§S6.5What changed

Control Detail
PATs disabled for most users; maximum 30-day lifetime for exceptions Stolen tokens expire quickly or can't exist
OAuth user-to-machine for CLI use; workload identity federation for automation No long-lived secrets
IP access lists and front-end private connectivity Stolen credentials don't work from the internet
Engineers' production access through groups granted just in time No standing access to all customer data
ABAC masking for personal data Engineers see masked values by default
Secret scanning with push protection on GitHub Blocks commits containing tokens
Audit alerts for API access from new IPs and large exports Faster detection

§S6.6Lessons

  • Long-lived tokens are passwords that bypass MFA. Replace them with OAuth and federation.
  • Network restrictions limit stolen credential value.
  • Least privilege matters most for the most capable users.
  • Cost alerts can be security alerts, but shouldn't be your only detection.
