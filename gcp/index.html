§1.1.1The hierarchy

Level What it is Used for
Organisation Root node tied to a Google Workspace or Cloud Identity domain Organisation-wide IAM and policies
Folder Groups projects and other folders Business units, environments, policy inheritance
Project The basic container for resources, APIs, IAM and quotas Everything you build lives in a project
Resource A dataset, bucket, topic, database instance The things themselves

IAM policies and organisation policies inherit downwards. A role granted on a folder applies to every project in it.

Each project has a project ID (globally unique, permanent), a project name (changeable) and a project number.

§1.1.2Billing accounts

A Cloud Billing account pays for projects linked to it. Several projects can share a billing account; a project has at most one. Billing export to BigQuery is the foundation for cost analysis and should be enabled on day one.

§1.1.3Laying out a data platform

Folder Projects
platform acme-network-host (Shared VPC), acme-logging, acme-security
data-prod acme-data-ingest-prod, acme-data-lake-prod, acme-data-warehouse-prod, acme-data-ml-prod
data-nonprod Matching dev and test projects
analytics acme-bi-prod (Looker, reporting service accounts), acme-sandbox-<team>

Why separate projects:

  • IAM boundaries: engineers can administer ingestion without owning the warehouse.
  • Quotas and limits are per project.
  • Cost reporting by project is automatic.
  • BigQuery compute and storage can live in different projects: queries are billed to the project that runs the job, while data can live elsewhere.

Don't overdo it. A project per table or per pipeline becomes unmanageable.

§1.1.4Labels and tags

  • Labels are key-value pairs on resources, flowing into billing export for cost allocation: team, env, cost_centre.
  • Tags (resource manager tags) are governed key-values that organisation policies and IAM conditions can reference, for example allowing a policy only on resources tagged env=prod.

§1.1.5Regions and multi-regions

Location type Example Notes
Region europe-west2 (London) Data stays in one region; lowest latency to nearby services
Multi-region EU, US BigQuery datasets and Cloud Storage buckets spread across regions in a geography
Dual-region Cloud Storage only Two specific regions

BigQuery can't join datasets in different locations in one query. Choose dataset locations carefully and consistently, because moving datasets later means copying.

Use the resource locations organisation policy to restrict where resources can be created, for data residency.

§1.1.6Landing zones

Google's enterprise foundations blueprint and Cloud Foundation Fabric provide Terraform starting points for organisation structure, networking, logging and security. They're worth using rather than inventing a structure from scratch.

§1.1.7What good looks like

  • Folders for environments and business areas; projects separated by function.
  • Billing export to BigQuery from the start.
  • Labels on every resource for cost allocation.
  • Dataset locations chosen deliberately and restricted by policy.

§1.1.8Red flags

  • One project holding dev, test and production data.
  • Datasets scattered across US, EU and three regions, so queries can't join them.
  • No billing export, and cost questions answered from invoice PDFs.
  • Hundreds of projects with no folder structure.

§1.2.1The IAM model

An allow policy on a resource binds principals to roles:

Principal type Example
Google account user:jane@acme.com
Google group group:data-analysts@acme.com
Service account serviceAccount:ingest@acme-data-ingest-prod.iam.gserviceaccount.com
Workload identity pool principal Identities from GitHub, AWS, Azure or Kubernetes
Domain domain:acme.com

A role is a collection of permissions such as bigquery.tables.getData.

Role type Examples Guidance
Basic Owner, Editor, Viewer Far too broad; avoid for production
Predefined roles/bigquery.dataViewer, roles/bigquery.jobUser, roles/storage.objectViewer Default choice
Custom Your own permission sets When predefined roles are too broad

Grant roles to groups, not individuals, and at the narrowest resource that works: a dataset rather than a project.

§1.2.2BigQuery roles you'll use constantly

Role Grants
bigquery.dataViewer Read tables in a dataset or project
bigquery.dataEditor Read and write tables
bigquery.jobUser Run jobs (queries) in a project
bigquery.user Run jobs and create datasets
bigquery.dataOwner Full control of datasets, including sharing
bigquery.admin Everything; platform administrators only

A user needs both the ability to run jobs in some project and read data in the dataset. They're often in different projects.

§1.2.3Service accounts

Service accounts are identities for workloads: Dataflow jobs, Cloud Run services, Airflow tasks, scheduled queries.

  • Use one service account per workload with minimal roles.
  • Attach service accounts to resources, such as a Cloud Run service or Dataflow job, so code gets tokens automatically through the metadata server. Application Default Credentials in client libraries find them.
  • Beware default service accounts such as the Compute Engine default, which historically had Editor. New organisations enforce a policy preventing that automatic grant.

§1.2.4No service account keys

Service account keys are long-lived JSON credentials. They leak through repositories, laptops and CI logs, and they work from anywhere.

Organisations created since 2024 enforce secure-by-default organisation policies, including iam.disableServiceAccountKeyCreation, iam.disableServiceAccountKeyUpload, and iam.automaticIamGrantsForDefaultServiceAccounts. Keep them enforced. Alternatives:

Need Use instead of keys
Code running on Google Cloud Attached service account
Engineer acting as a service account Impersonation with roles/iam.serviceAccountTokenCreator
CI/CD in GitHub, GitLab or Azure DevOps Workload identity federation
Workloads on AWS, Azure or on-premises Workload identity federation
Kubernetes on GKE Workload Identity Federation for GKE

Impersonation from the CLI:

gcloud config set auth/impersonate_service_account deploy@acme-data-ingest-prod.iam.gserviceaccount.com

§1.2.5Workload identity federation for GitHub Actions

gcloud iam workload-identity-pools create github --location=global
gcloud iam workload-identity-pools providers create-oidc github-oidc \
  --location=global --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" \
  --attribute-condition="assertion.repository == 'acme/data-platform' && assertion.ref == 'refs/heads/main'"

The attribute condition is the security control: only that repository and branch can exchange tokens. Then grant the pool principal permission to impersonate a deployment service account, or grant roles directly.

§1.2.6IAM conditions and deny policies

  • IAM conditions add attributes to grants, such as expiry times for temporary access, resource name prefixes, or tags: request.time < timestamp("2026-10-01T00:00:00Z").
  • Deny policies block permissions regardless of allow policies, for example denying bigquery.tables.delete on production to everyone except a break-glass group.
  • Privileged Access Manager grants temporary, approved elevation, similar to just-in-time access elsewhere.

§1.2.7Reviewing access

  • IAM Recommender suggests removing unused permissions based on 90 days of activity.
  • Policy Analyzer answers "who can access this dataset" across inheritance.
  • Cloud Audit Logs record admin activity and, when enabled, data access.

§1.2.8What good looks like

  • Predefined roles on groups at dataset or project level.
  • One service account per workload; no keys anywhere.
  • Workload identity federation for CI/CD and external workloads.
  • Temporary elevated access with conditions or Privileged Access Manager.

§1.2.9Red flags

  • Editor on the project for every engineer.
  • A JSON key file in a repository, a Docker image or an Airflow variable.
  • One data-pipeline@ service account used by every job.
  • Secure-by-default policies overridden "to get something working".

§1.3.1Organisation policies

Organisation policies constrain what can be configured, regardless of IAM:

Constraint Effect
gcp.resourceLocations Restrict resource creation to approved regions
iam.allowedPolicyMemberDomains Only identities from your domains can be granted access (domain-restricted sharing)
iam.disableServiceAccountKeyCreation No service account keys
storage.publicAccessPrevention Buckets can't be made public
storage.uniformBucketLevelAccess Consistent IAM on buckets
sql.restrictPublicIp Cloud SQL instances without public IPs
compute.vmExternalIpAccess Restrict external IPs on VMs
gcp.restrictCmekCryptoKeyProjects Keys must come from approved key projects

Set policies at organisation or folder level. Use dry-run mode to see what would break before enforcing.

§1.3.2VPC Service Controls

IAM answers "who". VPC Service Controls (VPC SC) answer "from where, and to where":

  • A service perimeter surrounds projects and protected services, such as BigQuery, Cloud Storage and Pub/Sub.
  • Requests crossing the perimeter are blocked unless explicitly allowed, even with valid credentials.
  • This stops data exfiltration such as copying a table to a bucket in a personal project, or reading data with stolen credentials from outside approved networks.
Perimeter: data-prod
  Projects: acme-data-ingest-prod, acme-data-lake-prod, acme-data-warehouse-prod
  Restricted services: bigquery.googleapis.com, storage.googleapis.com, pubsub.googleapis.com
  Access levels: corporate IP ranges; managed devices
  Ingress rules: Looker service account reading warehouse datasets
  Egress rules: exports to the partner-sharing project only

Practical guidance:

  • Start in dry-run mode, review violation logs for weeks, then enforce.
  • Expect breakage: BI tools, notebooks, Dataflow jobs and cross-project copies all need explicit rules.
  • Keep perimeters coarse (production data platform) rather than one per project.
  • Document ingress and egress rules with owners.

§1.3.3Private access to Google APIs

Feature Does
Private Google Access VMs without external IPs reach Google APIs
Private Service Connect for Google APIs Private endpoints in your VPC for Google APIs, such as restricted.googleapis.com used with VPC SC
Private Service Connect for services Private consumption of managed services and partner services
Private service access Private IP connectivity to Cloud SQL, AlloyDB, Memorystore and others

§1.3.4Encryption and Cloud KMS

All data is encrypted at rest by default with Google-managed keys. Customer-managed encryption keys (CMEK) use keys you control in Cloud KMS:

  • Supported by BigQuery (Enterprise and Enterprise Plus editions), Cloud Storage, Pub/Sub, Dataflow, Cloud SQL, Spanner and more.
  • Cloud KMS Autokey creates keys automatically per resource with sensible defaults.
  • Cloud HSM for hardware-backed keys; Cloud External Key Manager (EKM) for keys held outside Google.

CMEK gives control, including the ability to revoke access, and adds operational risk: disabled or destroyed keys make data unreadable. Use it where policy requires, with separate key admin roles and monitoring.

§1.3.5Putting it together

Layer Control
Identity Groups, predefined roles, no keys, federation
Guardrails Organisation policies for location, sharing and public access
Perimeter VPC SC around production data projects
Network Private access to APIs and databases; no public IPs
Encryption Default, or CMEK where required
Detection Security Command Center and audit logs

§1.3.6What good looks like

  • Organisation policies enforced for locations, domain-restricted sharing and public access.
  • VPC SC protecting production data, rolled out through dry-run.
  • Databases and workers on private IPs.
  • CMEK only where required, with Autokey or clear key ownership.

§1.3.7Red flags

  • Domain-restricted sharing disabled so a contractor's Gmail account can be added.
  • VPC SC enforced overnight without dry-run, breaking every dashboard.
  • Public IPs on Cloud SQL "for the BI tool".
  • CMEK keys administered by the same people who administer the data.

§2.1.1Serverless by design

BigQuery is a serverless data warehouse:

  • Storage is columnar and managed, separate from compute.
  • Compute is measured in slots, units of CPU and memory allocated to queries on demand.
  • There are no clusters to size, indexes to build or vacuum jobs to run.

A query is a job. Jobs run in a project, which is billed, and read data from datasets that may be in other projects.

§2.1.2Objects

Object Notes
Dataset Container for tables and views; has a location and default settings
Table Native, external, BigLake or Iceberg tables
View, materialised view Saved queries; materialised views store results
Routine SQL and JavaScript UDFs, stored procedures, table functions
Model BigQuery ML models

§2.1.3On-demand pricing

With on-demand pricing, you pay per terabyte scanned by queries, currently USD 6.25 per TiB in many locations, with the first 1 TiB per month free. Queries share a large pool of slots per project, up to a quota.

  • Simple, no commitment, great for small or unpredictable workloads.
  • Cost depends entirely on bytes scanned. SELECT * on a 10 TB table costs about USD 62 every time it runs.
  • Control it with partition filters, clustering, column selection, and custom query quotas.

§2.1.4Capacity pricing with editions

Reservations have:

  • A baseline of slots always allocated.
  • Autoscaling up to a maximum, adding slots in increments of 50 when needed, billed only while used.
  • Optional commitments for one or three years at discounted rates, covering the baseline.

§2.2.1Partitioning

Partitioning divides a table into segments, most often by date, so queries can skip irrelevant partitions:

CREATE TABLE analytics.events (
  event_ts TIMESTAMP,
  user_id STRING,
  event_name STRING,
  properties JSON
)
PARTITION BY DATE(event_ts)
CLUSTER BY user_id, event_name
OPTIONS (
  partition_expiration_days = 400,
  require_partition_filter = TRUE
);
Partitioning type Use
Time-unit column (day, hour, month, year) Most event and fact tables
Ingestion time When no reliable timestamp column exists
Integer range Numeric keys with even distribution
  • require_partition_filter stops queries that would scan the whole table. It is one of the best cost controls in BigQuery.
  • partition_expiration_days deletes old partitions automatically.
  • Limit of 10,000 partitions per table; daily partitioning covers about 27 years.
  • Don't partition small tables; clustering alone is better below roughly 10 GB.

§2.2.2Clustering

Clustering sorts data within partitions by up to four columns. Queries filtering or aggregating on those columns read less data. BigQuery re-clusters automatically at no cost.

Choose clustering columns that are frequently filtered, ordered from most to least commonly used, such as customer_id then event_name.

§2.2.3Nested and repeated fields

BigQuery performs best when related data is stored together instead of joined:

CREATE TABLE sales.orders (
  order_id STRING,
  order_ts TIMESTAMP,
  customer STRUCT<id STRING, email STRING, country STRING>,
  lines ARRAY<STRUCT<sku STRING, quantity INT64, unit_price NUMERIC>>
);

SELECT o.order_id, line.sku, line.quantity * line.unit_price AS line_total
FROM sales.orders AS o, UNNEST(o.lines) AS line
WHERE DATE(o.order_ts) = '2026-09-16';

Nested orders with their lines avoid a large join. Keep dimensions that change independently, such as product attributes, in separate tables.

§2.2.4Schema practices

  • Use NUMERIC or BIGNUMERIC for money, not FLOAT64.
  • Use TIMESTAMP for instants in time and DATETIME only for wall-clock values without time zones.
  • Use JSON type for genuinely variable payloads; extract hot fields into typed columns.
  • Add descriptions to tables and columns; they help people, Knowledge Catalog and Gemini.
  • Declare primary and foreign keys (NOT ENFORCED); the optimiser uses them for join optimisations.

§2.2.5Materialised views

Materialised views precompute aggregations and are refreshed automatically and incrementally. BigQuery can rewrite queries against base tables to use a materialised view automatically. Use them for repeated dashboard aggregations over large tables.

§2.2.6Search indexes and vector indexes

  • Search indexes speed up SEARCH() and point lookups on text and high-cardinality columns, such as finding logs containing an ID.
  • Vector indexes speed up VECTOR_SEARCH over embeddings.

§2.2.7BI Engine

BI Engine is an in-memory acceleration service reserved in gigabytes per project. It speeds up dashboard queries from Looker, Looker Studio and other BI tools with sub-second responses for eligible queries.

§2.2.8A layered dataset layout

Dataset Contents

staging Cleaned and typed, often views or short-lived tables
core Conformed entities and history
marts_<domain> Business-ready tables for BI and analysis
sandbox_<team> Temporary work with table expiration

§2.2.9What good looks like

  • Large fact tables partitioned by date, clustered by common filters, with partition filters required.
  • Nested and repeated fields for data read together.
  • Descriptions and declared keys.
  • Materialised views or BI Engine for heavy dashboards.

§2.2.10Red flags

  • A 5 TB event table without partitioning.
  • Hourly partitioning on a table queried by month, hitting partition limits.
  • Money stored as FLOAT64.
  • Dashboards joining ten normalised tables on every refresh.

§3.3.1Time travel

BigQuery keeps changed and deleted data for a time travel window of 2 to 7 days (7 by default), set per dataset:

SELECT * FROM sales.orders FOR SYSTEM_TIME AS OF TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 2 HOUR);

CREATE OR REPLACE TABLE sales.orders AS
SELECT * FROM sales.orders FOR SYSTEM_TIME AS OF '2026-09-16 08:00:00+01';

Deleted tables can be restored within the window using a snapshot decorator with the bq cp command.

§3.3.2Fail-safe

After time travel, data enters a 7-day fail-safe period. You can't query it yourself; recovery requires Google Cloud Support. It is a last resort, not a backup plan. With physical storage billing, time travel and fail-safe bytes are charged; with logical billing, they're included.

§3.3.3Table snapshots and clones

Feature What it is Cost
Table snapshot Read-only, point-in-time copy kept as long as you want Stores only bytes that differ from the base table
Table clone Writable copy Stores only changed bytes
Table copy Full independent copy Full storage 
CREATE SNAPSHOT TABLE backups.orders_20260916
CLONE sales.orders
OPTIONS (expiration_timestamp = TIMESTAMP_ADD(CURRENT_TIMESTAMP(), INTERVAL 90 DAY));

CREATE TABLE dev.orders_clone CLONE sales.orders;

Schedule snapshots of critical tables before risky changes and at month-end for audit points.

§3.3.4Replication and disaster recovery

Option What it provides Edition
Multi-region datasets (US, EU) Data stored redundantly across regions in a geography; protection against zonal and some regional failures Any
Cross-region dataset replication Read-only replica of a dataset in another region, promotable to primary Any edition, with replication costs
Managed disaster recovery Replication plus failover of compute reservations to a secondary region, with a single failover action Enterprise Plus

Managed disaster recovery handles both data and slot capacity, so after failover, queries run in the secondary region with reserved capacity. Test failover, and check how clients, scheduled queries and pipelines reconnect.

§3.3.5Independent backups

Replication copies mistakes and malicious deletes too. The UniSuper incident in 2024, covered in the scenarios, is a reminder: an entire private cloud subscription was deleted in both regions by a provider-side configuration error, and recovery depended on backups held with another provider.

For critical data, consider:

  • Periodic exports of key tables to Cloud Storage buckets in a separate project, with Bucket Lock retention policies.
  • Copies in a separate organisation or another cloud for the most critical records.
  • Restricted, separate administrators for backup projects.

§3.3.6A recovery plan

Scenario Response
Bad UPDATE in the last few hours Time travel restore
Table dropped yesterday Restore within the time travel window
Logic bug discovered weeks later Restore from snapshot, replay pipelines from raw data
Regional outage Managed DR failover or promote replica
Account-level catastrophe or malicious deletion Independent backups in a separate project or provider

§3.3.7What good looks like

  • Time travel windows set per dataset; snapshots for critical tables.
  • Replication or managed DR matched to recovery objectives.
  • Independent, immutable backups for the most important data.
  • Restores and failovers tested.

§3.3.8Red flags

  • Fail-safe treated as the backup plan.
  • Replicas but no one knows how to promote them.
  • Backups in the same project, deletable by the same administrators.
  • Time travel reduced to 2 days everywhere to save on physical storage costs.

§7.1.2Column-level security with policy tags

Policy tags in taxonomies control access to columns:

  1. Create a taxonomy such as Sensitivity with tags High (National insurance number, Bank account) and Medium (Email, Phone).
  2. Attach policy tags to BigQuery columns.
  3. Grant datacatalog.categoryFineGrainedReader on specific tags to groups allowed to read those columns.
  4. Enforce access control on the taxonomy.

Users without permission get an error when selecting protected columns, unless masking is configured.

§7.1.3Dynamic data masking

Data masking returns masked values instead of errors, configured with data policies on policy tags:

Masking rule Result
SHA-256 hash Consistent hashed value, still joinable
Nullify NULL
Default masking value Type-appropriate default
Email mask, first or last four characters Partially visible values
Custom masking routine Your own SQL UDF

Grant bigquerydatapolicy.maskedReader for masked access and fine-grained reader for full access.

§7.1.4Row-level security

CREATE ROW ACCESS POLICY uk_sales_only
ON marts_sales.orders
GRANT TO ('group:sales-uk@acme.com')
FILTER USING (country = 'GB');

CREATE ROW ACCESS POLICY global_sales
ON marts_sales.orders
GRANT TO ('group:sales-global@acme.com')
FILTER USING (TRUE);

Once a table has any row access policy, users not covered by one see no rows.

§7.1.5Authorised views, datasets and routines

  • Authorised datasets authorise every view in a dataset at once.
  • Authorised routines do the same for table functions and UDFs.

§7.1.6Sensitive Data Protection

  • De-identification masks, tokenises or pseudonymises data in pipelines, including format-preserving encryption.
  • Discovery results can tag data automatically in Knowledge Catalog and feed Security Command Center.

§9.1.3Analysing BigQuery usage

  user_email,
  project_id,
  COUNT(*) AS queries,
  SUM(total_bytes_billed) / POW(1024, 4) AS tib_billed,
  SUM(total_slot_ms) / 1000 / 3600 AS slot_hours
FROM `region-europe-west2`.INFORMATION_SCHEMA.JOBS_BY_ORGANIZATION
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
  AND job_type = 'QUERY'
GROUP BY user_email, project_id

LIMIT 25;

§S1.2What they found

Change Detail

  • Freshness expectations. A marketing dashboard needed data within a minute. They moved that model to a materialised view on the raw table instead of a 15-minute Dataform schedule.
  • Schema evolution. Adding fields to topic schemas needed coordination with table schema updates, which they automated in CI.

§S1.6Lessons

  • Don't use a processing engine for copying. Managed subscriptions exist for that.
  • Keep stream processing for stream processing problems: windows, joins, stateful logic.
  • Enforce schemas at publish time.
  • Match freshness to need, per table.

§S4.1Snapshot

Real incident. Summarised from UniSuper and Google Cloud public statements and press reporting. Details are simplified; check primary sources before quoting.

Item Detail
Organisation UniSuper, an Australian superannuation fund with over 620,000 members
Service Google Cloud VMware Engine (GCVE) private cloud
Date Deletion on 2 May 2024; services restored progressively over about two weeks
Cause Google operators left a parameter blank during initial provisioning, which defaulted the private cloud to a fixed one-year term with automatic deletion
Impact Private cloud deleted across both geographies; members unable to access accounts during the outage
Recovery Backups held with an additional service provider
Verdict Mixed: a severe outage caused by the provider, limited by good backup practice

§S4.2What happened

  1. When UniSuper's GCVE private cloud was originally deployed, a parameter was left blank by Google operators using an internal tool.
  2. The blank parameter caused the system to treat the private cloud as having a fixed term, with automatic deletion at the end.
  3. After one year, the private cloud was deleted. No customer notification was sent, because the deletion was a consequence of the configuration rather than a customer action.
  4. UniSuper had duplicated its environment across two geographies for resilience. The subscription-level deletion removed both.
  5. UniSuper held backups with an additional service provider, which allowed restoration of systems and data with limited loss.

Google Cloud and UniSuper issued joint statements, and Google published details of the incident and the remediation, including removing the internal tool behaviour and adding safeguards.

§S4.3Why it's in a data platform guide

The incident wasn't about BigQuery, but the lesson applies to any cloud data platform:

Assumption Reality
Multi-region replication protects against loss Replication protects against infrastructure failure, not deletion at the account or subscription level
The provider won't delete my resources Provider-side errors are rare but possible
Backups in the same cloud are enough Backups subject to the same control plane and accounts share failure modes

§S4.4What went well

  • Independent backups outside the affected platform made recovery possible.
  • Transparent communication from both parties, including joint statements from senior leaders.

§S4.5What went wrong

  • A single configuration error propagated to a catastrophic deletion.
  • Multi-geography design didn't protect against a subscription-level action.
  • Recovery took about two weeks, reflecting how complex rebuilding an environment from backups is.

§S4.6Lessons for data platforms

  • Keep at least one copy of critical data outside the blast radius of your main accounts: a separate organisation, project with separate administrators, or another provider.
  • Use immutable retention such as Cloud Storage Bucket Lock for backup copies.
  • Test full restores, not just file recovery. Rebuild time matters as much as data.
  • Treat account and subscription-level deletion as a disaster scenario in DR planning.
