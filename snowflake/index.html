How Snowflake Works

§1.1.1Three layers

Snowflake runs on AWS, Azure or Google Cloud, but hides the infrastructure. Its architecture has three independent layers:

Layer What it does You pay for
Storage Stores tables as compressed, columnar micro-partitions in cloud object storage Terabytes stored per month
Compute Virtual warehouses execute queries and loads; serverless features run on Snowflake-managed compute Credits per second of running compute
Cloud services Authentication, metadata, query optimisation, access control, transactions Only when it exceeds 10% of daily warehouse usage

The defining idea: storage and compute are separate. Many warehouses can query the same data at the same time without copying it or competing for resources. A finance warehouse running month-end reports doesn't slow down the data science warehouse.

§1.1.2Micro-partitions

Snowflake stores each table as many micro-partitions, each holding roughly 50 to 500 MB of uncompressed data, organised by column.

  • You never create or manage them. Snowflake does it automatically on load.
  • For each micro-partition, Snowflake keeps metadata: the minimum and maximum value of each column, distinct counts and more.
  • At query time, it uses that metadata to prune micro-partitions that can't contain matching rows, so it reads only what it needs.

Data arrives in the order you load it. If you load orders day by day, micro-partitions are naturally grouped by date, and date filters prune well. The performance module covers what to do when natural ordering isn't enough.

§1.1.3No indexes, no vacuuming, no statistics jobs

Traditional database chores mostly disappear:

  • No indexes to design on standard tables (search optimisation and hybrid tables are specific exceptions).
  • No vacuum or compaction jobs; storage is managed.
  • No statistics updates; metadata is maintained on write.
  • No distribution keys; the platform decides.

What remains your job: data modelling, query design, warehouse sizing, clustering for very large tables, and cost control.

§1.1.4Cloud services layer

The cloud services layer is the brain:

Function Consequence
Query compilation and optimisation Metadata-only queries, such as COUNT(*) on a table, can return without a warehouse
Metadata and transaction management ACID transactions and consistent reads
Security and access control Every request authenticated and authorised centrally
Result cache Identical queries on unchanged data can return instantly for 24 hours

Heavy use of metadata-intensive operations, such as very frequent SHOW commands or huge numbers of tiny queries, can push cloud services usage above the 10% allowance and start costing credits.

§1.1.5Hybrid, Iceberg and other table types

Standard Snowflake tables are the default. Other types exist for specific needs:

Table type Use
Transient and temporary Staging and intermediate data without Fail-safe costs
Apache Iceberg tables Open-format tables other engines can read and write
Hybrid tables Low-latency point reads and writes with row storage and indexes
External tables Query files in external storage in place
Dynamic tables Declarative, automatically refreshed transformation results

Later modules cover each.

§1.1.6What good looks like

  • Separate warehouses for separate workloads, all reading the same data.
  • Data loaded in an order that matches common filters.
  • Transient tables for staging and scratch data.
  • An understanding that performance problems are usually about pruning and warehouse size, not indexes.

§1.1.7Red flags

  • One enormous warehouse shared by loading, BI and data science.
  • Teams recreating traditional index and maintenance habits that Snowflake doesn't need.
  • Hundreds of thousands of tiny metadata queries from a badly written tool.
  • Staging tables created as permanent tables, carrying Fail-safe storage.

§1.2.1Organisations and accounts

Level What it is
Organisation Your company's container for accounts, billing and organisation-wide usage views
Account A Snowflake deployment in one cloud and region, with its own users, roles, warehouses and databases
Database, schema, object Tables, views, stages, functions and more inside an account

An account URL looks like https://<orgname>-<account_name>.snowflakecomputing.com. Use the organisation-based account identifier rather than legacy locator URLs.

The ORGADMIN role, or the organisation account in newer setups, manages accounts and can see usage across them.

§1.2.2How many accounts

Pattern When
One account, separate databases for dev, test and prod Small teams; simplest
Separate accounts per environment Stronger isolation of production; different security settings; clearer cost
Accounts per region or cloud Data residency, latency, or proximity to other systems
Accounts per business unit Large organisations with separate ownership and billing

Replication and sharing work across accounts, so multi-account designs don't isolate data completely. They do isolate users, roles and mistakes.

§1.2.3Editions

Edition Adds
Standard Core platform, Time Travel up to 1 day, encryption, basic security
Enterprise Multi-cluster warehouses, Time Travel up to 90 days, materialised views, column masking and row access policies, search optimisation, access history
Business Critical Private connectivity (PrivateLink), customer-managed keys with Tri-Secret Secure, support for regulated data such as HIPAA and PCI DSS, account failover
Virtual Private Snowflake (VPS) A completely separate Snowflake environment for the most sensitive organisations

Many governance features used in this guide need Enterprise or above. Regulated organisations usually need Business Critical for private connectivity and failover.

§1.2.4Credits

Compute is billed in credits. The price of a credit depends on edition, cloud, region and contract.

Consumer Billing
Virtual warehouses Credits per hour by size, billed per second with a 60-second minimum each time a warehouse starts
Serverless features (Snowpipe, serverless tasks, automatic clustering, search optimisation, dynamic table refreshes on serverless compute) Credits for compute used
Snowpipe Streaming high-performance architecture Credits per gigabyte ingested
Cloud services Only above 10% of daily warehouse credits
Cortex AI functions Credits or tokens per model and function
Snowpark Container Services Credits per compute pool node hour

§1.2.5Storage and data transfer

  • Storage is billed per terabyte per month, averaged daily, including Time Travel and Fail-safe data.
  • Data transfer out of the region or cloud, including replication and some external function calls, is charged.

§1.2.6Capacity versus on-demand

  • On-demand accounts pay list price monthly in arrears.
  • Capacity contracts commit to spend in advance for discounted credits. Unused capacity can be lost at the end of the term, so commit to realistic forecasts.

§1.2.7What good looks like

  • Production in its own account, or at least strict role separation if sharing one.
  • The edition chosen from security and continuity requirements, not only price.
  • Region chosen near data sources and consumers, with residency confirmed.
  • Organisation-level usage views reviewed monthly.

§1.2.8Red flags

  • A Standard edition account holding regulated data that needs PrivateLink.
  • Production and experiments in one account with the same administrators.
  • A three-year capacity contract signed from a guess.
  • Data replicated across regions nightly without anyone knowing the transfer cost.

§1.3.1Sizes and credits

Size Credits per hour (standard warehouse)
X-Small 1
Small 2
Medium 4
Large 8
X-Large 16
2X-Large to 6X-Large 32 to 512

Each size up doubles compute and credits per hour. For work that parallelises well, a query that takes 8 minutes on Medium may take about 4 minutes on Large, costing roughly the same credits while finishing sooner. When doubling no longer halves runtime, you've gone too big.

§1.3.2Auto-suspend and auto-resume

CREATE WAREHOUSE wh_transform
  WAREHOUSE_SIZE = 'MEDIUM'
  AUTO_SUSPEND = 60
  AUTO_RESUME = TRUE
  INITIALLY_SUSPENDED = TRUE;
  • Auto-suspend stops billing after a period of inactivity. The default for new warehouses is 600 seconds; 60 seconds is common for most workloads.
  • Auto-resume starts the warehouse when a query arrives.
  • Each resume bills at least 60 seconds, so extremely short suspends on warehouses that receive a query every minute can cost more than a slightly longer suspend.
  • Suspending clears the warehouse's local disk cache, which can slow the first queries after resume.

§1.3.3Scaling up versus scaling out

Problem Fix
Individual queries are slow because they process lots of data Scale up: larger warehouse size
Queries wait in a queue because many users run at once Scale out: multi-cluster warehouse

Multi-cluster warehouses (Enterprise edition and above) add clusters of the same size when queries queue, and remove them when load falls:

ALTER WAREHOUSE wh_bi SET
  MIN_CLUSTER_COUNT = 1
  MAX_CLUSTER_COUNT = 4
  SCALING_POLICY = 'STANDARD';  -- or 'ECONOMY' to favour cost over queueing

§1.3.4Warehouse types

Type Use
Standard (Gen1) General purpose
Gen2 standard warehouses Upgraded hardware and engine improvements for faster queries, especially DML and larger analytic workloads; generally available on AWS, Azure and Google Cloud
Snowpark-optimised Much more memory per node for machine learning training and memory-hungry Snowpark code
Adaptive warehouses (Adaptive Compute) Generally available since June 2026: Snowflake sizes compute per query automatically instead of fixed T-shirt sizes

Gen2 warehouses cost more credits per hour but often finish work sooner. Test representative workloads and compare total credits, not hourly price.

Adaptive Compute removes much of the sizing guesswork. It is worth evaluating for new workloads, particularly mixed or unpredictable ones, while keeping fixed warehouses where you have well-understood, tuned jobs.

§1.3.5A warehouse layout

Warehouse Size and settings Used by
WH_LOAD Small, auto-suspend 60 s Ingestion and COPY commands
WH_TRANSFORM Medium or Large, auto-suspend 60 s dbt, tasks, transformations
WH_BI Small, multi-cluster 1–4 Dashboards and analysts
WH_DATA_SCIENCE Snowpark-optimised when needed Notebooks and ML
WH_ADHOC_XS X-Small Occasional exploration

Grant USAGE on each warehouse only to the roles that should use it. Separate warehouses make cost allocation and troubleshooting straightforward.

§1.3.6Timeouts and guardrails

ALTER WAREHOUSE wh_bi SET
  STATEMENT_TIMEOUT_IN_SECONDS = 1800
  STATEMENT_QUEUED_TIMEOUT_IN_SECONDS = 600;
  • Statement timeouts stop runaway queries.
  • Resource monitors, covered in the cost module, cap credits per warehouse.

§1.3.7What good looks like

  • Warehouses separated by workload, each with auto-suspend and timeouts.
  • Sizes chosen by testing, with scale-out for concurrency rather than bigger sizes.
  • Gen2 or Adaptive Compute evaluated with real workloads.
  • Resource monitors on every warehouse.

§1.3.8Red flags

  • An X-Large warehouse with auto-suspend at 3,600 seconds used by one analyst.
  • A single warehouse for loading, transformation and BI.
  • Slow dashboards "fixed" by making the warehouse larger when the real problem is queueing.
  • No statement timeouts, and a two-day query nobody noticed.

Stage Where files live Typical use

§2.1.2Storage integrations

A storage integration lets Snowflake access your cloud storage using a cloud identity instead of stored keys:

CREATE STORAGE INTEGRATION si_landing_s3
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/snowflake-landing-reader'

Then:

CREATE STAGE raw.landing_orders
  URL = 's3://acme-landing/orders/'
  STORAGE_INTEGRATION = si_landing_s3
  FILE_FORMAT = (TYPE = PARQUET);

On Azure the integration uses a Snowflake-created service principal granted a storage role; on Google Cloud, a Snowflake-managed service account. Never create stages with embedded access keys or SAS tokens in production.

§2.1.4COPY INTO

COPY INTO raw.orders

FILE_FORMAT = (TYPE = PARQUET)
MATCH_BY_COLUMN_NAME = CASE_INSENSITIVE
ON_ERROR = 'ABORT_STATEMENT';

Key behaviours:

  • Load metadata records which files were loaded for 64 days, so rerunning the same COPY skips files already loaded. That makes reruns safe. Don't override it with FORCE = TRUE unless you mean to duplicate.
  • ON_ERROR options: ABORT_STATEMENT, CONTINUE, SKIP_FILE. For production, abort or skip file, and alert.
  • VALIDATION_MODE = RETURN_ERRORS checks files without loading.
  • The COPY_HISTORY table function and LOAD_HISTORY views show what loaded and what failed.

§2.2.2Snowpipe Streaming: rows, not files

The high-performance architecture:

  • Throughput of up to several gigabytes per second per table.
  • Java and Python SDKs built on a shared Rust core, plus a REST API.
  • Server-side schema validation and in-flight transformations using COPY-style syntax in a pipe.
  • Throughput-based pricing per gigabyte ingested, instead of client connection time.
  • Generally available on AWS from September 2025, with other clouds following.

Use it for application events, IoT and CDC streams where files would be awkward.

§2.2.3Kafka

§2.2.4Openflow

  • Deployment either inside Snowflake on Snowpark Container Services, or bring your own cloud (BYOC) in your own AWS account, where data can stay in your network until it reaches Snowflake.
  • Both are generally available; second-generation deployments and runtimes are the current model, with new first-generation deployments retired in September 2026.

Openflow reduces the need for separate integration tools for many common sources.

§3.1.1Streams: change tracking

A stream records inserts, updates and deletes on a table since the stream was last consumed:

CREATE STREAM raw.orders_stream ON TABLE raw.orders;

Querying the stream returns changed rows plus metadata columns:

Column Meaning
METADATA$ACTION INSERT or DELETE
METADATA$ISUPDATE TRUE when an insert/delete pair represents an update
METADATA$ROW_ID Stable row identifier

A stream's offset advances only when it is used in a DML statement that commits. Reading it with a plain SELECT doesn't consume it.

Stream types:

  • Standard: inserts, updates and deletes.
  • Append-only: inserts only; cheaper for insert-only tables.
  • Insert-only streams on external and Iceberg tables.

Staleness#

A stream becomes stale if not consumed within the table's data retention period (extended up to 14 days where needed). A stale stream must be recreated, and changes may be lost. Monitor STALE_AFTER in SHOW STREAMS.

§3.1.2Tasks: scheduled work

CREATE TASK transform.merge_orders
  WAREHOUSE = wh_transform
  SCHEDULE = 'USING CRON */10 * * * * UTC'
  WHEN SYSTEM$STREAM_HAS_DATA('raw.orders_stream')
AS
MERGE INTO core.orders t
USING (
  SELECT * FROM raw.orders_stream
  WHERE METADATA$ACTION = 'INSERT'
) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.status = s.status, t.updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT (order_id, customer_id, status, updated_at)
  VALUES (s.order_id, s.customer_id, s.status, s.updated_at);

ALTER TASK transform.merge_orders RESUME;
  • The WHEN SYSTEM$STREAM_HAS_DATA condition skips runs when nothing changed, and doesn't start the warehouse.
  • Tasks are created suspended. Remember to resume them.

§3.1.3Serverless tasks

Omit WAREHOUSE and set USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE to run a serverless task. Snowflake sizes compute from history. Serverless tasks suit short, frequent jobs where keeping a warehouse awake would waste credits. You can set a target completion interval to guide sizing.

§3.1.4Task graphs

Tasks form directed acyclic graphs (DAGs): a root task on a schedule, child tasks with AFTER dependencies, and an optional finaliser task that always runs at the end, useful for clean-up and notifications.

CREATE TASK transform.build_dim_customer
  WAREHOUSE = wh_transform
  AFTER transform.merge_orders
AS CALL transform.sp_build_dim_customer();

Monitor with TASK_HISTORY, COMPLETE_TASK_GRAPHS and Snowsight's task graph view. Configure error notifications to send failures to a notification integration such as email, a cloud queue or a webhook.

§3.1.5Pitfalls

Pitfall Avoid by
Forgetting to resume tasks after deployment Deployment scripts that resume root tasks explicitly
Two tasks consuming the same stream One consumer per stream; create separate streams for separate consumers
Streams going stale after long outages Alerts on staleness; adequate retention
Non-idempotent logic MERGE on business keys; dedupe inside the source query
Deep task graphs with hidden SQL Keep logic in versioned procedures or dbt; tasks orchestrate

§3.1.6When to prefer dynamic tables

Streams and tasks give fine control. For most "keep this table up to date from those tables" needs, dynamic tables are simpler, covered next. Use streams and tasks when you need procedural logic, side effects, or precise control of each step.

§3.1.7What good looks like

  • Stream-triggered tasks that skip runs without changes.
  • Serverless tasks for short frequent jobs; warehouses for heavy ones.
  • Task graphs with finalisers and failure notifications.
  • Staleness and task failures monitored.

§3.1.8Red flags

  • A task running every minute on a Medium warehouse doing nothing most of the time.
  • Several consumers of one stream wondering why changes disappear.
  • Task graphs suspended after a failed deployment for a week.
  • Business logic pasted into task definitions with no version control.

§3.2.1Declarative transformations

A dynamic table is defined by a query. Snowflake keeps its results up to date automatically, within a freshness target you set:

CREATE DYNAMIC TABLE core.daily_sales
  TARGET_LAG = '15 minutes'
  WAREHOUSE = wh_transform
  REFRESH_MODE = AUTO
AS
SELECT
  o.order_date,
  c.region,
  SUM(o.net_amount) AS net_sales,
  COUNT(*)          AS orders
FROM core.orders o
JOIN core.customers c ON c.customer_id = o.customer_id
GROUP BY o.order_date, c.region;

You describe what the table should contain. Snowflake decides how and when to refresh it, including incrementally processing only changes where possible. No streams, tasks or MERGE statements to maintain.

§3.2.2Target lag

TARGET_LAG is the maximum acceptable staleness:

  • A specific time, such as '5 minutes' or '1 hour'.
  • DOWNSTREAM: refresh only as often as dynamic tables that depend on this one need.

Pipelines usually set a real lag on the final tables consumers use and DOWNSTREAM on intermediate tables, so Snowflake coordinates refreshes across the chain.

Shorter lag means more frequent refreshes and more credits. Match lag to the business need: executive dashboards rarely need one-minute freshness.

§3.2.3Refresh modes

Mode Behaviour
INCREMENTAL Processes only changed data; efficient for large tables with small changes
FULL Recomputes the whole result
AUTO Snowflake chooses at creation based on the query

Some query constructs prevent incremental refresh. Check SHOW DYNAMIC TABLES for the chosen mode, and simplify queries if a large table ends up on full refresh unexpectedly.

§3.2.4Building pipelines

RAW.ORDERS ──> CORE.ORDERS_CLEAN (DOWNSTREAM) ──> MART.DAILY_SALES (15 minutes)
RAW.CUSTOMERS ─> CORE.CUSTOMERS_CURRENT (DOWNSTREAM) ─┘

Snowsight shows the graph of dynamic tables with refresh history, lag and errors. Useful views and functions:

  • DYNAMIC_TABLE_REFRESH_HISTORY for refresh outcomes and durations.
  • DYNAMIC_TABLE_GRAPH_HISTORY for the pipeline graph.

You can suspend and resume dynamic tables, and trigger a manual refresh.

§3.2.5Dynamic tables, tasks, or dbt?

Need Choose
Keep derived tables fresh with SQL Dynamic tables
Procedural steps, API calls, side effects Streams, tasks and stored procedures
Software engineering workflow with tests, docs and modular models dbt, which can also create dynamic tables as a materialisation
Complex Python transformations Snowpark in procedures or notebooks

These combine well: dbt models materialised as dynamic tables give dbt's development workflow with Snowflake managing freshness.

§3.2.6Cost habits

  • Right-size the warehouse used for refreshes and use a dedicated one for visibility.
  • Prefer incremental refresh for large tables.
  • Avoid very short lags on expensive tables unless justified.
  • Watch for tables refreshing on schedule while nothing upstream has changed; check whether sources change constantly for no business reason.

§3.2.7What good looks like

  • Dynamic tables for most SQL transformation chains.
  • Lag set on consumer-facing tables, DOWNSTREAM on intermediates.
  • Refresh mode checked for large tables.
  • Refresh failures and lag misses alerted.

§3.2.8Red flags

  • Every dynamic table set to a one-minute lag.
  • A 2 billion-row table unexpectedly on full refresh every 10 minutes.
  • Hand-built stream and task chains for simple aggregations.
  • No monitoring of refresh errors.

§4.1.1Pruning is the first lever

Most Snowflake performance comes from reading fewer micro-partitions. A query filtering WHERE order_date = '2026-09-01' can skip every micro-partition whose date range excludes that day.

Pruning works well when:

  • Filters are on columns whose values are grouped together in micro-partitions, such as a load date.
  • Filters are sargable: WHERE order_date >= '2026-09-01' prunes; WHERE TO_CHAR(order_date, 'YYYY-MM') = '2026-09' usually doesn't.

The query profile shows partitions scanned against partitions total. Scanning 95% of partitions for a one-day filter means pruning isn't working.

§4.1.2Clustering keys

For very large tables (typically hundreds of gigabytes to terabytes) where natural load order doesn't match common filters, define a clustering key:

ALTER TABLE core.events CLUSTER BY (event_date, account_id);

Automatic clustering then reorganises micro-partitions in the background using serverless credits.

  • Check clustering quality with SYSTEM$CLUSTERING_INFORMATION('core.events').
  • Choose low to moderate cardinality leading columns that match filters, such as date before ID.
  • Don't cluster small tables or tables with random-access patterns. The reclustering credits won't pay back.
  • Tables with frequent updates across all partitions can be expensive to keep clustered.

§4.1.3Search optimisation service

The search optimisation service (Enterprise edition and above) builds a persistent search access path to speed up selective lookups:

  • Equality and IN filters on high-cardinality columns, such as finding one customer ID in billions of rows.
  • Substring and regular expression searches.
  • Searches inside semi-structured VARIANT data.
  • Geospatial functions.
ALTER TABLE core.events ADD SEARCH OPTIMIZATION ON EQUALITY(customer_id), SUBSTRING(url);

It adds storage and maintenance credits. Enable it for specific columns with clear, repeated lookup workloads.

§4.1.4Query acceleration service

The query acceleration service offloads parts of eligible queries, such as large scans with selective filters, to additional serverless compute, and helps warehouses handle occasional outlier queries without being upsized:

ALTER WAREHOUSE wh_bi SET ENABLE_QUERY_ACCELERATION = TRUE QUERY_ACCELERATION_MAX_SCALE_FACTOR = 8;

SYSTEM$ESTIMATE_QUERY_ACCELERATION shows whether a query would benefit.

§4.1.5The three caches

Cache What it holds Lifetime
Result cache Results of previous queries 24 hours, extendable with reuse up to 31 days; invalidated when data changes
Warehouse local disk cache Micro-partition data read recently by that warehouse Until the warehouse suspends or the data is evicted
Metadata cache Table statistics in the services layer Always

Implications:

  • Dashboards that repeat identical queries on unchanged data hit the result cache for free.
  • Non-deterministic functions such as CURRENT_TIMESTAMP() in a query prevent result cache reuse.
  • Warehouses that suspend very aggressively lose their disk cache.

§4.1.6Materialised views

Materialised views (Enterprise edition and above) store precomputed results for a single-table query and keep them current with serverless maintenance. They suit expensive, frequently repeated aggregations or projections on one large table. For multi-table transformations, prefer dynamic tables.

§4.1.7Query design habits

  • Select only needed columns; columnar storage rewards it.
  • Filter early and on raw columns.
  • Avoid exploding joins; check join keys for duplicates.
  • Prefer UNION ALL over UNION when duplicates are impossible.
  • Use QUALIFY with window functions instead of self-joins for "latest row per key".
  • Avoid ORDER BY on huge results unless needed.

§4.1.8What good looks like

  • Queries that prune effectively on common filters.
  • Clustering only on very large tables with measured benefit.
  • Search optimisation for specific high-selectivity lookup patterns.
  • Dashboards designed to benefit from result caching.

§4.1.9Red flags

  • A clustering key on a 5 GB table burning credits every day.
  • Functions wrapped around filter columns defeating pruning.
  • Search optimisation enabled on every column "just in case".
  • Upsizing warehouses before looking at partitions scanned.

§4.2.1Finding what to tune

SELECT
  query_parameterized_hash,
  ANY_VALUE(LEFT(query_text, 200)) AS sample_text,
  warehouse_name,
  COUNT(*)                          AS runs,
  SUM(total_elapsed_time) / 1000    AS total_seconds,
  AVG(bytes_scanned) / POWER(1024, 3) AS avg_gb_scanned
FROM snowflake.account_usage.query_history
WHERE start_time > DATEADD(day, -7, CURRENT_TIMESTAMP())
  AND execution_status = 'SUCCESS'
GROUP BY query_parameterized_hash, warehouse_name
ORDER BY total_seconds DESC
LIMIT 20;

Grouping by query_parameterized_hash finds the same query run with different literal values, which is often where the cost is. QUERY_ATTRIBUTION_HISTORY attributes credits to individual queries.

§4.2.2The query profile

Open a query in Snowsight and look at the query profile: a tree of operators with time and data volumes.

Signal What it means Typical fix
Partitions scanned close to partitions total Poor pruning Better filters; clustering for very large tables
Bytes spilled to local or remote storage The warehouse ran out of memory Larger warehouse, fewer columns, reduce data before joins
Join output far larger than inputs Exploding join from duplicate keys Fix join keys; deduplicate first
Most time in one TableScan Reading too much Select fewer columns; filter; prune
Queued time Warehouse overloaded Multi-cluster; separate workloads
Compilation time high Very complex SQL or many objects Simplify views; reduce nesting

Remote spilling is especially slow. It is one of the few signals where a larger warehouse is the correct fix.

§4.2.3Tuning a warehouse

Use data over a week or two:

  • Queueing (WAREHOUSE_LOAD_HISTORY): if queries often queue, add clusters rather than size.
  • Utilisation: a large warehouse running mostly idle between tiny queries should be smaller.
  • Spilling: frequent spilling on key workloads suggests a larger size for that warehouse only.
  • Auto-suspend patterns: many short resume cycles each billing 60 seconds may justify a slightly longer suspend.

Test changes with the same queries and compare total credits and runtime, not runtime alone.

§4.2.4Workload patterns

Workload Tuning approach
BI dashboards Small multi-cluster warehouse; result caching; aggregated tables or dynamic tables for heavy visuals
ELT transformations Right-sized warehouse per pipeline; incremental processing; avoid rebuilding everything
Data science Snowpark-optimised warehouses only when memory-bound
Ad hoc exploration Small warehouse with statement timeouts
Heavy one-off backfills Temporarily larger warehouse, then scale back

  • Query tags set by applications and dbt (ALTER SESSION SET QUERY_TAG = 'dbt:mart_sales') to group cost and performance by pipeline.
  • Third-party optimisation tools for large estates.

§4.2.6What good looks like

  • A weekly top-20 expensive query review with owners.
  • Query tags on all automated workloads.
  • Warehouse changes based on queueing, spilling and utilisation data.
  • Fixes to SQL and data layout before larger warehouses.

§4.2.7Red flags

  • "Snowflake is slow" with no one looking at query profiles.
  • The same inefficient dashboard query running 40,000 times a day.
  • Remote spilling on the nightly job for months.
  • No query tags, so nobody knows which pipeline is expensive.

§5.1.1Time Travel

Time Travel keeps historical versions of data for a retention period, so you can query or restore the past:

-- As of a timestamp
SELECT * FROM core.orders AT (TIMESTAMP => '2026-09-16 08:00:00'::timestamp_ltz);

-- As it was before a specific statement
SELECT * FROM core.orders BEFORE (STATEMENT => '01b2c3d4-0000-1111-0000-123456789abc');

-- Restore dropped objects
UNDROP TABLE core.orders;
UNDROP SCHEMA core;
UNDROP DATABASE analytics;
Edition Maximum retention
Standard 1 day
Enterprise and above Up to 90 days for permanent objects

Set it per account, database, schema or table with DATA_RETENTION_TIME_IN_DAYS. Transient and temporary tables allow at most 1 day.

§5.1.2Fail-safe

After Time Travel ends, permanent tables enter Fail-safe for 7 more days.

  • You cannot query or restore Fail-safe data yourself.
  • Only Snowflake Support can recover it, for disaster scenarios, on a best-effort basis.
  • Transient and temporary tables have no Fail-safe.

Fail-safe is not a backup strategy. It is a last-resort safety net.

§5.1.3Storage cost of history

Time Travel and Fail-safe store changed and deleted micro-partitions. Tables with heavy updates or full reloads can carry several times their active size in history.

  • Use transient tables for staging and rebuildable intermediate data to avoid Fail-safe costs.
  • Set longer retention on critical curated tables, shorter on high-churn tables.
  • Check TABLE_STORAGE_METRICS for active, Time Travel and Fail-safe bytes.

§5.1.4Zero-copy cloning

A clone creates a copy of a table, schema or database instantly, sharing the original micro-partitions:

CREATE DATABASE analytics_test CLONE analytics;
CREATE TABLE core.orders_before_fix CLONE core.orders AT (OFFSET => -3600);
  • No data is copied at creation, so it costs no extra storage until either side changes.
  • Changes in the clone or original create new micro-partitions only for changed data.
  • Clones can use Time Travel to copy a past state.

Uses:

  • Test and development environments from production data in seconds, with masking policies applied as needed.
  • Pre-change safety copies before risky updates.
  • Point-in-time snapshots for audits and month-end.

Privileges on child objects are not inherited by default when cloning databases or schemas, except where you specify COPY GRANTS for tables. Check access on clones, and remember clones of production contain production data.

§5.1.5Backups

Snowflake now offers backups features for immutable, point-in-time snapshots with retention policies, useful where compliance requires copies protected from deletion even by administrators. Combine with replication to another region or account for disaster recovery, covered next.

§5.1.6What good looks like

  • Retention periods set deliberately by table importance.
  • Transient tables for staging and scratch work.
  • Clones used for fast test environments with masking applied.
  • A recovery process practised using Time Travel and clones.

§5.1.7Red flags

  • Treating Fail-safe as the backup plan.
  • Staging tables truncated and reloaded hourly as permanent tables with 90-day retention.
  • Developers querying unmasked production clones.
  • No one knows how to restore a table dropped by mistake.

§5.2.1Replication

Snowflake replicates objects from a source account to target accounts in other regions or clouds within the same organisation.

Group type Contents Edition
Replication group Read-only replicas of selected objects Standard and above for databases; more object types on higher editions
Failover group Replicas that can be promoted to become the primary Business Critical and above

Objects that can be replicated include databases, shares, users, roles and grants, warehouses, integrations, network policies and more, depending on edition and type.

-- On the source account
CREATE FAILOVER GROUP fg_analytics
  OBJECT_TYPES = DATABASES, ROLES, USERS, WAREHOUSES, INTEGRATIONS, NETWORK POLICIES
  ALLOWED_DATABASES = analytics, raw
  ALLOWED_ACCOUNTS = acme.analytics_dr_eu
  REPLICATION_SCHEDULE = '10 MINUTE';

-- On the target account
CREATE FAILOVER GROUP fg_analytics AS REPLICA OF acme.analytics_prod_uk.fg_analytics;

Replication is incremental. The replication schedule sets your recovery point: with a 10-minute schedule, you could lose up to about 10 minutes of changes.

§5.2.2Failover

In a regional outage, promote the secondary:

ALTER FAILOVER GROUP fg_analytics PRIMARY;  -- run on the target account

Afterwards, the old primary becomes secondary when it's reachable again, and you can fail back later.

§5.2.3Client Redirect

Applications and BI tools connect to a hostname. Client Redirect uses a connection object with a stable URL that you point at whichever account is primary:

CREATE CONNECTION analytics_conn;
ALTER CONNECTION analytics_conn ENABLE FAILOVER TO ACCOUNTS acme.analytics_dr_eu;

Clients use acme-analytics_conn.snowflakecomputing.com. During failover, redirect the connection, and clients reconnect to the new primary without configuration changes.

Item Consider
Warehouses and resource monitors Replicated, or created by infrastructure as code in the DR account
Integrations and stages Cloud storage and identities available in the DR region
Network policies and private connectivity PrivateLink endpoints configured for the DR account
Pipelines and tasks Tasks replicate suspended; decide what resumes in DR and prevent double-running
Ingestion sources Snowpipe notifications, connectors and partner tools pointed at DR
Identity provider SSO and SCIM configured for the DR account

§5.2.5Designing the plan

  1. Agree RTO and RPO per dataset. Not everything needs 10-minute replication.
  2. Choose failover groups for critical data and read replicas for less critical.
  3. Use Client Redirect for applications and BI.
  4. Keep the DR account's non-replicated configuration in infrastructure as code.
  5. Test failover at least yearly, including ingestion and tasks.

§5.2.6Other continuity tools

  • Time Travel and clones for logical errors such as bad deletes.
  • Backups for immutable point-in-time copies.
  • Secure data sharing consumers may also need their providers to replicate listings to other regions.

§5.2.7What good looks like

  • Failover groups for critical data with replication schedules matching RPO.
  • Client Redirect used by all critical clients.
  • DR configuration defined as code and tested.
  • A runbook including tasks, pipelines and identity.

§5.2.8Red flags

  • "We replicate the database" with no plan for users, roles, integrations or tasks.
  • Applications hard-coded to the primary account URL.
  • Failover never tested.
  • Every database replicated every minute regardless of business need.

§5.3.1Sharing without copying

Secure data sharing lets a provider account grant another Snowflake account live, read-only access to selected data. No files are exported and no data is copied: the consumer queries the provider's micro-partitions using the consumer's own compute.

CREATE SHARE sh_supplier_sales;
GRANT USAGE ON DATABASE analytics TO SHARE sh_supplier_sales;
GRANT USAGE ON SCHEMA analytics.shared TO SHARE sh_supplier_sales;
GRANT SELECT ON VIEW analytics.shared.v_supplier_sales TO SHARE sh_supplier_sales;
ALTER SHARE sh_supplier_sales ADD ACCOUNTS = acme_partner.supplier_account;

Benefits:

  • Always current: consumers see changes immediately.
  • No pipelines or file transfers to maintain.
  • Revocable instantly.
  • Consumers pay for their own queries.

§5.3.2Sharing safely

  • Share secure views, not raw tables, so you control columns and rows.
  • Filter by consumer with CURRENT_ACCOUNT() in a mapping table for multi-tenant shares:
CREATE SECURE VIEW analytics.shared.v_supplier_sales AS
SELECT s.*
FROM analytics.core.sales s
JOIN analytics.shared.supplier_accounts m
  ON m.supplier_id = s.supplier_id
 AND m.snowflake_account = CURRENT_ACCOUNT();
  • Apply masking and row access policies as with internal users.
  • Review shares and their consumers regularly.

§5.3.3Listings and the Marketplace

Listings package shares with descriptions, sample queries, terms and usage metrics:

Listing type Audience
Private listing Specific accounts or organisations, such as partners and customers
Public listing on Snowflake Marketplace Any Snowflake customer, free or paid
Internal Marketplace Teams inside your organisation discovering data products

Cross-Cloud Auto-Fulfillment replicates listing data to consumers in other regions and clouds automatically, so you don't manage replication per consumer.

Listings can also include Native Apps, shipping code and data together.

§5.3.4Reader accounts

A consumer without Snowflake can use a reader account created and paid for by the provider. It's a limited account for querying shared data. Keep usage controlled with resource monitors, since the provider pays.

§5.3.5Data clean rooms

Snowflake Data Clean Rooms let two or more parties analyse combined data without revealing raw records to each other. Typical use: an advertiser and a publisher measuring overlap and campaign performance without exchanging customer lists.

  • Each party controls which analyses the other may run.
  • Results can be restricted to aggregates above minimum group sizes.
  • Built on sharing, secure functions and policies, with a web application for business users.

§5.3.6Sharing inside the organisation

Sharing is also useful internally across accounts: a central data team shares certified data products to business unit accounts, each paying for its own compute, with the internal Marketplace for discovery.

§5.3.7What good looks like

  • Shares built on secure views with per-consumer filtering.
  • Listings with documentation and usage monitoring for external consumers.
  • Clean rooms for sensitive collaboration instead of file exchanges.
  • Regular review of who has access to which shares.

§5.3.8Red flags

  • CSV files emailed to partners every Monday while both sides use Snowflake.
  • Whole databases shared because it was quicker than building views.
  • A reader account with no resource monitor running up the provider's bill.
  • Customer lists exchanged with an advertising partner as files.

§6.1.1Why Iceberg

Apache Iceberg is an open table format: Parquet data files plus metadata that tracks snapshots, schema and partitions. Many engines understand it, including Spark, Trino, Flink, Databricks, Fabric through virtualisation, BigQuery and Snowflake.

Storing data in Iceberg means:

  • No lock-in to one engine's storage.
  • Several engines on one copy: Snowflake for SQL analytics, Spark for machine learning, others as needed.
  • Your storage: data files live in your own cloud bucket.

§6.1.2Iceberg tables in Snowflake

Type Catalog Snowflake can Other engines can
Snowflake-managed Iceberg table Snowflake (Horizon Catalog) Read and write, with most Snowflake features Read and write through Horizon's Iceberg REST catalog APIs
Externally managed Iceberg table An external catalog such as AWS Glue, Snowflake Open Catalog, Databricks Unity Catalog or another Iceberg REST catalog Read, and write where supported through catalog integration Read and write through their catalog

A Snowflake-managed Iceberg table:

CREATE EXTERNAL VOLUME ev_lakehouse
  STORAGE_LOCATIONS = ((
    NAME = 'uk-lake'
    STORAGE_PROVIDER = 'S3'
    STORAGE_BASE_URL = 's3://acme-lakehouse/iceberg/'
    STORAGE_AWS_ROLE_ARN = 'arn:aws:iam::123456789012:role/snowflake-iceberg'
  ));

CREATE ICEBERG TABLE core.orders_iceberg (
  order_id NUMBER, customer_id NUMBER, order_ts TIMESTAMP_NTZ, net_amount NUMBER(12,2)
)
  CATALOG = 'SNOWFLAKE'
  EXTERNAL_VOLUME = 'ev_lakehouse'
  BASE_LOCATION = 'orders';

An external volume defines where data files are stored and the cloud identity Snowflake uses.

§6.1.3Catalogs

Catalog Role
Horizon Catalog Snowflake's built-in catalog and governance layer; exposes Snowflake-managed Iceberg tables to external engines through Iceberg REST APIs, with Snowflake access controls applied
Snowflake Open Catalog Managed service for Apache Polaris, an open-source Iceberg REST catalog, for multi-engine lakehouses
Catalog integrations Connect Snowflake to external catalogs such as AWS Glue, Open Catalog, Unity Catalog or any Iceberg REST catalog
Catalog-linked databases Mirror the namespaces and tables of an external catalog into a Snowflake database automatically

At Summit 2026, Snowflake announced Apache Iceberg v3 support as generally available, including bidirectional read and write through Polaris in the Horizon Catalog.

§6.1.4Choosing standard or Iceberg tables

Choose standard tables when Choose Iceberg tables when
Only Snowflake queries the data Several engines need the same data
You want every Snowflake feature with least effort Data must stay in your own storage in an open format
Hybrid tables, some sharing features or specific capabilities are needed You're building a multi-engine lakehouse
Simplicity matters most Avoiding lock-in is a strategic requirement

Iceberg tables add responsibilities: storage account security, file lifecycle and compaction settings, catalog choice, and understanding which features differ from standard tables.

§6.1.5Interoperability patterns

Pattern How
Snowflake writes, Spark reads Snowflake-managed Iceberg; Spark connects to Horizon's Iceberg REST endpoint
Spark writes, Snowflake reads Tables in Open Catalog or Glue; Snowflake catalog integration or catalog-linked database
Databricks and Snowflake share data Unity Catalog Iceberg REST access or Delta UniForm tables read by Snowflake as Iceberg
Fabric reads Snowflake data Snowflake Iceberg tables via OneLake shortcuts or Fabric mirroring of Snowflake

§6.1.6Governance across engines

Open formats don't mean open access. Decide:

  • Which catalog is authoritative for each table.
  • How access control is enforced for engines outside Snowflake, through catalog-vended credentials rather than raw bucket access.
  • Where lineage and quality are tracked.

Giving every engine direct read access to the bucket bypasses catalog permissions entirely.

§6.1.7What good looks like

  • Iceberg used where multiple engines genuinely need the data.
  • One authoritative catalog per table, with credential vending for external engines.
  • External volumes with narrowly scoped cloud roles.
  • Standard tables kept for Snowflake-only workloads.

§6.1.8Red flags

  • Everything converted to Iceberg "for openness" with no second engine using it.
  • Spark jobs with full bucket credentials reading tables that Snowflake governs with masking policies.
  • Two catalogs both believing they own the same table.
  • No compaction or snapshot expiry, and storage growing without limit.

§7.1.1How access works

In Snowflake, privileges are granted to roles, and roles are granted to users or to other roles. Every object has exactly one owner role, which has full control of it.

  • A user has a default role and can switch roles, or use secondary roles to combine privileges from all granted roles in a session.
  • Roles granted to other roles form a hierarchy: a parent inherits the privileges of its children.

§7.1.2System roles

Role Purpose Guidance
ACCOUNTADMIN Top-level control, billing, account settings Very few users; MFA; never a default role; not for daily work
SECURITYADMIN Manage grants and users Platform security team
USERADMIN Create users and roles Identity administration or SCIM
SYSADMIN Create warehouses and databases Custom roles should roll up to it
ORGADMIN or organisation roles Organisation-level tasks Very few users
PUBLIC Granted to everyone Grant nothing sensitive to it

A common failure is objects created while using ACCOUNTADMIN, which then own everything and are hard to delegate. Create objects with dedicated admin roles.

§7.1.3The access-role and functional-role pattern

Separate what a privilege set is from who needs it:

Role type Example Holds
Access roles AR_SALES_MART_READ, AR_SALES_MART_WRITE, AR_WH_BI_USAGE Object privileges on specific databases, schemas and warehouses
Functional roles FR_SALES_ANALYST, FR_DATA_ENGINEER, FR_DBT_PROD Combinations of access roles matching a job 
-- Access role: read the sales mart
CREATE ROLE ar_sales_mart_read;
GRANT USAGE ON DATABASE analytics TO ROLE ar_sales_mart_read;
GRANT USAGE ON SCHEMA analytics.sales_mart TO ROLE ar_sales_mart_read;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics.sales_mart TO ROLE ar_sales_mart_read;
GRANT SELECT ON ALL VIEWS IN SCHEMA analytics.sales_mart TO ROLE ar_sales_mart_read;
GRANT SELECT ON FUTURE TABLES IN SCHEMA analytics.sales_mart TO ROLE ar_sales_mart_read;
GRANT SELECT ON FUTURE VIEWS IN SCHEMA analytics.sales_mart TO ROLE ar_sales_mart_read;

-- Functional role: sales analysts
CREATE ROLE fr_sales_analyst;
GRANT ROLE ar_sales_mart_read TO ROLE fr_sales_analyst;
GRANT ROLE ar_wh_bi_usage TO ROLE fr_sales_analyst;

-- Roll up to SYSADMIN so administrators can manage what the roles own
GRANT ROLE fr_sales_analyst TO ROLE sysadmin;

Users receive functional roles, ideally mapped from identity provider groups through SCIM.

§7.1.4Future grants

GRANT ... ON FUTURE TABLES applies privileges automatically to objects created later. Without them, every new table from dbt or a pipeline breaks analysts' access until someone re-grants. Future grants at schema level take precedence over database level.

§7.1.5Managed access schemas

In a normal schema, the object owner can grant access to their objects. In a managed access schema, only the schema owner or roles with MANAGE GRANTS can grant privileges:

CREATE SCHEMA analytics.sales_mart WITH MANAGED ACCESS;

Use managed access for curated data, so individual developers can't quietly share tables they create.

§7.1.6Database roles

Database roles are scoped to a database and travel with it, including through sharing and replication. They are ideal for access roles defined inside a data product database:

CREATE DATABASE ROLE analytics.sales_reader;
GRANT SELECT ON ALL VIEWS IN SCHEMA analytics.sales_mart TO DATABASE ROLE analytics.sales_reader;
GRANT DATABASE ROLE analytics.sales_reader TO ROLE fr_sales_analyst;

§7.1.7Service identities

Pipelines, dbt, BI tools and applications should each have their own service user with its own functional role, such as FR_DBT_PROD or FR_TABLEAU, holding only what that tool needs. Never share human accounts with tools.

§7.1.8Auditing access

  • SHOW GRANTS TO ROLE, SHOW GRANTS ON, and GRANTS_TO_ROLES and GRANTS_TO_USERS views.
  • Access history (Enterprise edition) shows which users read which columns.
  • Review members of ACCOUNTADMIN and SECURITYADMIN monthly.

§7.1.9What good looks like

  • Access roles for privileges, functional roles for people and tools, provisioned by SCIM.
  • Future grants and managed access schemas on curated data.
  • A handful of ACCOUNTADMINs using MFA, none with it as a default role.
  • Separate service users and roles per tool.

§7.1.10Red flags

  • Analysts granted SYSADMIN "so they can see everything".
  • Hundreds of direct grants to individual users.
  • Everything owned by ACCOUNTADMIN.
  • One ETL_USER shared by five tools and three contractors.

§7.2.1Why this matters

In 2024, attackers used credentials stolen by malware from customers' computers to sign in to about 165 Snowflake customer accounts that had no MFA, and stole large volumes of data. Snowflake's platform wasn't breached. Customers' authentication was the weak point. That campaign is covered in the scenarios section, and it drove major changes in Snowflake's authentication defaults.

§7.2.2User types

TYPE For Password allowed?
PERSON (or unset) Humans Only with MFA, and SSO strongly preferred
SERVICE Applications, pipelines, tools No; uses key pair, OAuth, PATs or workload identity federation
LEGACY_SERVICE Transitional type for services still using passwords Being retired
SERVICE_AGENT AI agents acting as services Non-password methods 
CREATE USER svc_dbt_prod TYPE = SERVICE DEFAULT_ROLE = fr_dbt_prod;

§7.2.3The removal of single-factor passwords

Snowflake is phasing out password-only sign-in in milestones:

Milestone Period Change
1 September 2025 to January 2026 MFA required for Snowsight sign-in with passwords
2 May to July 2026 New human users must use MFA; no new LEGACY_SERVICE users
3 August to October 2026 All human users need MFA for password sign-in; service users can't use passwords; LEGACY_SERVICE fully deprecated

By the end of October 2026, anything still signing in with a plain password will stop working. Inventory users with LOGIN_HISTORY and USERS views and migrate them now.

§7.2.4Humans: SSO first

  • Configure SAML single sign-on with Microsoft Entra ID, Okta or another identity provider, and enforce MFA and device policies there.
  • Provision users and roles with SCIM so leavers lose access automatically.
  • Where passwords remain, Snowflake MFA supports authenticator apps, passkeys and Duo.
  • Use authentication policies to restrict which methods and clients are allowed, for example SSO only for Snowsight:
CREATE AUTHENTICATION POLICY ap_humans
  AUTHENTICATION_METHODS = ('SAML')
  CLIENT_TYPES = ('SNOWFLAKE_UI', 'DRIVERS')
  MFA_ENROLLMENT = REQUIRED;
ALTER USER jane_smith SET AUTHENTICATION POLICY ap_humans;

A policy set on the account applies to every user without their own policy, including services. Give service users a separate policy that allows only their methods, such as key pair or workload identity federation, before tightening the account level.

§7.3.1Network rules and network policies

A network rule describes network identifiers. A network policy allows or blocks lists of network rules for the account, a user or an integration:

CREATE NETWORK RULE nr_corp_vpn
  MODE = INGRESS
  TYPE = IPV4
  VALUE_LIST = ('203.0.113.0/24', '198.51.100.10');

CREATE NETWORK RULE nr_dbt_cloud
  MODE = INGRESS
  TYPE = IPV4
  VALUE_LIST = ('52.45.144.63', '54.81.134.249');

CREATE NETWORK POLICY np_account
  ALLOWED_NETWORK_RULE_LIST = ('nr_corp_vpn');

CREATE NETWORK POLICY np_svc_dbt
  ALLOWED_NETWORK_RULE_LIST = ('nr_dbt_cloud');

ALTER ACCOUNT SET NETWORK_POLICY = np_account;
ALTER USER svc_dbt_prod SET NETWORK_POLICY = np_svc_dbt;
  • User-level policies override the account-level policy for that user.
  • Network rules can also describe private endpoint identifiers, such as AWS VPC endpoint IDs or Azure private link IDs, so you can allow only private connections.
  • Test with a second session before applying an account policy, or you can lock yourself out.

Every service user should have a network policy limited to where the service runs. It's also required for service users to use programmatic access tokens.

§7.3.2Private connectivity

On Business Critical edition and above, connect privately:

AWS AWS PrivateLink

§7.3.3Outbound access from Snowflake

By default Snowflake code can't reach the internet. Outbound access is explicit:

  • External access integrations with EGRESS network rules listing allowed hosts for UDFs, procedures and notebooks.
  • Secrets objects to hold API keys and OAuth credentials used by that code.
  • Storage integrations and external volumes for cloud storage.
  • Private connectivity to your own cloud services where supported.

Keep egress rules narrow and owned.

§7.3.4Encryption

  • All data is encrypted at rest with AES-256 and in transit with TLS.
  • Snowflake uses a hierarchical key model with automatic key rotation, and periodic rekeying available on Enterprise edition and above.
  • Tri-Secret Secure (Business Critical) combines a Snowflake-managed key with a customer-managed key in your cloud KMS. Revoking your key makes the data unreadable, which gives control and a kill switch, and also a serious availability risk if keys are mishandled.

§7.3.7Red flags

§7.4.1Policies instead of copies

Rather than maintaining filtered copies of tables for each audience, Snowflake applies policies at query time. The same table returns different results depending on who asks. Most of these features need Enterprise edition or above.

§7.4.2Dynamic data masking

A masking policy decides what a column returns per role or context:

CREATE MASKING POLICY gov.mask_email AS (val STRING) RETURNS STRING ->
  CASE
    WHEN IS_ROLE_IN_SESSION('FR_CUSTOMER_SERVICE') THEN val
    WHEN IS_ROLE_IN_SESSION('FR_ANALYST') THEN REGEXP_REPLACE(val, '^[^@]+', '*****')
    ELSE '** masked **'
  END;

ALTER TABLE core.customers MODIFY COLUMN email SET MASKING POLICY gov.mask_email;

Use IS_ROLE_IN_SESSION rather than CURRENT_ROLE(), so role hierarchy and secondary roles work as expected.

§7.4.3Row access policies

A row access policy filters rows:

CREATE ROW ACCESS POLICY gov.rap_region AS (region STRING) RETURNS BOOLEAN ->
  IS_ROLE_IN_SESSION('FR_GLOBAL_ANALYST')
  OR EXISTS (
    SELECT 1 FROM gov.role_region_map m
    WHERE m.region = region AND IS_ROLE_IN_SESSION(m.role_name)
  );

ALTER TABLE core.sales ADD ROW ACCESS POLICY gov.rap_region ON (region);

Keep mapping tables small, owned and audited. Policy logic runs for every query, so keep it simple.

§7.4.4Tag-based masking at scale

Applying policies column by column doesn't scale across thousands of columns. Use object tags:

CREATE TAG gov.pii_type ALLOWED_VALUES 'email', 'phone', 'name', 'national_id';

ALTER TAG gov.pii_type SET MASKING POLICY gov.mask_email;  -- policies for string columns with this tag

ALTER TABLE core.customers MODIFY COLUMN email SET TAG gov.pii_type = 'email';

Any column tagged pii_type is then masked by the policy attached to the tag, including in new tables when tags are applied by pipelines or classification.

§7.4.5Sensitive data classification

Snowflake can classify columns automatically, detecting semantic categories such as email, name, phone number and national identifiers, and apply system tags:

  • Run classification on demand or set up automatic classification on databases so new data is classified as it arrives.
  • Map classification results to your own tags, which then trigger tag-based masking.

Classification finds things people forget, such as email addresses inside free-text notes columns.

§7.4.6Other policy types

Policy Does
Projection policy Prevents a column from being selected in results while still allowing it in joins or filters
Aggregation policy Forces queries to aggregate with minimum group sizes, for privacy
Join policy Requires joins on specific columns
Secure views Hide view definitions and prevent optimisation-based data leaks; useful for sharing

§7.4.7Testing policies

  • Test with every functional role, including roles inherited through the hierarchy.
  • Check behaviour through BI tools and service users, not only Snowsight.
  • Remember owner's-rights stored procedures run as their owner; policies still apply based on context.
  • Use access history to confirm who reads sensitive columns in practice.

§7.4.8What good looks like

  • Tags drive masking for PII across the estate.
  • Automatic classification on databases receiving new data.
  • Row access policies for regional or tenant separation, tested per role.
  • Policies owned by a governance role, separate from engineers who own tables.

§7.4.9Red flags

  • Separate "masked copies" of customer tables maintained by nightly jobs.
  • Masking policies using CURRENT_ROLE() and failing for users with secondary roles.
  • PII discovered in unclassified free-text columns after an incident.
  • Engineers able to drop masking policies from tables they own.

A resource monitor tracks credits for warehouses and can notify or suspend:

CREATE RESOURCE MONITOR rm_bi WITH
  CREDIT_QUOTA = 500
  FREQUENCY = MONTHLY
  START_TIMESTAMP = IMMEDIATELY
  TRIGGERS
    ON 75 PERCENT DO NOTIFY
    ON 100 PERCENT DO SUSPEND
    ON 110 PERCENT DO SUSPEND_IMMEDIATE;

§S1.2The design

Component Detail

§S1.3What went well

  • Access requests became "join this Entra group", approved by data owners, applied within minutes by SCIM.
  • New tables from dbt were readable by the right analysts immediately, thanks to future grants.
  • Audits used access history and grant views to answer "who can see card data" in an afternoon.
  • The 2024 credential-theft campaign against Snowflake customers didn't affect them: SSO with MFA for humans and key pairs with network policies for services.
  • Milestone 3 of password deprecation in 2026 needed no changes.

§S1.4What went wrong

  • Role explosion risk. Early on, a role per individual schema and per operation created hundreds of roles. They consolidated read roles to domain level.
  • Sandbox sprawl. Sandboxes grew without limits until they added storage reports and a 90-day clean-up rule.
  • Secondary roles confusion. Masking policies written with CURRENT_ROLE() behaved unexpectedly for users with secondary roles. Rewriting with IS_ROLE_IN_SESSION() fixed it.

§S1.5Lessons

  • Design roles before users arrive. It is far harder to untangle direct grants later.
  • Automate with SCIM and Terraform. Manual grants don't scale.
  • Future grants and managed access make curated data both usable and controlled.
  • Strong authentication early avoids painful migrations later.

Organisation Online and store retailer

§S2.2Context

  • Several consumers read the same streams, so changes were sometimes consumed by one task and missed by another.
  • Streams went stale after a long weekend outage, requiring manual rebuilds.
  • Tasks ran every five minutes on a Medium warehouse whether or not data changed.
  • Logic lived in task definitions with no tests or version history.

§S2.3What they did

  1. Mapped the existing graph and grouped transformations into domains.
  2. Rebuilt logic as dbt models in Git with tests for keys, nulls and relationships.
  3. Materialised freshness-sensitive models as dynamic tables, with DOWNSTREAM lag on intermediates and 15 minutes on marts.
  4. Checked each large dynamic table's refresh mode and simplified queries that fell back to full refresh.
  5. Ran old and new pipelines in parallel for three weeks with reconciliation queries.
  6. Removed tasks and streams domain by domain.

§S2.4What went well

  • Failures fell sharply. No stream staleness or double consumption.
  • Credits dropped by about a third, because refreshes ran only when inputs changed and incremental refresh avoided full rebuilds.
  • Observability improved with the dynamic table graph and refresh history in Snowsight.
  • Changes became reviewable as dbt pull requests with tests.

§S2.5What went wrong

  • Full refresh surprises. Two models with complex window functions refreshed fully every cycle. Splitting them into simpler steps restored incremental refresh.
  • Lag expectations. Stakeholders assumed "15 minutes" meant exactly every 15 minutes. Lag is a maximum, so dashboards needed a freshness indicator.
  • Procedural steps such as calling a partner API didn't fit dynamic tables and stayed as tasks with procedures.

§S2.6Lessons

  • Declarative beats hand-built orchestration for most SQL transformations.
  • Check refresh modes on large tables.
  • Keep tasks for genuinely procedural work.
  • Parallel runs with reconciliation make migrations safe.

§S3.2What happened

  • Analysts complained dashboards were slow.
  • An engineer read that clustering improves pruning and applied clustering keys to every table over 1 GB, often on customer_id.

  • Search optimisation suits specific selective lookups.
  • Queueing is often the real dashboard problem, and multi-cluster warehouses fix it.

In 2024 a financially motivated group used credentials stolen by malware from customers' and contractors' computers to sign in to Snowflake customer accounts that lacked MFA and network restrictions, exfiltrate data and demand ransoms. Snowflake's own platform was not breached.

§S6.1Snapshot

Real incident. Summarised from Mandiant and Snowflake public reporting and security analysis. Details are simplified; check primary sources before quoting.

Item Detail
Threat actor UNC5537, a financially motivated group tracked by Mandiant
Period Activity from April 2024; public disclosure late May and June 2024
Victims About 165 Snowflake customer organisations notified of potential exposure
Publicly named victims Included Ticketmaster and Live Nation, AT&T, Santander, Advance Auto Parts and Neiman Marcus
Initial access Valid usernames and passwords harvested by infostealer malware
Root cause Customer accounts without MFA, often without network allow-lists, with some credentials years old and never rotated
Verdict Bad

§S6.2What happened

  1. Credentials were stolen long before. Infostealer malware families such as Lumma, Raccoon, RedLine and Vidar had infected computers belonging to employees and contractors, sometimes personal or gaming machines also used for work. They captured saved credentials, including Snowflake logins.
  2. Credentials were collected and tested. The attackers gathered credentials from criminal marketplaces and malware logs and tried them against Snowflake customer accounts.
  3. No MFA, no network restrictions. Many accounts accepted a password alone from any IP address.
  4. Data was taken. Using legitimate sign-ins and standard tooling, the attackers ran queries, created temporary stages and exported data.
  5. Extortion. Victims were pressed for payment, with data offered for sale on criminal forums.

Mandiant reported no evidence that Snowflake's own enterprise environment was breached. The weakness was customer authentication.

§S6.3Why it worked

Weakness Control
Password-only sign-in MFA for every human; SSO through an identity provider
Service accounts with passwords Service users with key pair, OAuth or workload identity federation
No network policies Account and user network policies allowing only known networks
Credentials never rotated Rotation and expiry; SCIM de-provisioning
Contractors' unmanaged devices Device compliance in Conditional Access; SSO rather than local passwords
Little monitoring Alerts on sign-ins from new IPs, unusual clients, and large data exports

§S6.4Aftermath

  • Law enforcement arrests and indictments of alleged members followed later in 2024.
  • Snowflake introduced stronger defaults: MFA enrolment prompts, the ability for administrators to enforce MFA, the Trust Center, and the multi-year programme to remove single-factor password sign-in, completing in October 2026.

§S6.5Lessons

  • Password-only access to a data platform is indefensible. Enforce MFA or SSO for humans and keyless methods for services.
  • Network policies limit the value of stolen credentials.
  • Infostealers are everywhere; assume credentials on endpoints will eventually leak.
  • Shared responsibility is real: a secure platform doesn't secure your account settings.
